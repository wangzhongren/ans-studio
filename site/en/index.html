Role-first governance for AI agents

Role-first organizing principle

An autonomous organization runtime for AI agents.

ANS Studio organizes multiple AI agents into a team with roles, boundaries, dispatch, and independent acceptance—not a single assistant working alone.

The organizing principle is Role-first: define business responsibility and roles before modules and code ownership. Write authority comes only from role boundaries. Claude is the default engine; Pi and Codex are also available. The CLI supports demo, Pi, Codex, and Claude.

A smarter assistant is not the same as an organization that can take responsibility.

A model can write code, but it does not know who should own the result. Role-first puts the organization before the code: roles before modules, boundaries before writes, evidence before acceptance.

  • Responsibility before modules

    Define business responsibility and roles first, then modules and code ownership; the role card states duties, and Section 1 of boundary.yaml lists the paths a role may change.

  • Boundaries are part of the runtime

    Write authority comes only from role boundaries. Out-of-bound writes are rejected before side effects and pointed back to the correct owner. Shell commands go through the approval chain like everything else.

  • Acceptance is an independent role, not a self-declaration

    A report saying “done” is only a statement; Proof independently checks delivery and hand-back evidence before issuing an acceptance card.

Three powers · five roles

Role-first lands as five built-in governance roles in new or empty projects. The three powers are proposal, team formation, and orchestration; communication and acceptance are not decision powers. None of the five holds final approval.

    Lead

    liaison Default entry

    Customer communication and the default entry point; writes intent to docs/intents/; also acts as workflow manager.

    PowerCustomer communication · Workflow management

None of the five holds final approval; final approval stays with you. Built-in roles ship with the app and have no role directories; their file writes are limited to governance files and evidence, and they do not implement or test.

From intent to acceptance, a checkable process

An autonomous organization runs on process: each formal task moves in a fixed order, and every output lands in files or the ledger, ready to review and verify.

  1. 01

    Intent confirmation Lead

    State goals, scope, and acceptance criteria to Lead; the intent is written to docs/intents/, and only passes to Draft after confirmation.

  2. 02

    Proposal and contracts Draft

    Draft forms a proposal and cross-role contracts from the intent; you choose accept, accept-quick, revise, or reject.

  3. 03

    Team formation and appointment Crew

    Nominates project roles and writes role cards and boundaries; appointments and each path write pass through confirmation.

  4. 04

    Flow and dispatch Steward

    Writes the flow record, orchestrates the flow, and dispatches formal tasks to project roles; tasks queue while a role is busy.

  5. 05

    Implementation and hand-back Project roles

    Project roles implement and test within their own boundaries, then hand back reports and evidence.

  6. 06

    Independent acceptance Proof

    Independently checks delivery and hand-back evidence and issues an acceptance card; you decide accept or reject.

docs/flows/todo-list-v1.yaml YAML 
flowId: todo-list-v1
version: 1
qualityTier: production
steps:
  - id: delivery-server
    title: Server delivery
    owner: <project role id>
    kind: dispatch
    status: done
    evidence:
      kind: dispatch
      ref: delivery-server

docs/flows/<flowId>.yaml is the single machine state; done needs ledger-matched evidence; advancing the flow is not approval.

Boundaries are gates, not prompts

Role-first does not rely on the model's good behavior: writes, shell, and automatic judgment each have a gate on the execution path.

  • Write gate

    Role cards, boundaries, proposals, flows, acceptance, and file writes get a preview or confirmation card before writing; out-of-bound writes are rejected and pointed back to the correct owner.

    write_file 角色卡/提案/… → rejected · owner: Draft / proposal

    The example keeps the real repository path; role directories in this project are named in Chinese.

  • shell approval

    Every role has shell capability, and all of it goes through approval; a read-only allowlist runs directly; risky, review, and deny each require approval from you or the judge agent.

    rm -rf build/ → approval card · runs only if approved

  • judge agent

    Read-only and fail-closed. Insufficient budget, insufficient evidence, unclear risk, or a missing intent all block automatic approval. A successful auto-approval is labeled “judge-approved” and never impersonates your click.

    Auto-approve: on → judge-approved

Honest caveat: shell has no OS sandbox; file side effects of an approved command are not covered by the write gate; the approval chain is the only control. Open only projects you trust. See README current limitations.

Three engines, one governance chain

Engines are the execution layer: switching engines does not switch the organization; role boundaries and gates stay on the same governance chain. Each engine uses its own configuration and never falls back to another engine when configuration is missing.

From a paper to a runnable governance system

ANS Skill is a role-first AI development skill inspired by the Role-First Software Governance (RFSG) paper; ANS is a name, not an acronym. Role-first comes from this paper, and ANS Studio turns it into a runnable desktop app and CLI: role cards, boundaries, and gates are implementations of its principles.

Wang, Zhongren. 2026. Role-First Software Governance: Asymmetric Authority Boundaries for AI-Native Agent Systems. DOI: 10.5281/zenodo.22824700
