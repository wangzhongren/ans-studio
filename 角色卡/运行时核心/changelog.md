## 2026-10-17 停止本轮清理失败后的永久隔离修复（Claude 真机卡死）

真机（诊断日志）：Claude 会话点「停止本轮」→ `session.abort.failed errorMessage="Query closed before response received"`；该轮随后以 AbortError 结束（底层轮次**确实已结束**），但之后每次发送都失败于「上一轮仍在运行或中止清理中」，队列反复重试、会话永久卡死。根因（`src/service/runtime/session.ts`）：`requestAbort()` 的 catch 同时置 `cleanupFailed=true; quarantined=true;`；`prompt()` 的 `underlying.then(...)` 仅在 `!turn.cleanupFailed` 时清 `quarantined`；finally 又以 `turn.cleanupFailed === true || (underlying !== undefined && !underlyingFinished)` 判定 ⇒ 清理一失败，即使底层轮次随后结束，隔离也永不解除。修复：①`quarantined` 唯一语义改为「底层 provider 轮次可能仍在运行」；②`underlying` settle（成功或失败）无条件清除隔离（`cleanupFailed` 不再参与清隔离）；③`requestAbort` catch 不再直接置 `quarantined`，`cleanupFailed` 仅保留为诊断/事件事实；④`underlying` 永不 settle 时 finally 仍置隔离并保持（fail-closed 不放宽）；⑤既有错误文案、`active` 判定、finally 的 settled 事件语义均未改变。测试：新增 `test/runtime-core/abort-quarantine.test.ts` 3 例——abort 拒绝＋underlying 稍后 settle ⇒ 下一轮可再次进入；abort 拒绝＋underlying 永不 settle ⇒ 反复尝试仍被隔离拒绝；正常 abort（不抛错）隔离生命周期不变。`test/runtime-core/session.test.ts` 原「cleanup 失败后下一轮仍 /清理中/」用例固化了缺陷行为，改为断言底层 settle 后隔离解除、下一轮 completed（终态仍为 aborted＋completed 两条、清理失败 denied 事件照实保留）。验证：`test/runtime-core` 聚焦 29/29 绿（含新增 3 例与改后旧例）；typecheck 仅剩 2 条既有错（`test/claude-adapter/session.test.ts` 的 `assert.rejects(session.abort!(), …)` 收 `void | Promise<void>`，非本角色边界、与本次改动无关）；全量三层 glob `node --test "test/**/*.test.ts"` 2420 计 / 2397 过 / 20 红 / 3 跳过——20 红与基线（本日 shell-judge 条：2373 计 / 2350 过 / 20 红 / 3 跳过）同类同量：8 条 Windows `symlink EPERM` 环境红、1 条 vendor 哈希钉、5 条 renderer/桌面 UI 源码钉、5 条其他角色在飞源码钉、1 条并发下 shell abort 时序（单独复跑通过），**无本次改动新增红**。未跑真实模型/凭据/网络，未 commit。
