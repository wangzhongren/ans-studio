## 二、B9.1 实施内容（对照任务条目）

### 2.1 新增 §「任务文本与哈希口径（worker 不用 shell 算 hash）」（v2 资源）

四条写死口径（`chief-workflow-v2.md` 新段）：

1. **任务文本只要求 worker 报告事实，不要求 hash**：chief→运营 stage-request、运营派生产线角色、
   幕僚直派验收角色的任务文本必须写明——完成文档/代码后**只报告路径、frontmatter/内容实际值与
   结论**（intentId/flowId/version/goal/scope/acceptance/nonGoals、commit OID、测试结论）；
   **不要自己算或转抄哈希**，`sha256` 由应用计算；任务文本只给**可核验证据路径**（path），
   不写「给出/附上 sha256」；旧模板要求 hash 时改为「路径 + frontmatter 实际值；hash 由应用计算」。
2. **hash 的唯一来源是应用**：应用在**任务收口**、`docs/acceptance` **归档**、`documentRefs` 生成与
   **依据/漂移校验**时按文件真实字节计算 SHA-256 并重算比对；模型/worker 回执中的 hash 不采信；
   A2/A5/A8/A9/A11/A12 的「hash」完成条件均指应用计算值。
3. **不得用 shell 算 hash**：worker 不得为取 hash 调用 `run_shell` 或任何 shell/解释器命令——点名
   `certutil -hashfile`、`Get-FileHash`、PowerShell/pwsh、`sha256sum`、`shasum`、`openssl dgst`、
   node/python 等；hash 不是 worker 产物。
4. **卡预算：3 张确认卡 + `merge-main`**：意图确认（intent-confirm，A3）+ 方案确认（proposal，A6）+
   任命确认（appointment，A10）+ 高风险合并卡 `merge-main`（A13/B4）；**不应出现额外的 shell 审批卡、
   stable-write 卡或其它客户门**；shell 审批是高风险动作，本流程不需要为 hash 触发任何客户卡；
   若 worker 因 hash 弹出 shell 审批卡，按**任务文本缺陷**处理（改写任务文本，不代答、不扩大卡预算）。

### 2.2 任务文本模板与各阶段点位的同步修正
