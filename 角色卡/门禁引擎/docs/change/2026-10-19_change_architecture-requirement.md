# 工程质量基线新增「架构与可扩展性」

## 客户原始批评（原话）

> 这个感觉也没有啥架构的啊，提案角色应该也要考虑到扩展性，给出一个架构方案啊。

客户指出：提案角色（Draft / 提案）给出的方案没有架构内容，必须考虑扩展性并给出架构方案。本批
只做**门禁引擎**属主部分（基线常量与五张内置治理角色卡文本、对应测试与文档）；判定逻辑、
写权、禁写、预授权、能力位与流程零变化。

## 真机证据

同轮真机验收中，两份提案的章节结构如实记录如下：

- **R1 提案**：只有意图 / 交付物 / 数据模型 / API / 权限 / 状态机 / 分页 / 前端 / 测试 / README /
  验收 / 分工 / 风险。
- **R3 提案**：只有状态机 / 权限 / 统计 / 契约 / 测试 / 分工 / 风险。

两者都没有**模块分解、依赖方向、扩展点、数据/契约版本与迁移策略**——正是客户所说「没有啥架构」。

## 基线新增（单一来源常量，逐字）

`src/common/门禁引擎/governance-roles.ts` 的 `ENGINEERING_QUALITY_BASELINE` 新增一条（插入在
「可维护性」之后、「可观测性」之前）：

```text
- 架构与可扩展性：模块分解与职责、依赖方向（无环）、数据流清晰；扩展点明确（新增状态/角色/导出格式/统计维度时改哪里、不改哪里）；数据 schema 与 API 契约有版本/迁移/兼容/弃用策略；横切关注点（配置/错误/日志/鉴权/测试缝）有归属；变更类提案必须附架构影响分析（模块/边界/兼容/回滚）。
```

五张内置治理角色卡（`liaison` / `rapporteur` / `nominator` / `convener` / `verifier`）逐字包含
扩展后的基线全文（原断言「五卡逐字包含基线」未放宽，自动覆盖新条目）。

## 各角色专属架构职责（卡片文本）

| 角色 | 专属架构职责 |
| --- | --- |
| Lead / 主理（`liaison`） | 1）客户提到演进/规模/未来需求（后续新增状态、角色、导出格式、统计维度、接入方）时，必须把可扩展性诉求写入意图 acceptance，不得遗漏；2）架构选择属 Draft / 提案 的提案权——只转达诉求，不自行替客户决定架构（模块划分、技术选型、版本/迁移策略）。 |
| Draft / 提案（`rapporteur`） | 1）提案必须含「架构方案」（新项目）或「架构影响分析」（变更）一节，逐项覆盖基线「架构与可扩展性」五项（模块分解与职责、依赖方向（无环）、扩展点（改哪里/不改哪里）、数据 schema 与 API 契约的版本/迁移/兼容/弃用策略、横切关注点归属），变更类还须写模块/边界/兼容/回滚影响；2）缺失或未覆盖时**不得建议 accept、不得进入实现**；发提案卡前文件必须已含该章节，**客户在提案卡上看到的内容必须包含它**，不得只口头说明。 |
| Crew / 组队（`nominator`） | 项目角色的写区（`boundary.yaml`）与角色卡必须与提案中的架构模块**一一对应**，禁止写区重叠；每个模块必须有明确属主（一个模块只归一个项目角色）。 |
| Steward / 统筹（`convener`） | 1）流程单与 `dispatch_task` 的任务描述必须引用提案中的架构模块/边界（模块名、依赖方向与写入归属），不得只写功能目标；2）流程必须存在 **contract-freeze 步骤**（先冻结 `docs/contracts/<name>-v1.md`）与**集成/端到端步骤**，两者缺一不得进入验收。 |
| Proof / 验收（`verifier`） | 1）验收必须核对实现与提案的架构声明一致：模块边界、依赖方向（无环）、扩展点位置、数据/契约版本与迁移策略，偏离声明须列为不通过；2）提案/交付缺少「架构方案」或「架构影响分析」章节，或实现偏离架构声明时，**不得建议 accept**。 |

## 跨角色依赖（须各自属主决定是否同步，本角色未越界修改）

1. **编排（`src/pipeline/orchestration/govern-session.ts`）**：该文件**逐字复制**了一份
   `ENGINEERING_QUALITY_BASELINE`（`govern-session.ts:528-540`，其注释明记「与门禁引擎五张内置治理
   角色卡里的同一基线逐字一致；改文案时两处必须同步」）。本批扩展基线后，两份物理副本**已不一致**
   ——编排属主必须同批补上「架构与可扩展性」行。同一文件的 `ENGINEERING_QUALITY_STAGE_REQUIREMENTS`
   （`:567`）与 trio Draft 纪律（`:670-671`「质量与证据」段）也应补「架构方案/架构影响分析」要求，
   否则治理会话提示词会落后于角色卡。
2. **编排 / 判断 agent（`src/common/编排/governance-judge.ts`）**：判断卡物证不解析提案章节。
   「缺架构章节不得建议 accept / 不得进入实现」目前是卡片行为约束；若要做成机械门槛，需编排属主
   在提案/验收判定中检查提案文件的架构章节。
3. **桌面（`app/desktop/**`）**：提案卡的呈现若只渲染提案文件摘要，需确认客户在卡上能看到
   「架构方案/架构影响分析」章节；本角色只写卡文本，无法保证渲染面。
4. **运行时核心 / 装配（`src/provider/runtime/tools.ts`）**：写 `角色卡/<id>/role-card.md` 时不校验
   架构模块与写区的一一对应（Crew 纪律目前是行为约束）。
5. **README / 产品文档**：角色职责概览与提案要求如逐项列出，由文档属主同步。

## 残余风险

- **架构要求仍是行为约束**：门禁层不解析 Markdown，「提案含架构章节」「写区不重叠」「流程含
  contract-freeze/集成步骤」「实现与声明一致」均依赖模型执行卡片纪律与客户/判断 agent 审查。
- **「一一对应」难以机验**：Crew 的模块—写区映射是语义判断；同一模块拆给多角色或一个角色覆盖
  多模块边界不清时，没有机械检查。
- **架构声明可形式化**：模型可能给出空洞的「模块分解」段落；卡片要求覆盖五项，但质量仍靠人工/
  判断 agent 评审。
- **卡片继续变长**：本批每张卡新增 1-2 条职责（约 2-4 行），提示词成本上升；未做长度预算评估。
- **两份基线副本的同步风险**：编排副本未在本批同步（跨角色边界），在同步前治理会话提示词与
  角色卡存在文案漂移。
- 真机端到端（客户提出演进需求 → Lead 写入 acceptance → Draft 给出架构方案 → Crew 按模块建角色 →
  Steward 含 contract-freeze/集成步骤 → Proof 核对声明一致）与独立复验未进行。
