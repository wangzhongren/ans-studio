# 五张内置治理角色卡加入工程质量基线

## 客户原始批评与批准

客户批评（经任务转达的要点，未提供逐字原文）：五个内置治理角色的角色卡缺少统一的**工程质量
基线**，验收关注点可以只落在功能上，健壮性/安全/可维护性/测试等工程质量维度没有硬约束；并且
存在「没有真实启动过应用、没有演示」就建议验收通过的空间。客户要求把「验收前必须真实启动应用
并演示」写成硬要求。

## 基线全文（单一来源常量，逐字复用）

`src/common/门禁引擎/governance-roles.ts` 的 `ENGINEERING_QUALITY_BASELINE`（导出常量）逐字如下：

```text
工程质量基线（默认生产级；客户明确选原型档才可放宽）：
- 正确性：验收标准逐条可演示；无 TODO/占位/假数据；边界与非法输入有明确行为。
- 健壮性：输入校验与上限、错误码一致、失败不破坏已有数据；持久化原子写与重启恢复；并发/重入有明确策略。
- 安全：认证/授权即使简化也要写清边界；防注入/XSS/路径穿越/CSRF；不记录密钥与敏感数据；零第三方依赖时说明理由。
- 可维护性：模块边界清晰、命名一致、只在约束处注释；README 含启动、架构、API、权限、状态机、已知限制与权衡。
- 可观测性：关键失败可诊断（结构化日志/错误信息），不静默吞错。
- 性能与容量：分页/上限/超时明确；不无限增长；给出已知容量边界。
- 前端：加载/空/错误态齐备；键盘可用、标签与对比度等基本可访问性；窄屏可用。
- 测试：单元+集成+端到端矩阵；权限与非法路径必须有负例；测试独立于实现；不得为保绿弱化断言。
- 交付：验收前必须真实启动应用并演示（启动命令、访问地址或截图/录屏）；未真实运行不得建议验收通过。
```

五张内置治理角色卡（`liaison` / `rapporteur` / `nominator` / `convener` / `verifier`）逐字包含
上述全文，并在其后各带「你的质量职责（<角色>）」专属要求。

## 各角色职责（卡片文本）

| 角色 | 专属质量职责（1-3 条） |
| --- | --- |
| Lead / 主理（`liaison`） | 1）意图阶段必须与客户确认质量档位（原型 / 生产；客户未指定时默认生产档），不得自行放宽；2）必须把工程质量基线（含质量档位与验收前真实启动应用并演示的要求）写入意图文件的 `acceptance`，逐项可核对。 |
| Draft / 提案（`rapporteur`） | 1）提案必须包含「质量基线与证据计划」一节，逐项对应基线，写明验证方式与所需证据；2）验收标准必须覆盖质量基线各项（含真实启动应用并演示的证据），不得只写功能验收。 |
| Crew / 组队（`nominator`） | 1）项目角色卡必须继承工程质量基线，并为每个角色写明其质量职责（含测试与真实演示责任）；2）测试角色的角色卡必须要求负例、边界、重启恢复与权限用例，不得只要求功能正例。 |
| Steward / 统筹（`convener`） | 1）流程单与 `dispatch_task` 的任务描述必须带工程质量基线与「真实启动应用并演示」要求；2）流程的 verification 步骤必须包含「真实启动应用并演示」（启动命令、访问地址或截图/录屏），未演示不得进入验收。 |
| Proof / 验收（`verifier`） | 1）验收必须逐项核对工程质量基线，并在核对报告中逐条给出结论与证据出处；2）没有真实启动/演示证据时不得建议 `accept`，须在验收报告中明确退回或要求补做；3）不得以「工具无 shell」为由跳过可执行的核对——Proof 已有审批档 shell，可执行的核对必须执行并留证。 |

## 跨角色依赖（须各自属主决定是否同步，本角色未越界修改）

1. **编排 / 判断 agent（`src/common/编排/governance-judge.ts`）**：验收卡的机械门槛目前只核对
   流程完成度（流程单 + 账本），**不核对**「真实启动应用并演示」证据。卡文本已要求 Proof 无证据
   不得建议 accept，但客户开启「替我决策」时，判断 agent 仍可能仅凭流程完成度代批验收卡。若要
   让「未演示不得进入验收」成为机械硬门槛，需编排属主在 `verifyAcceptanceMechanics` 增加演示证据
   物证检查（如要求流程单/验收报告引用启动命令与截图/录屏路径）。
2. **编排（`src/pipeline/orchestration/govern-session.ts`）**：`dispatch_task` 的任务描述目前由
   Steward 模型自行组织，代码层不注入基线文本；卡文本已要求必须携带。若要在派发物上强制，
   需编排在任务模板/提示词中拼装基线摘要。
3. **桌面应用（`app/desktop/session.ts`）**：Proof 卡的「你已有审批档 shell」依赖上一批
   （2026-10-19 all-roles-shell-approval）登记的桌面接线——`shellOperatorOnly` 仍为 su-only 时，
   Proof 实际无 shell，卡文本会领先于运行时；桌面属主切换后该表述才完整成立。
4. **运行时核心 / 装配（`src/provider/runtime/tools.ts`）**：写 `角色卡/<id>/role-card.md` 时
   只对 `boundary.yaml` 做内容校验，不校验角色卡是否继承质量基线。Crew「项目角色卡必须继承
   基线」目前是卡片行为约束；若要机械强制，需运行时/装配增加 role-card 内容校验。
5. **README / 产品文档**：角色卡文本新增基线，README 的角色职责概览若要逐项列出，由文档属主同步。

## 残余风险

- **基线主要是行为约束，机械强制点有限**：除「五卡逐字包含基线」由测试钉死外，意图 acceptance
  是否真的写入基线、提案是否有证据计划、验收是否真的逐项核对，均依赖模型执行卡片文本与客户/判断
  agent 审查；门禁判定层不解析这些 Markdown 内容。
- **演示证据可伪造/不可机验**：启动命令、访问地址、截图/录屏是物证，但本角色不做真实性核验；
  「真实启动」的最终判断仍在客户/判断 agent。
- **质量档位无机械开关**：「客户明确选原型档才可放宽」靠 Lead 卡片纪律与客户确认卡；没有代码级
  档位字段，模型不能自行放宽只是行为约束。
- **卡片变长**：每张卡新增约 11 行基线 + 3-5 行职责，提示词 token 成本上升、长卡可能稀释其他
  纪律的注意力；本批未做提示词长度预算评估。
- **api-spec.md 存在与本批无因果的旧口径**：其注册表代码块仍写 `id` 四人联合（缺 `verifier`）、
  `customerInput` 注释 Liaison=false、`shell` 注释「convener=readonly；其余 none」，为 2026-10-17/18
  批次遗留，建议由本角色另开文档校正批次处理；本批未改以免混淆归因。
- 真机端到端（Lead 确认质量档位 → Draft 证据计划 → Steward 流程含演示步骤 → Proof 凭证据验收）
  与独立复验未进行。
