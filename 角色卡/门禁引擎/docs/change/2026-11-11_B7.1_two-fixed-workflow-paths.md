## 二、B7.1 实施内容（对照任务条目）

### 2.1 首个 A1 精确 stage-request（`chief-workflow-v2.md` §「首个动作：A1 精确 stage-request」）

- 新增可复制的 `dispatch_task` JSON 示例，**写死**：`roleId:"convener"`、`task`（自足文本）、
  `taskKind:"stage-request"`、`workflowAction:"advance"`、`workflowPath:"A"`（路径 B 为 `"B"`）、
  `stage:"A1"`（路径 B 首请求 `"B1"`）、`flowId:"<flowId>"`、`sideEffect:"read-only"`。
- 可选 `requestedEvidence`（≤5 条证据路径提示，不是验收结论）；`workflowId` 首请求可省略
  （应用确定性生成并在回执给出），后续请求必须携带账本/回执中的 `workflowId`。
- **缺 `workflowPath`/`stage`/`flowId`/`taskKind` 任一 ⇒ 应用 fail-closed**（`stage-request-invalid`/
  `stage-request-required`）：不创建任务、不是普通派发、**不回退 legacy**；模型须补齐后重试。
- **禁止直派** product/rapporteur/nominator（`chief-production-dispatch-forbidden`）；生产线任务只由
  运营在真实受派回合内派发。
- **禁止 legacy run 概念**：stage-request 不得携带 `runId`/`pinned`/`baseDigest`，不请求写
  `.ans/trunk`/`.ans/runs`；若应用仍把 stage-request 受理为 legacy 星形派发（出现 `runId`、写
  `.ans/trunk`/`.ans/runs`），立即停手并如实报告路由缺陷，不继续 legacy 链、不伪造回执。
- 保持每个活动 workflow 至多一个 open advance 请求（`stage-request-open`）。

### 2.2 各阶段 fixed 任务字段与卡节奏（新增同名 §）

- **A1→A2**：运营派 product 生产任务（`roleId:"product"`、`flowId`、`workflowId`、`stage:"A2"`、
  `sideEffect:"docs"`，不带 `taskKind`、无 module）；产品写 `docs/product/<flowId>-intent-vN.md`。
- **A3/A6/A10**：三卡由幕僚发起/呈交；A6 绑定 `documentRefs`；A10 只任命、不派实现。

  （`stage:"A8"`）用 `activate_role_documents` v2 逐个 `role.activated`；A8 不弹客户卡。
- **A11**：A10 后发 `stage:"A11"` stage-request（选中角色/子集，`workflowId` 必填）；运营派实现任务
  （`workflowId`、`stage:"A11"`、`moduleId`+`modulePaths`、`sideEffect` 按实际声明，写任务串行）。
- **A12a**（先于 A11 实现派发）：幕僚直接创建验收标准任务（不经运营；应用按目标派生 review 目的；
  `stage:"A12a"`、`sideEffect:"docs"`）。
- **A12b**（A11 之后）：幕僚直接创建验收报告任务（`stage:"A12b"`）；A12 完成 = A12b accepted +
  report hash + 应用归档 `docs/acceptance/<flowId>-acceptance-vN.md`；不通过回 A11
  （`reworkOf:"A12b"`）。
- **A13**：merge-main 卡由应用构造、幕僚走应用卡通道呈交客户。
- 卡节奏补充：「A10 卡后发 A11 stage-request；A12a 先于 A11 实现派发；A12b + `docs/acceptance` 归档完成验收」；

  merge-main 必须客户本人、judge 不可代批）。
