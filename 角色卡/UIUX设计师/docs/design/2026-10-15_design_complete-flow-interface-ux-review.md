# 来源文档入口与仅保存恢复的设计短评

**设计结论：接受这两项具体方案，按下述文案和交互边界交客户确认。** 它们比客户已确认的完整流v2更具体：成果阅读多一次显式选文件，保存失败多两类仅补保存动作。原v2确认不代表客户已经批准本差异、预算/失败策略或实施。

本次仅只读[UI消费方案](../../../桌面UI/docs/design/2026-10-15_design_complete-flow-consumer-plan.md)、[Window A/C r3](../../../桌面窗口/docs/design/2026-10-15_design_complete-flow-ac-consumers.md)与[Core C/r2](../../../运行时核心/docs/design/2026-10-15_design_report-provenance-contract-c.md)。没有浏览器/真实桌面操作、未来API测试或生产改动；不修改[冻结v2规范](2026-10-15_design_desktop-complete-flow.md)和[原型](2026-10-15_design_desktop-complete-flow-prototype.html)字节，不声称新增状态已经实现。

## P3：先选来源角色的已列文档，再阅读

C目前没有准确的artifact fileRef，因此**不能把证据句子直接当成“阅读这份报告”的精确文件链接**。接受卡上动作改为 **「查看来源角色文档」**：按可信sourceRoleId，在原覆盖抽屉内展示B当前签发的该角色documentRefs，用户显式选择一个文件，再调用受限read。多一步的代价是需要用户识别文档；收益是入口准确表达所知范围，不误开同名文件或暗授读取权限。

- 抽屉标题建议 **「测试 · 来源文档」**（角色名按可信值）；列表说明 **「以下是当前项目中该角色已列出的可读文档，请选择要阅读的文件。」** 不写“已找到对应报告”，不默认第一项，不从evidence/标题/路径文本猜文档；目录仅分组，不能当可读文件或计入文件数。
- 文件项显示label与相对路径，动作 **「阅读」**。正文中有 **「返回来源文档」**；返回恢复该列表的展开、选中文档和滚动位置，并聚焦原文件项。关闭抽屉回原成果卡实际invoker；原卡离窗时按可信行身份定位或稳定备选，不能按同名文字搜索另一个卡。全过程不切当前聊天角色/runtime，不开启来源角色会话，不清聊天草稿或改变聊天阅读位置。
- 读取中说明 **「正在读取文档…」**，只禁该次重复读取；返回/关闭使旧请求序号失效，不假称已取消底层OS读取。B的scope/documentId/current context仍须匹配，旧响应不能在新列表或项目出现。

| 可信结果/能力 | 建议文案与动作 |
| --- | --- |
| 来源角色未知或已不在当前listing | **「无法确定来源角色，暂不能列出来源文档。」** 保留成果与证据原文，无伪装可读的按钮 |
| 来源角色有效但当前无documentRefs | **「该角色当前没有已列出的可读文档。」** 不自动换角色、扫描目录或尝试证据路径 |
| PROJECT_NOT_GRANTED/无B scope | **「尚未获得当前项目的文档读取许可，请重新选择项目文件夹。」** 如有重新选择入口，复用原生选择；不把按钮点击当授权、不在后台重选 |
| PROJECT_NOT_ACTIVE/STALE_SCOPE | **「项目文档列表已失效，请返回当前项目重新选择。」** 不在旧卡悄悄更新grant |
| UNSUPPORTED_ENVIRONMENT | **「当前环境暂不支持安全读取项目文档。」** 无反复重试或file:旁路 |
| 文件不存在/不再是文件/不可读等B错误 | 按权威安全错误给出对应原因，保留原列表/卡与路径；仅引用仍有效且允许重试时显示 **「重试读取」** |

本次设计接受的是这条“来源角色文档→用户显选→阅读”的最小路径，**不是已批准的准确一键报告定位**。若以后需要准确artifact链接，应另有可信文件引用合同；不纳入本短评。

## C2：原卡显示保存事实，恢复动作只补存

接受把source报告保存与target接收历史保存分别呈现，紧贴原报告/投递卡，使用次级状态行和明确动作；不得新建一张成果、把保存失败画成模型仍在运行，或把持久成功写成已验收。报告结论、投递/执行事实、历史保存三者不互相代替。

| 权威状态 | 建议原卡文案 | 动作 |
| --- | --- | --- |
| source enabled且PERSIST_FAILED，有原冻结reportId且retryAvailable=true | **「报告尚未保存，暂未继续回交。可补存原报告，无需重新运行任务。」** | **「重试保存报告」**；处理中 **「正在保存报告…」** 且禁重复点击 |
| target history=failed，原attemptId及可补材料有效 | **「本次接收历史未保存；执行状态以上方实际结果为准。」** 辅助说明 **「补存已有记录，不再次执行或投递。」** | 权威retryAvailable/retryHistoryAvailable允许时 **「重试保存历史」**；处理中 **「正在保存历史…」** |
| saved/already-saved | 分别 **「报告已保存」** / **「接收历史已保存」** | 更新同ID原卡，移除重试动作；不是“重新完成”“已验收”或第二份成果 |
| expired/SNAPSHOT_EXPIRED | **「可补存的会话材料已失效，无法在此补存。」** | 无假按钮，不用旧文字重建，不重模型补报告 |
| disabled | **「仅本次会话可见，未启用历史保存。」** | 保留原live回交/投递，不阻断、不暗建store、不显示保存按钮 |
| unknown-live/unsupported/无真实handle或ID | **「当前会话无法确认或不支持此保存恢复能力。」**（按实际原因细分） | 保留live与未知事实，不伪造reportId/saved；不新开会话补能力 |
| CONFLICT/INVALID/REPLAY_DAMAGED/REPLAY_CHANGED等不可补错误 | 分别说明冲突、记录不可自动补存等安全原因 | 不自动覆盖、截坏行或“再次执行”；retryAvailable=false时不呈现可点击重试 |

**source补存成功后的原流程不能被文案隐藏：** 按C/Window候选，Window可在原业务对象已登记且首次达到saved时，继续一次原待投递回交。按钮本身只按ID补存，不生成新报告、不重prompt源、不重复入队；不能把它宣传成“保存后绝不发生投递”。这是原回交恢复的首次推进，不是“重新执行”。目标 **「重试保存历史」** 则即使Provider原先未启动，补存成功也不能自行启动它。

实现接线须区分外层受限调用ok与内层save result.ok；外层ok不表示已保存。get/query和订阅只观察，同scope/原handle/ID的一次在途保存禁重复，状态乱序更新由权威当前结果归并，不因迟到unknown把saved倒退，也不因缺settled猜Provider没启动。B **「重试读取」** 与C这两个动作分别表意，不统称“重试”。

点击前记录当前卡、原按钮、聊天/抽屉阅读位置。按钮更新原卡不自动展开详情、不跳尾、不抢走正在输入的焦点；若用户焦点仍停在已消失的重试按钮，成功/失效后移到同卡可聚焦的状态行，下一Tab沿自然顺序。关闭/角色或引擎切换/项目变化不把旧scope的迟到回执或旧焦点送入新视图。状态可用polite live region报告一次“已保存/保存失败”，不朗读整份报告或重复产生完成通知；不以定时器猜过期。

## 交付与仍待决定

本短评接受设计方向，无新增选装项、确认弹窗或大原型。产品已独立接受P3多一步；具体接口/预算/保存失败阻投及恢复策略仍是本次客户需要确认的范围。UI应将上面文案/入口差异并入唯一消费方案，Window/Core沿各自union与权限边界提供权威结果；旧r1段落或引用需消费者自行同步，不能由本角色改他人文件。

上述交互只提出后续验收口径：来源列表显选/返回位置/关回原卡、不切scope；保存单在途/同卡更新/query零副作用/expired禁按钮/disabled原live保留。当前没有运行这些不存在的API或声称行为通过。冻结v2仍是原已确认版本，这两项差异待客户本次确认与明确实施授权。
