# 验收标准：wuxia-roguelike（v1）

本文件是 `wuxia-roguelike` 在 A12b 阶段进行独立验收的**唯一依据**。本文件只定义“如何验收、何为通过、何为失败、需要什么证据”，**不包含任何验收结论**；当前实现尚未全部完成，是否通过必须在 A12b 按冻结标准与任务指定的最终完整 OID 真实核对后另行报告。

## 2. 验收对象、范围与非目标

验收对象（静态交付物）：

- 入口页 `index.html`；
- 运行时代码 `game/`（`engine/`、`app/`、`player/`、`combat/`、`enemies/`、`progression/`、`items/`、`ui/`、`data/`）；
- 随包静态资源 `assets/`（如有）；
- 项目说明与手写验收清单 `README.md`、`qa/`（作为参考证据，不替代独立验收）。

范围内：AC-1~AC-8 与 T-1~T-7 的可观察行为、离线可运行性、关键架构约束的可感知后果。

明确不在验收范围（沿用意图的非目标，不因未实现而判失败）：

- 高精度美术、动画、配音、商业级打磨；
- 深度数值平衡（仅要求“能赢也能输”、单局 3-5 分钟闭环）；
- 移动端触屏适配、音效、多语言、联网排行、账号、云存档、付费；
- 复杂剧情、关卡编辑器、资产管线、长期元进度/成就。

质量档位：**可玩原型级（prototype-playable）**。“可玩即可”不等于可以缺证据；功能闭环与关键路径必须真实可复现。

## 3. 验收强度、证据通道与限制

### 3.1 强度调节

- **完整验收（默认）**：逐条执行 AC-1~AC-8 与 T-1~T-7，产出对应的静态核对记录与运行期证据；P0 证据必须带 sidecar。
- **轻量验收（仅当任务文本明确指定）**：核对任务指定写集与关键证据，至少覆盖 AC-1、AC-4、AC-7、AC-8 的冒烟路径与文件级静态检查；未覆盖的条目必须在报告中标“未验证”，不得写成通过。
- 强度只调节核对深度，不调节如实性：任何未实际观察到的行为都不得判通过。

### 3.2 本任务（A12a）的限制

- 本任务**不运行任何命令**（含 `mkdir`、目录创建、构建、启动服务器、运行游戏）；`write_file` / `edit_file` 会自动建目录。
- 本任务只产出本验收标准，不产出运行期证据，不写验收结论，不发客户验收卡，不宣告通过。
- 本文件不能作为“实现已通过”的证据；A12b 必须重新真实核对。

### 3.3 静态核对与运行期核对

- **静态核对**：读取入口页、脚本、样式、配置文本，检查加载方式、外部引用、模块语法、配置形态。静态通过只证明“文本层面符合”，不能替代运行期行为。
- **运行期核对**：以 `file://` 真实打开页面、真实游玩、真实观察控制台/网络/画面。AC-1~AC-8 的关键判定均为运行期或运行期 + 静态组合。
- 运行期无法取证（无浏览器/无显示环境/文件无法打开/任务未提供运行条件）时，对应条目写 **“未验证”（insufficient evidence）**，不得据代码阅读推断通过。

### 3.4 证据真实性

- 证据必须来自真实运行或真实文件读取；不得伪造截图、控制台输出、日志、时间或 hash。
- 截图不得裁掉关键上下文（地址栏 `file://`、控制台、HUD、结算面板等）；不得开启 DEBUG 覆盖真实状态。
- 缺证据、证据矛盾、证据不可复现、证据与指定 OID 不对应，均按 insufficient evidence 处理，不判通过。
- 录屏不是必需项；截图 + 文本记录/日志可满足证据要求，缺录屏不判失败。

## 4. 技术约束与静态核对（T-1~T-7）

| ID | 约束 | 核对方式 | 通过判定 | 失败边界 |
|---|---|---|---|---|
| T-1 | `file://` 双击直接打开可玩，无需服务器 | 运行期：文件管理器双击 `index.html`，观察地址栏与画面 | 地址栏为 `file:///.../index.html`，页面渲染并可进入游戏 | 必须经 http 服务器、构建产物或本地服务才能打开；白屏；双击无反应 |
| T-2 | 无构建链、无 npm/打包器依赖 | 静态：检查入口与脚本均为可直接加载的相对 `.js`；运行期：未执行任何构建步骤 | 不执行安装/构建即可打开；入口不依赖 `package.json`/打包产物 | 入口依赖构建产物、npm 安装、打包器或编译步骤 |
| T-3 | 无外部 CDN、外部字体/图片/音频 | 静态：检查 `index.html`、`game/**/*.js`、`game/ui/**` 样式中的 `http://`、`https://`、协议相对 `//`、外部 `@import`/`url(...)`；运行期：DevTools Network | 零外部网络请求；资源全部为本地相对路径；字体为系统字体栈 | 任何运行时外部请求、CDN 脚本、外链字体/图片/音频；离线后资源缺失 |
| T-4 | 禁止 ES Module | 静态：检查无 `<script type="module">`、无 `import`/`export` 语句、无动态 `import()` | 全部为经典脚本加载 | 出现 module 脚本或模块语法，导致 `file://` 下 CORS/加载失败 |
| T-5 | 禁止本地 `fetch`/`XHR` 读取配置 | 静态：检查无 `fetch(`、`XMLHttpRequest`、本地 JSON 运行时读取；配置为先加载的 JS 常量 | 配置随脚本加载，运行时不请求本地 JSON | 运行时 fetch/XHR 本地文件；配置读取失败导致无法开局 |
| T-6 | 打开页面无阻断性报错 | 运行期：DevTools Console/Network 记录冷启动与开始游戏 | 无 uncaught exception、无资源 404/CORS/fetch 失败；开始游戏可用 | 任一阻断首屏/开始/核心循环的报错；控制台未捕获异常；关键资源加载失败 |
| T-7 | 单一命名空间 `window.WX` 与固定脚本顺序 | 静态：读 `index.html` 的脚本顺序（config → engine → domain → ui → app → start）；运行期：Console 查 `window.WX` 与模块对象 | 顺序符合架构 §5.1；`window.WX` 及各模块对象存在；启动调用发生在依赖之后 | 顺序错误导致模块 undefined；业务逻辑散落在入口页；启动前访问未加载模块 |

补充判定口径：

- T-3 的“外部引用”以**运行时是否发起外部请求**为最终判定；注释或文档中的网址不计为失败，但不得被实际加载。
- T-6 中控制台的**非阻断性警告**（如弃用提示、样式警告）不单独判失败；但任何影响开局、战斗、升级、结算、重开的异常均按失败处理。
- T-7 的“全局污染”只核对是否以 `window.WX` 为唯一模块命名空间；不因第三方调试变量或浏览器自身注入判失败。

## 5. AC-1 ~ AC-8 验收标准

通用前置条件（A12b 执行时）：

- 已取得任务指定的最终完整 OID，且当前被验内容与该 OID 一致；否则停止并回报。
- 使用真实浏览器（建议 Chrome/Edge 近期稳定版），记录操作系统、浏览器版本、窗口分辨率与缩放（建议 1280×720、100% 缩放）。
- 运行期证据保留地址栏、控制台/网络面板或关键游戏画面；文本记录写明操作步骤、预期、实际观察。
- 任何“通过”必须同时满足该 AC 的“通过判定”；触及任一“失败边界”即该 AC 不通过。

### AC-1 可直接打开入口页面进入游戏，无需安装依赖/构建/服务器，页面无阻断性报错

- 优先级：P0（阻断）。
- 类型：运行期 + 静态。
- 验收方法：冷启动直接 `file://` 打开 + 控制台/网络检查 + 开始游戏一次 + 重复打开一次。
- 可复现步骤：
  1. 不启动任何服务器、不执行安装/构建；在文件管理器双击 `index.html`（或浏览器地址栏输入 `file:///.../index.html`）。
  2. 打开 DevTools 的 Console 与 Network（勾选保留日志），刷新一次页面。
  3. 观察首屏与开始界面；点击“开始”进入游戏，确认可操作。
  4. 再刷新一次，重复进入开始界面，确认不是偶然可用。
- 可观察证据：地址栏为 `file://` 的首屏截图；Console 无阻断错误的截图；Network 零外部请求的截图；开始游戏后的画面截图。
- 通过判定：页面正常渲染；开始界面可见；点击开始进入可操作的游戏状态；Console 无 uncaught exception、无关键资源 404/CORS；无需安装/构建/服务器；重复打开仍可用。
- 失败边界：白屏或首屏不渲染；必须经服务器/构建才能运行；出现 module CORS、fetch 失败、脚本 404 等阻断错误；开始按钮无效；刷新后不可用。
- 证据命名示例：`docs/verification/wuxia-roguelike-ac1-open-console-v1.png`、`docs/verification/wuxia-roguelike-ac1-menu-v1.png`、`docs/verification/wuxia-roguelike-t3-network-v1.png`。

### AC-2 玩家可移动、受伤、死亡；敌人会持续出现并构成威胁

- 优先级：P0（阻断）。
- 类型：运行期。
- 验收方法：键盘移动观察 + 受击观察 + 死亡/结算观察 + 持续刷怪观察。
- 可复现步骤：
  1. 开始游戏，使用 WASD 与方向键分别向上/下/左/右移动，观察角色位置变化。
  2. 保持不动或靠近敌人，观察生命值下降与受击反馈；记录两次扣血之间是否存在短暂无敌/间隔。
  3. 站立不动直至生命归零，观察是否进入失败结算，而不是卡死或继续游戏。
  4. 在安全位置观察一段时间，确认敌人持续出现并会主动接近/构成威胁。
- 可观察证据：移动前后位置对比截图；受击时生命值下降截图；生命归零与失败面板截图；连续刷怪画面截图或带时间戳的记录。
- 通过判定：四方向移动有效；敌人接触/攻击会造成生命下降；生命归零触发明确的失败/结算状态；敌人持续生成并能造成威胁。
- 失败边界：无法移动或移动无反馈；敌人不造成伤害；生命归零后无死亡/结算；敌人不刷新或完全不构成威胁；角色瞬死到无法观察/无任何可玩性。
- 说明：受击无敌帧是架构 §3/§5 的支撑要求，记录其是否存在；若缺失但不影响本 AC 的可玩性判定，作为“架构符合性偏差”单独记录并回报，不自动等同于产品 AC-2 失败；若导致瞬间连续扣血、无法正常游玩，则计入失败边界。
- 证据命名示例：`docs/verification/wuxia-roguelike-ac2-move-v1.png`、`docs/verification/wuxia-roguelike-ac2-hit-v1.png`、`docs/verification/wuxia-roguelike-ac2-death-v1.png`。

### AC-3 自动攻击生效：无需手动瞄准即可对范围内或最近敌人造成伤害

- 优先级：P0（阻断）。
- 类型：运行期。
- 验收方法：不进行任何攻击/瞄准输入，观察自动索敌、伤害与击杀。
- 可复现步骤：
  1. 开始游戏后不点击攻击、不按攻击键、不移动鼠标瞄准；静止观察至少 10 秒。
  2. 靠近或等待敌人进入攻击范围，观察攻击表现（投射物/范围效果/命中反馈）与敌人生命值变化。
  3. 保持自动攻击，观察敌人死亡与击杀计数增加。
  4. 若存在多个敌人，观察攻击目标是否为范围内最近敌人（或符合架构的索敌规则）。
- 可观察证据：静止无输入状态下的攻击与敌人受伤/死亡截图；击杀计数变化截图；必要时两帧/两段带时间戳的记录。
- 通过判定：无任何手动瞄准/攻击输入时，自动攻击按冷却触发；敌人实际掉血/死亡；击杀计数增加；索敌目标符合“范围内最近”或架构约定的规则。
- 失败边界：必须按键/点击才能攻击；无自动攻击；攻击不造成伤害；只能朝鼠标方向攻击；敌人永远不掉血；攻击表现存在但实际无伤害结算。
- 证据命名示例：`docs/verification/wuxia-roguelike-ac3-autoattack-v1.png`。

### AC-4 波次可推进并产生明确胜负结算，结算后可重开并再次完整游玩

- 优先级：P0（阻断）。
- 类型：运行期。
- 验收方法：完整跑到胜利 + 另一局失败 + 重开再玩。
- 可复现步骤：
  1. 开始一局，观察波次计数/计时推进与敌人强度变化；记录波次从 N 到 N+1 的可观察变化。
  2. 正常游玩至胜利条件，观察胜利结算面板（结果、统计/重开入口）。
  3. 另起一局，故意站立受击至失败，观察失败结算面板。
  4. 在胜利或失败结算面板点击重开，观察是否回到可操作的游戏状态；再游玩一小段确认完整循环可再次进行。
- 可观察证据：波次推进截图；胜利面板截图；失败面板截图；重开后回到游戏并可操作的截图。
- 通过判定：波次/计时确实推进；胜利与失败都能产生明确、可区分的结算；结算面板有清晰结果与重开入口；重开后生命/等级/经验/波次/计时等单局状态重置，且可再次完整游玩。
- 失败边界：波次不推进；只有失败没有胜利路径（或反之）；结算面板不出现/结果不明确；重开无效或残留上一局状态；重开后卡死/不可操作。
- 说明：提案 §3.4 要求“能赢也能输”，仅能失败或仅能胜利均不满足 AC-4。
- 证据命名示例：`docs/verification/wuxia-roguelike-ac4-wave-v1.png`、`docs/verification/wuxia-roguelike-ac4-victory-v1.png`、`docs/verification/wuxia-roguelike-ac4-defeat-v1.png`、`docs/verification/wuxia-roguelike-ac4-restart-v1.png`。

### AC-5 击杀敌人可获取经验，经验达到阈值触发升级，升级出现至少 2-3 个强化选项且选择后效果可感知

- 优先级：P0（阻断）。
- 类型：运行期。
- 验收方法：击杀/拾取经验 → 触发升级 → 数选项 → 选择 → 对比效果。
- 可复现步骤：
  1. 击杀敌人，观察经验掉落或经验值增加；拾取后确认经验条/数值变化。
  2. 持续获取经验直至达到阈值，观察是否进入升级状态并展示强化选择面板。
  3. 数清本次可用选项数量（至少 2 个，目标 3 个），确认选项名称/描述可区分，不是占位重复项。
  4. 在面板打开期间观察世界是否冻结（敌人是否停止移动/造成伤害），记录观察结果。
  5. 选择一个强化，确认面板关闭、游戏恢复；用可观察指标验证效果（如伤害数字、攻击间隔、移动速度、最大生命、拾取范围、暴击等），记录强化名称/id 与选择前后差异。
- 可观察证据：经验增加截图；升级面板与选项数量截图；选择后面板关闭并生效的截图；选择前后可量化对比记录（文本）。
- 通过判定：击杀/拾取确实增加经验；达到阈值触发升级；选项数量 ≥2（目标 3）且可区分；选择后效果真实生效且可被观察到；选择后游戏正常恢复；升级期间世界按架构冻结。
- 失败边界：击杀不产生经验；经验不增加或阈值不触发；升级面板不出现；选项少于 2 个/重复占位/无法选择；选择后无任何可感知效果；选择后卡在面板或世界继续伤害玩家。
- “效果可感知”的判定：至少一项可用数值或明确画面变化证明（如攻击间隔从 X 变为 Y、伤害数字变大、移速明显变化、最大生命提升等）；仅有文字提示而无数值/表现变化不算通过。
- 证据命名示例：`docs/verification/wuxia-roguelike-ac5-exp-v1.png`、`docs/verification/wuxia-roguelike-ac5-levelup-v1.png`、`docs/verification/wuxia-roguelike-ac5-effect-v1.png`。

### AC-6 至少 1 种武器或道具可通过实际玩法获取并使用或生效

- 优先级：P0（阻断）。
- 类型：运行期。
- 验收方法：通过正常游玩路径获取，并观察使用/触发效果。
- 可复现步骤：
  1. 正常游玩，记录首次获得初始武器之外武器/道具的途径（掉落拾取、波次奖励、升级选项、场景拾取等）。
  2. 获取后确认其进入背包/装备/生效状态（UI 可观察）。
  3. 使用或触发该武器/道具，观察实际效果（新增攻击、伤害提升、属性增益、叠加层数等）。
  4. 若支持叠加/成长，至少观察到一次叠加或数值增长；若不支持，记录其单次获得与生效即可。
- 可观察证据：获取路径与获得瞬间截图；效果触发前后对比截图；必要时记录道具名称与数值变化。
- 通过判定：至少 1 种非初始武器/道具能通过实际玩法获得；获得后可使用或自动生效；效果可观察；不是仅存在于配置或 UI 列表中。
- 失败边界：只有初始武器；道具无法通过正常玩法获得；只能通过控制台/改文件获得；获得后无任何效果；效果仅文字描述无实际结算。
- 证据命名示例：`docs/verification/wuxia-roguelike-ac6-acquire-v1.png`、`docs/verification/wuxia-roguelike-ac6-effect-v1.png`。

### AC-7 HUD 可读：生命、等级/经验、波次/计时等关键信息可见

- 优先级：P0（阻断）。
- 类型：运行期（目视/截图核对）。
- 验收方法：游戏进行中检查 HUD 四类关键信息与数值更新。
- 可复现步骤：
  1. 以 1280×720、100% 缩放开始游戏，截取游戏进行中的完整画面。
  2. 核对生命（数值/血条）、等级与经验（数值/经验条）、波次、计时（剩余或已生存时间）是否同时可见。
  3. 让生命、经验、波次、计时发生变化，确认对应显示会更新而非静态占位。
  4. 可选：将窗口调至 1024×768 或常见笔记本分辨率，确认关键信息不被遮挡/裁切。
- 可观察证据：游戏进行中的 HUD 截图（含分辨率与缩放记录）；数值变化前后的截图或文本记录。
- 通过判定：四类关键信息同时可见；文字/数值清晰可读（对比度、字号、无重叠）；数值随游戏状态更新。
- 失败边界：任一关键信息缺失；文字不可读/被遮挡/重叠；数值不更新；仅靠控制台或开发者工具才能看到。
- 证据命名示例：`docs/verification/wuxia-roguelike-ac7-hud-v1.png`。

### AC-8 单局 3-5 分钟内可完成完整闭环，离线可玩

- 优先级：P0（阻断）。
- 类型：运行期（含离线环境与计时）。
- 验收方法：断网冷启动 + 完整玩一局并计时 + 重开一次。
- 可复现步骤：
  1. 断开网络（关闭 Wi-Fi/有线或启用系统飞行模式；也可在 DevTools 设 Offline），确认页面仍可从 `file://` 打开。
  2. 记录开始时间（墙钟），从开始界面进入游戏，完整经历“移动—自动攻击—清怪—拾取经验—升级—选择强化—继续战斗—胜负结算”。
  3. 记录结算发生时间（墙钟），计算单局时长；确认本局为胜利（或至少完成完整闭环并产生明确结果）。
  4. 在结算面板点击重开，再游玩一小段，确认离线状态下重开与再次游玩正常。
  5. 记录本局中闭环各环节是否都实际发生，而非仅存在代码。
- 可观察证据：DevTools Offline/系统断网状态下的游戏截图；开始与结算时间记录（文本，含日期、时区、浏览器）；完整闭环各环节截图；重开后截图。
- 通过判定：离线状态下可打开并完整游玩；**一次胜利单局**的墙钟时长在 180–300 秒（3–5 分钟）内；闭环各环节均真实发生；结算后重开正常。
- 失败边界：需要联网才能加载/游玩；离线白屏或资源缺失；完整闭环缺少任一环节（无拾取、无升级、无强化、无结算、无重开）；胜利单局时长 <180 秒或 >300 秒；无法产生明确结果；重开失败。
- 计时说明：失败单局可以短于 3 分钟，用于验证失败与重开路径，但不能替代“3-5 分钟完整闭环”的胜利计时证据。若游戏在失焦时自动暂停，应保持标签页前台并记录暂停情况；计时以墙钟起止为准，排除暂停时段需在报告中说明。
- 证据命名示例：`docs/verification/wuxia-roguelike-ac8-offline-v1.png`、`docs/verification/wuxia-roguelike-ac8-timing-v1.txt`（记录起止时间、时长、结果）、`docs/verification/wuxia-roguelike-ac8-loop-v1.png`。

### 6.2 证据文件命名

规则：

### 6.3 Sidecar 与 hash

- P0 证据必须配 sidecar：`<artifact>.meta.json`，格式 `evidence-meta/v1`；至少包含 `schema`、`artifact`、`sha256`、`bytes`、`lines`、`generatedAt`，并按需写 `acIds`、`command`、`metrics`。
- **不手写 sha256/bytes/lines**：由应用在生成/登记证据时计算并写入；验收文档与报告不预写 hash 值。
- sidecar 的 `acIds` 必须覆盖该证据对应的 AC；`generatedAt` 不得早于 artifact 的 mtime。
- 证据被修改后 sidecar 会过期（mismatch）；应重新生成证据与 sidecar，不得改 artifact 迁就旧 sidecar，也不得伪造 sidecar。
- 单次验收若无法生成合规 sidecar，相关 P0 证据按 insufficient evidence 处理，不得口头宣称通过。

## 7. 判定口径与未验证处理

- **通过**：在该 AC 的全部“通过判定”上都有真实、可复现、与指定 OID 对应的证据，且未触及任何失败边界。
- **不通过**：触及任一失败边界。报告必须记录真实现象与证据，不得用“基本可用”“应该没问题”替代。
- **未验证 / 证据不足**：未实际执行、环境不具备、证据缺失/不可读/矛盾/无法复现、证据与 OID 不对应。此类结果不得写成 Pass，也不得据此宣告整体通过。
- **阻塞**：无法取得被验内容、无法确认指定 OID、文件不可读、运行环境不可用等导致无法开始核验；按 blocked 回幕僚，不静默等待。
- 静态核对通过只能支持对应技术约束，不能单独证明 AC-1~AC-8 的运行期行为；尤其 AC-1、AC-4、AC-8 不得仅凭代码阅读判通过。
- 任何“可玩即可”的解释不得降低 AC-1~AC-8 的事实性要求；美术/平衡不完美不导致失败，但功能缺失、阻断报错、无法闭环必须如实判失败。
