## 0.5 目标（本次增量，正文口径）

**让「暂停」成为玩家可以信赖的战斗控制**：战斗中按 `Esc` 立刻停住这一局，再按 `Esc` 原样接着打。

三条可判定的目标（按优先级）：

1. **停得住**：暂停期间**战斗输入不产生任何状态变化**，**战斗计时不推进**（含结算用时），玩家离开再回来不会被偷走血量、冷却或时间。
2. **接着走**：恢复后从暂停瞬间的状态**连续继续**——位置、气血、内力、冷却、蓄力、房间进度全部一致，无跳变、无补算、无一次性大步进。
3. **可复现**：暂停不消耗随机数、不改变随机序列，同种子下「是否暂停过」不影响地牢布局、敌人配置与战斗随机结果。

不追求：暂停菜单的扩展功能（设置、存档、地图等），也不把暂停做成时间操控（减速/逐帧）——见 §4.2 非目标。

## 1. 目标用户与场景（本次增量视角）

| 用户 | 场景 | 关心什么 |
| --- | --- | --- |
| 玩家（最终用户） | 战斗中被打断（接电话、开门、看消息），需要立刻停住这一局 | **按一下 Esc 就停**；回来接着打，不因为离开而掉血、不吃冷却、不计时 |
| 玩家（最终用户） | 想看清 Boss 弹幕 / 当前局势，或短暂思考走位 | 暂停时画面**仍然可见**，而不是黑屏；暂停状态**一眼能看出** |
| 客户（验收人） | 在自己机器上验证「暂停真的冻结了战斗」 | 暂停后**敌人不动、计时不走、按键无反应**；再按 Esc 状态**接着原来的走**，没有跳变 |
| 策划 / 实现 / 美术 | 按意图拆工 | 暂停的**冻结边界**（冻结什么、不冻结什么）写清楚，验收可执行 |
| 运营 / 质检 | 派发与核对 | 每条增量 AC 有明确「怎么验」和可观察证据 |

## 2. 要解决的问题

1. **当前暂停能力只被当作 P1 加分项**（v3 AC-21），客户本次把它作为**明确的功能要求**提出：这是可玩性底线，不是加分项。
2. **「暂停」最常见的实现缺陷是「假暂停」**：UI 上盖了一层遮罩，但底层仍在跑——敌人继续移动与攻击、技能冷却继续走、蓄力继续涨、结算用时继续跳、持续伤害继续结算。玩家回来时已经被打死或数值已变。客户明确要求「**冻结战斗输入与计时**」，因此验收必须**分别**验证「输入冻结」与「计时冻结」两件事，不能只看遮罩。
3. **暂停与「同种子复现」可能互相污染**：若暂停期间仍推进随机数、或恢复时补算错过的帧，会破坏可复现性（v3 AC-20/AC-32）。暂停必须**不消耗随机数、不补算、不跳帧**。
4. **暂停切换要幂等且不误触**：连按 Esc、长按、暂停中被窗口失焦等场景不得导致双次切换、卡在暂停态或状态错乱。

## 3. 客户原话（逐字保留，不改写、不缩略、不转述）

> 在现有「2D 金庸武侠 roguelike」项目中增加战斗暂停/继续功能——按 Esc 暂停与继续，暂停时冻结战斗输入与计时。

**从原话直接落到约束的四点**（仅作拆解标注，不替代原话）：

- 「按 Esc 暂停与继续」→ 同一个键**双向切换**；暂停与继续必须是同一个入口，不要求额外按键。
- 「暂停时冻结战斗输入」→ 暂停期间玩家操作**不产生任何战斗效果**。
- 「暂停时冻结……计时」→ 暂停期间所有与战斗进程相关的时间推进**停止**。
- 「战斗暂停」→ 作用域是**战斗内**；标题/结算等非战斗界面不因本需求改变行为。

## 4. 范围与非目标

### 4.1 范围（In scope，本次增量）

**P-1 暂停与继续的切换**
- 战斗进行中按 `Esc` 进入暂停；暂停中再按 `Esc` 返回继续。
- 暂停状态必须是**可观察的显式状态**：画面保持渲染（不黑屏、不白屏），并显示**可读的暂停覆盖层**（至少可读到「暂停」字样与「按 Esc 继续」的提示）。
- 切换必须**幂等**：一次按键只切换一次；连按 / 长按不得出现「暂停→继续→暂停」的抖动或卡死。

**P-2 冻结战斗输入**
- 暂停期间，全部战斗输入**无效且无副作用**：`WASD`（移动）、`J`（普攻）、`K`（蓄力/释放）、`Shift`（冲刺）、`E`（拾取）。
- 冻结意味着**不产生状态变化**，而不只是「视觉上没动」：输入不得改变位置、气血/内力、冷却、蓄力值、拾取结果、随机数状态。
- 暂停前已按住的键（例如正在蓄力中按下 Esc）：进入暂停后**蓄力进度停止**；恢复后从暂停时的进度**继续**，不得清零、不得直接释放。

**P-3 冻结战斗计时**
- 暂停期间以下与战斗进程相关的时间推进**全部停止**：敌人 AI 决策与行动、敌人与 Boss 攻击节奏 / 弹幕生成、技能与冲刺冷却、蓄力进度、持续伤害与持续回复结算、掉落 / 拾取物存在时长等战斗内计时。
- **结算用时统计必须冻结**：暂停 `N` 秒后继续，本局结算界面的「用时」不得因这 `N` 秒而增加（这是「计时冻结」最直观的可观察证据）。
- 恢复后计时**从暂停时的值接着走**，不补算暂停期间的时间、不跳帧、不产生「一次性追赶」的大步进。

**P-4 与既有系统的一致性**
- 暂停**不得消耗随机数**、不得影响随机序列：同一种子下，是否使用过暂停，都不改变地牢布局、敌人配置与战斗随机结果（对齐 v3 AC-20 / AC-32）。
- 暂停覆盖层属游戏内像素 UI：**32 色板内**、**320×180 逻辑分辨率下可读**、随整数倍放大（对齐 v3 AC-6/AC-7/AC-8）。
- 暂停与恢复不得产生未捕获异常 / 未捕获 Promise 拒绝（对齐 v3 AC-30）。

**P-5 边界行为**
- 暂停中触发窗口失焦 / 切标签页后返回：仍处于暂停态（不得自动恢复，也不得叠加两层暂停）。
- 死亡瞬间 / 结算界面 / 标题界面：不引入本需求的新行为（暂停只在战斗内生效；非战斗界面按 Esc 不得造成状态错乱或崩溃）。

| AC-40 | P0 | 恢复**状态连续**且暂停**不污染随机序列**，同种子复现不变 | ① 暂停前记录：玩家与敌人位置/气血/内力/冷却/蓄力值/当前房间进度 → 暂停 10 秒 → 恢复 → 立即比对，全部一致；② 存在随机要素（掉落/生成）时，暂停前后序列不因暂停时长而改变；③ **同种子对照**：同一种子下「全程不暂停」与「中途暂停 N 次」两种玩法，地牢布局、房间类型序列、Boss 房位置一致（对齐 v3 AC-20）；④ 单测覆盖「暂停期间时间步不推进 / 随机数不被消耗」，保留真实输出 |
| AC-41 | P1 | 边界健壮性：暂停与常见异常输入组合不崩溃、不白屏、不卡死 | 逐项实测并记录：① 蓄力中暂停 / 冲刺无敌帧中暂停 / 受击瞬间暂停 / Boss 弹幕中暂停 / 死亡同帧暂停；② 快速连按与长按 `Esc`；③ 暂停中切走窗口再切回（仍处暂停态、未叠加）；④ 暂停中反复按键后再恢复；⑤ 非战斗界面（标题 / 结算）按 `Esc`。以上均不得崩溃、不得白屏、不得卡在无法恢复的暂停态 |
| AC-42 | P1 | 暂停证据齐备，且全流程无未捕获错误 | ① 新增 1 张截图 `evidence/screenshots/10-pause.png`：战斗中暂停覆盖层可见、画面非空白、提示可读（真实浏览器、关闭调试层）；② 单测真实输出含「暂停冻结输入 / 冻结计时 / 不消耗随机数」断言且全绿；③ 从标题到结算（含一次暂停使用）console 无 `error`、无未捕获 Promise 拒绝 |

## 6. 质量档位（v4 口径）

- **P0（缺一即不交付，共 35 条）**：v3 的 30 条 P0 全部继续有效；本次新增/升档 —— **AC-21（Esc 暂停恢复，升档）、AC-37（暂停可观察可读）、AC-38（输入冻结）、AC-39（计时冻结）、AC-40（状态连续 + 不污染随机序列）**。即「暂停/继续」本身属于交付门槛。
- **P1（应当达成，共 7 条；缺口不阻塞交付但必须进「遗留问题」）**：AC-11、AC-27、AC-30、AC-31、AC-32、**AC-41（边界健壮性）**、**AC-42（暂停证据与无未捕获错误）**。
- **P2（可省）**：v3 的非验收加分项继续适用（音效、更多敌人、成就等），本次不新增 P2 项。
- 质量基线补充：暂停状态必须**一眼可辨**（玩家不用猜「是不是卡住了」）；恢复必须**无感连续**（不出现瞬移、数值突变、弹幕突现）。

## 7. 约束、假设与风险

### 7.1 约束（沿用 v3，仅列与本次增量相关者）

- 原生 ES Modules + Canvas 2D、无构建步骤、零第三方运行时依赖、全程离线（O-1~O-5 有效）。
- 逻辑分辨率 320×180 整数倍放大；渲染只用固定 32 色板；暂停覆盖层同样受此约束。
- 不写项目外目录、不 `pip install`、不 commit 不发布（O-6、O-7 有效）。
- 种子是唯一随机输入；暂停不得成为第二个随机源或时间源（对齐 v3 R-6）。

### 7.2 关键假设

- 暂停以「时间步不推进」的方式实现（实现方式由方案定，产品只要求可观察的冻结效果）。
- 结算用时**可被冻结**：暂停期间经过的时长不得计入本局用时；计时基准与实现方式由方案决定，但必须同时满足「暂停期间冻结」与「恢复后连续」两条可观察要求。
- 键盘 `Esc` 在目标浏览器中可被游戏正常捕获（桌面 Chromium 系 + 键鼠）。

### 7.3 风险与缓解（产品侧口径）

| 编号 | 风险 | 影响 | 缓解办法（产品侧口径） |
| --- | --- | --- | --- |
| RP-1 | 「假暂停」：遮罩有了、模拟仍在跑 | AC-38/AC-39 不过，玩家回来已被打死 | 输入冻结与计时冻结**分开验**（AC-38 / AC-39）；以「结算用时不因暂停增长」作为最硬证据；单测必须断言时间步未推进 |
| RP-2 | 恢复时补算暂停期间的时间（一次性跳帧） | 状态跳变、弹幕突现、玩家猝死 | AC-40 要求恢复后状态逐项一致、无大步进；单测覆盖恢复首帧 |
| RP-3 | 暂停期间仍消耗随机数 | 同种子复现塌掉（AC-20/AC-32 连带失效） | AC-40 同种子对照（不暂停 vs 暂停 N 次）；单测断言随机数不被消耗 |
| RP-4 | 长按 / 连按 `Esc` 造成双次切换或卡死 | 玩家卡在暂停态，无法恢复 | AC-37 幂等要求 + AC-41 连按/长按实测 |
| RP-5 | 暂停前正在蓄力 / 冲刺 / 无敌帧，状态处理不当 | 蓄力清零、无敌帧延长、冷却异常 | AC-38 ⑤ 明确「暂停中进度停止、恢复后从该进度继续」；AC-41 覆盖这些组合 |
| RP-6 | 暂停覆盖层文字在 320×180 下读不清或超出 32 色 | AC-37 不过 | 覆盖层按 32 色板内像素 UI 设计；验收以截图可辨为准（对齐 v3 R-8） |
| RP-7 | 计时口径由「累计帧数」改为「墙钟时间」以求省事 | 暂停冻结失效，且不同机器用时不可比 | 以 AC-39 的可观察结果为准；是否采用墙钟由方案决定，但必须满足冻结与连续两条 |
| RP-8 | 窗口失焦被浏览器自动暂停（visibility）与游戏内暂停叠加 | 双重暂停、恢复后状态错乱 | AC-41 ③ 明确切走再回来仍处暂停态、不叠加、可正常恢复 |

## 8. 验收与交付口径（增量部分）

- **交付判定**：**P0（35 条）全部通过** = 可交付；任一 P0 不通过 = 不交付。**「暂停/继续」属 P0，不能作为遗留项延期。**
- **P1 缺口处理**：P1（7 条）不通过不阻塞交付，但必须在最终汇报「遗留问题」中逐条列出（哪条 AC、缺口、影响）。
- **证据规则**：口头结论不算证据；每条通过的 AC 需能给出可复现路径（命令 / 文件 / 截图 / 单测输出）。
- **版本规则**：本文件落盘后**只读**；暂停口径若再变化（例如是否隐藏 HUD、是否允许暂停中退出），产品出 v5，不回改 v4。**下游一律按最新版本（当前 v4）工作。**
- **最终汇报须包含**（在 v3 四要素基础上补一条）：① 做了什么；② 测试与素材校验结果；③ 如何启动；④ 遗留问题；⑤ **暂停功能的验收证据位置**（AC-37~AC-42 对应的单测输出与 `10-pause.png`）。
