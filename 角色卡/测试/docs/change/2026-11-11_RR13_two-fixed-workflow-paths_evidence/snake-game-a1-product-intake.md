# snake-game · A1 产品侧受理与准备记录

## 1. 客户原始表述（原话照录）

> 做一个贪吃蛇游戏，要求键盘控制、计分、重开、边界碰撞（撞边界即失败 / 结算）。

## 2. 产品侧受理结论

- **结论：可受理（accepted-with-open-questions）。**
- 客户目标表达完整、可执行：四个点名能力（键盘控制、计分、重开、边界碰撞即失败/结算）构成一个边界清晰、闭包完整的单局小游戏，无相互矛盾之处，也无必须先行澄清才能受理的硬阻塞项。
- 与运营 A1 受理记录（`docs/governance/convener/snake-game-a1-intake.md`）对照：**功能域初判、非目标初判、成功标准初判三者与客户表述一致，未发现偏差。**
  - 运营第 2 节列出的四项必含功能域与客户原话逐项对应，无遗漏、无加戏。
  - 运营第 3 节成功标准初判中「撞边界必须判为失败/结算，不得仅穿墙重生或静默继续」是对客户「撞边界即失败/结算」的正确解读，产品侧确认保留这一强约束。
- 需要提醒 A2 的一点表述风险（非偏差）：客户写的是「边界碰撞」而非「必须绘制可见的边界墙」。**碰撞语义已明确（撞即失败/结算），但边界的视觉呈现是否需要（画框/墙体/仅场地边界）属视觉问题**，应作为开放问题在 A2 澄清，不得由产品侧或实现侧擅自决定。
- 受理层面的一个前置事实：当前基线为空项目，无既有意图/方案/源码/证据可复用（与运营第 4 节一致）；运行形态未定，直接影响技术栈与验收方式，属 A2 必须先清的第一顺位问题。

## 3. 产品视角的范围 / 非目标初判（供 A2，非最终）

### 3.1 目标用户与场景初判（仅初判，A2 需客户确认）

- 用户：单一本地玩家（本人自娱/演示用途为主），无账号、无网络、无社交。
- 场景：在本地打开即玩的短时单局游戏；一局结束（失败）后可立即重开再来。
- 推断依据仅限客户原话与项目上下文（空项目、单人本地小游戏），属产品侧假设，**须在 A2 由客户确认，不得直接当作用户画像定稿**。

### 3.2 范围初判（客户点名，必含）

1. 键盘方向控制蛇的移动；
2. 计分与分数展示；
3. 一局结束后的重开能力；
4. 边界碰撞判定：撞边界即失败并进入结算（客户原话的强语义）。

### 3.3 非目标初判（建议明确排除，待 A2 客户确认）

- 多人联机 / 对战；
- 排行榜、账号体系、云端存档；
- 移动端触控、手柄等其他输入形态；
- 关卡编辑、皮肤系统、成就系统等增强项；
- 美术资源与音效的精修（是否接受最小可用画风见开放问题 P-Q7）。

### 3.4 质量档位初判（供 A2 定档，非定稿）

- 产品侧建议按「最小可用但完整可玩」档位受理：四个点名能力全部可用、失败与重开闭环正确、无明显卡死/状态残留；不以美术精修、性能压榨、多端适配为目标。
- 若客户希望更高档位（例如精致视觉、动画过渡、本地最高分持久化、难度曲线），需在 A2 明确追加，否则默认不做，避免范围隐性膨胀。

## 4. A2 意图撰写需要澄清的开放问题清单

下列问题分两组：Q1–Q9 为运营已列问题（产品侧逐条确认保留，并补充「为何重要 / 期望澄清到什么颗粒度」）；P-Q10 起为产品侧增补。**本清单是提问，不是答案，不得据此写成意图正文或验收标准定稿。**

### 4.1 运营已列问题（产品侧确认保留）

- **Q1 运行形态（最高优先）**：纯前端网页版（浏览器直接打开即玩）还是桌面可执行程序？是否允许构建步骤？
  - 为何重要：决定技术栈、交付物形态与验收证据方式；也直接决定 P-Q2「入口」的答案。建议 A2 让客户用一句话选定一种，不接受「都行」。
- **Q2 交付形态与入口**：单页 HTML 即可，还是需要独立前端工程（源码 + 构建产物 + 启动说明）？
  - 产品侧补问：**入口如何被打开**——双击 HTML 以 `file://` 直接打开，还是必须经本地静态服务器/构建后启动？若要求「直接打开即玩」，则实现不得依赖需要服务器的模块加载方式。此项须在 A2 落成明确约束。
- **Q3 控制方式细节**：仅方向键，还是同时支持 WASD？是否允许反向立即掉头（常规禁止）？是否需要暂停？
  - 产品侧补充必须澄清项：**页面失焦/未点击时键盘输入是否生效**（是否需要先点击画布获取焦点）——这直接影响「打开即玩」的体验与验收判定，属于常被漏掉的可用性问题。
- **Q4 计分规则**：每吃一个食物 +1 还是按等级递增？是否显示最高分（会话内 / 本地持久化）？
  - 产品侧补充：**重开时分数是否清零**（默认应清零，最高分若存在则保留）；**最高分是否跨刷新持久化**（涉及是否使用本地存储，属范围决策，须客户明示）。
- **Q5 碰撞与结算语义**：撞边界即失败已明确；撞自身是否也判失败（常规做法）？结算页形态（分数 + 重开按钮）具体如何？
  - 产品侧补充必须澄清的三点：
    1. **结算形态**：游戏内覆盖层弹窗，还是跳转独立页面？（影响「重开」是就地复位还是重新加载）
    2. **失败后的状态**：蛇是否停止移动、是否仍响应方向键（应冻结输入，需确认）；
    3. **重开是否清空整局**：分数、蛇身长度/初始位置、食物位置是否全部复位（产品侧认为必须全部复位，待客户确认并写入验收）。
- **Q6 场地与速度**：固定网格尺寸？移动速度 / 难度递增是否纳入范围？
  - 产品侧补充：速度是否**恒定**（建议默认恒定，难度递增列为可选增强）；网格尺寸是否允许随窗口自适应（影响「边界」在视觉上的定义是否与逻辑边界一致）。**逻辑边界必须与可见场地边界一致，不允许视觉与判定错位**——此点建议直接作为意图层约束保留。
- **Q7 视觉与资源**：是否接受最小可用画风（纯色方块 / Canvas 绘制），是否需额外美术资源？
  - 产品侧补问：是否需要**可见边界墙**（对应第 2 节的表述风险）；是否需要中文界面文案。
- **Q8 非目标确认**：多人、排行榜、账号、音效、移动端触控等是否明确排除？
  - 产品侧建议：A2 把「非目标」写成显式清单并向客户确认一次，避免后续按「客户没说不行」扩张范围。
- **Q9 验收证据方式**：以何种证据验收（可运行本地页面截图 / 手动操作步骤清单）？
  - 产品侧补充：需明确**由谁执行验收**（客户本人手动试玩 / 项目内可复现步骤 + 截图留证）；建议 A2 至少确定「可复现的手动操作脚本 + 关键状态截图」这一组合，具体证据规范由后续质量/验收阶段定，不在 A1 定稿。

### 4.2 产品侧增补问题

- **P-Q10 单局边界**：一次「开局」是否只包含一局？是否要求连续多局累计成绩，还是每局独立？（影响结算与重开的语义）
- **P-Q11 初始状态**：开局时蛇的初始长度、位置、初始移动方向（是否静止待首次按键后开始移动）是否需要规定？
  - 具体问法：开局是否「按方向键后才开始移动」——这是新手体验常见期望，也影响「失败判定何时开始生效」。
- **P-Q12 食物生成规则**：食物是否保证不出现在蛇身上？是否同一时刻只有一个食物？（产品侧认为这是正确性的必要条件，但需客户/意图层面确认后写入验收）
- **P-Q13 失败判定是否唯一**：除撞边界、撞自身外，是否存在其他失败条件（如超时、撞墙后延迟结算）？客户原话只点名边界，其他需显式排除或纳入。
- **P-Q14 分数展示位置**：分数常驻显示在页面（HUD）还是仅结算页显示？客户要求「计分」，产品侧理解为**游戏过程中实时可见**，需确认。
- **P-Q15 键盘输入细节**：是否需要防止浏览器默认行为（方向键滚动页面）？是否要求按键长按连发/单次触发？（影响操作手感，属可验收的交互细节）
- **P-Q16 语言与文案**：界面文案用中文还是英文？是否需要开始页/标题？
- **P-Q17 兼容性范围**：需要支持哪些浏览器/操作系统？（若客户无要求，产品侧建议限定为「客户本机常用现代浏览器」，并写入非目标以免过度投入）
- **P-Q18 客户原话与约束留痕**：A2 意图文档须原样收录第 1 节客户原话；客户若有口头补充（如「就做个简单的」），也须落成约束条款而非口头默契。
