## 3. 对目标 / 范围 / 成功标准的初步理解

**目标**：交付一个可游玩（可运行、可由人实际操作并得到反馈）的贪吃蛇游戏。

**范围（客户原话圈定的四项）**：

1. **键盘控制** — 玩家通过键盘方向输入控制蛇的移动方向。
2. **计分** — 具备分数统计与展示。
3. **重开** — 一局结束后可重新开始游戏。
4. **边界碰撞** — 蛇撞到场地边界时需有碰撞处理（具体行为待澄清）。

**成功标准（初步）**：上述四项功能均可用，且游戏可正常启动运行、可完成一局完整游玩流程（开始 → 操作 → 得分 → 结束 → 重开）。

以上为初步理解，**不是**已确认的验收标准；正式验收标准应在 A2 意图及后续验收条款中确定。

## 4. 待产品澄清的缺口清单

以下为进入 A2 前需要客户/幕僚澄清的缺口，逐条列出（每条标注「为什么需要问」）：

1. **目标平台 / 运行形态** — 浏览器网页、桌面窗口程序、终端（TUI）还是其他？决定技术栈与验收方式。
2. **技术栈 / 语言** — 客户是否有指定（如 HTML+JS、Python 等），还是交给策划与实现方决定？
3. **界面形态与视觉要求** — 网格化像素风 / 简单方块 / 是否需要美术素材、配色、字体？有无明确的画面尺寸或风格参考？
4. **边界碰撞后的行为** — 撞墙即游戏结束（失败）、穿墙（从对侧出现）、还是停止/反弹？客户原话只说了「边界碰撞」，未说结果。
5. **计分规则** — 吃一个食物固定加分？随长度/时间变化？是否需要在界面上实时显示分数？
6. **重开方式** — 结束后按键重开、按钮重开、还是自动重开？重开是否清零分数？
7. **游戏结束条件** — 除边界碰撞外，蛇咬到自己身体是否也算结束？
8. **是否需要以下附加能力**（客户原话未提，需确认是「不做」还是「后续再做」）：暂停/继续、难度分级或速度递增、最高分记录与持久化、音效、移动端触屏支持、多语言。
9. **场地与节奏参数** — 网格大小、蛇初始长度、食物生成规则（是否允许出现在蛇身上）、移动速度，是否由实现方默认取值即可。
10. **验收/演示方式** — 由谁、以何种方式判定「可玩」：现场演示、截图/录屏、还是自动化测试？是否需要在本地可一键运行且写明运行方式。

> 若客户对 1–7 未给明确答复，A2 不得自行臆定为已确认需求；应按幕僚既定流程以默认建议 + 明确标注「待确认」的方式推进。
