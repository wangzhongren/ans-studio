# 后台任务 B1–B4 验收：先写死「怎样算做到」

客户要的效果很具体：模型启动开发服务器后，工具**立刻**把回合还给模型；之后模型能查看日志、停止任务；关闭角色会话时，仍在运行的服务器被清理。今天的行为是整轮被长进程占住，所以这次要证明的不只是「多了一个工具」，而是**启动不阻塞、任务可管理、关闭会清理、失败不撒谎**。

### 2.3 本功能明确不承诺的事

以下不是缺陷，而是已确认边界；验收时必须看到功能文档与工具描述如实写明，不能把限制藏起来或说成已解决：

1. **不跨会话、不跨应用重启**：任务表、日志缓冲、pid 都只在内存；会话关闭或应用重启后不存在，旧任务号只能返回「未知任务」。
2. **日志不落盘**：会话结束后日志消失，不能事后从磁盘找回。
3. **应用直接退出可能残留进程**：正常关闭/淘汰会话会 dispose 清理；应用崩溃、被强杀、断电或当前桌面退出流程不逐个 dispose 会话时，后台进程可能存活。Windows 上 `taskkill` 不可用时只回退终止直接子进程，孙进程可能残留；POSIX 上程序自行 `setsid`/双 fork 也可能逃出清理。
4. **轮次结束/停止本轮不杀后台任务**：这是功能本身；停止只由显式 `stop_background_task` 或会话 `dispose` 触发。
5. **后台任务不受 10 分钟命令级时限约束**：这正是功能目的；以并发上限、显式停止和会话清理控制风险。

## 三、成功标准 S1–S6

每条都要有当前候选上的**可执行证据**（测试用例名、命令、退出码、原始输出）；只有代码阅读或设计论证不算动态证据。

### S1 启动工具在进程持续运行时立即返回任务号与 pid

**必须观察到**

1. 用一个会持续运行并打印日志的 fixture（如 Node 脚本）调用 `start_background_task`：工具返回 `ok:true`，含任务号（形如 `bg-1`）、真实 pid、状态 `running`。
2. 返回时 fixture **仍在运行**，工具没有等 `close`；实测耗时以设计 §3.2.7 的 spawn 事件/error 等待上界（约 2 秒）为参考，且必须明显短于 fixture 的持续运行时间。
3. 返回的 pid 与真实子进程对应（管理器断言或系统进程查询可核对），不是占位值。
4. 随后 `list_background_tasks` 能看到该任务为 `running`，启动时间与命令摘要存在（摘要按设计截断）。

**判失败**：必须等进程退出才返回；返回时进程已结束或 pid 不存在；返回成功但实际没有任务；只返回任务号没有 pid/状态。

### S2 列表、读取（尾部行、截断标记）与停止可用

**必须观察到**

1. **list**：返回当前会话全部保留任务的摘要（任务号、状态、pid、启动时间、命令摘要、退出码）；空会话如实说「没有后台任务」；不猜测已过期任务。
2. **read**：默认 `stream:"both"`、默认 40 行、上限 200；能读到该任务已打印的 stdout/stderr 尾部；`stream` 选择生效；进程自然退出后状态变为 `exited` 且退出码如实。
3. **read 截断**：单路输出超过 256 KiB 时，读取结果明确标 `truncated`，只返回尾部，不返回损坏的多字节字符（UTF-8 安全）。
4. **stop**：先 SIGTERM，250ms 后 SIGKILL，1s 内观察到 `close` 才算 `stopped`；返回退出事实；停止后 pid 对应的进程/进程组不再存在（平台允许的核对方式内）。
5. **自然退出**：fixture 自行结束后，`read`/`list` 显示 `exited` 与真实退出码，不把自然退出说成被停止。

**判失败**：read 无截断标记却丢日志；截断切坏多字节字符；stop 在未观察到 `close` 时就宣告 `stopped`；状态与真实事件不符。

### S3 会话 dispose 清理

**必须观察到**

1. 会话仍有运行中任务时调用 `dispose()`：所有运行中任务被终止（并行，共用同一终止预算），管理器标记已关闭，dispose 幂等。
2. dispose 后 `list` 为空或管理器不可用；对旧任务号的操作返回「未知任务」，不假装任务还活着。
3. dispose 后再次 `start` 明确失败「会话已关闭，未启动」；即使审核在此前恰好通过，也**零 spawn**（竞态分支有测试或可复现证据）。

**判失败**：dispose 后任务仍在运行；dispose 不幂等或抛错；关闭后 start 仍能启动；靠应用退出钩子代替会话 dispose 的清理（O5 未授权）。

### S4 轮次中止/结束不杀后台任务

**必须观察到**

1. 至少一条可执行测试或可复现运行时记录：模拟轮次中止/「停止本轮」后，后台任务仍为 `running`、pid 仍存活、`read` 仍可读。
2. 代码层面没有把轮次 signal/abort 接到管理器的终止逻辑；停止只由显式 `stop` 或 `dispose` 触发。

**判失败**：轮次一结束任务被终止（等于功能目的没有实现）；测试只证明「dispose 会清理」而没有反证轮次中止不清理。

### S5 三引擎通过注入的 `options.tools` 都能看到四个工具

**必须观察到**

1. 分别覆盖 **Claude、Codex、Pi** 三条会话装配路径：注入含四工具的 `options.tools` 后，引擎实际可见/注册的工具清单包含四个工具名（Pi 走生产入口的 `"tools" in adapterInput` 分支）。允许离线/注入引擎测试，不要求线上模型。
2. 四个适配器路径（§2.5）零 diff；不得为暴露工具而改适配器。
3. 只证明 `buildGovernedTools` 返回了四工具，**不等于**三引擎可见；三引擎证据必须分别落到各装配路径。

**判失败**：只测了一个引擎或一个共享工具构造函数；改了任一适配器；工具只在类型上存在但引擎注册清单没有。

### S6 上限、淘汰与日志缓冲按设计默认值

**必须观察到**

1. 同时运行任务数上限 **8**：第 9 个被拒（与 F4 共用证据）。
2. 保留任务数 **32**：超出后按「最老的已结束任务优先」淘汰；运行中任务永不淘汰；被淘汰任务号读取返回明确「未知任务」。
3. 每路输出缓冲 **256 KiB**；`read` 默认 40、上限 200；终止预算 SIGTERM→250ms→SIGKILL→1s。
4. 若实现调整了上述任一默认值，必须附客户明确意见/授权证据；本轮交接没有记录任何调整，因此按设计默认值验收。

**判失败**：上限/预算与设计不一致且无客户意见证据；运行中任务被淘汰；用无限缓冲代替环形缓冲。

## 四、失败与边界标准 F1–F10

这些场景共同证明「失败不撒谎、拒绝零 spawn、边界不扩大」。每条都要求当前候选上的可执行证据。

### F1 空命令/纯空白命令

`start_background_task("")`、`"   "` → `ok:false`，明确无命令可执行；**零 spawn、无任务、无 pid**，不调用审核。

### F2 F-7 守卫命中

`npm run dev &`、`a && b`、`echo $(x)` 等 → 在审核之前被拒；**`shellGate` 一次都没被调用**（spy/计数为零）；零 spawn、无任务；诊断沿用 `shell.guard.blocked`（字段白名单内）。

**判失败**：被拒但仍创建任务/启动进程；先调审核再被守卫拒绝；为新工具放宽 F-7。

### F3 审核拒绝/`undefined`/抛错/超时

`ShellGate` 返回拒绝、`undefined`、非明确 `allow:true`、抛错或超时 → 工具明确报「未执行」；**零 spawn**（无 pid、无任务、无日志）；管理器 `start` 未被调用。四种分支都要有测试或等价证据，不能只测「拒绝」。

### F4 并发已满：第 9 个在 ShellGate 之前被拒

先启动 8 个运行中任务，再启动第 9 个：

1. 在 **`ShellGate` 调用之前**被拒（见 §五 CC1）；**不弹审批/不产生审核请求**（`shellGate` 零调用、无 `shell.review.start/end`）。
2. 零 spawn、无第 9 个任务、已有 8 个任务不受影响。
3. 记录诊断 `background.limit`，字段 `reasonCode`、`count`（均在白名单内）。
4. 名额检查与占用必须是原子的，并行调用不能一起突破上限。

**判失败**：第 9 个先弹审批再因并发被拒；并发检查放在 spawn 前但审核之后；无 `background.limit`；并行调用突破 8。

### F5 spawn 失败不保留半成品任务

管理器 `start` 收到 `error` 事件或 spawn 抛错 → 工具 `ok:false`，**不保留任务**、不返回任务号/pid，名额释放；后续仍可正常启动到上限。不能用「先建任务再等 error」留下假任务。

### F6 未知任务号

对不存在、已淘汰、其他会话、会话关闭后或应用重启后的任务号调用 `read`/`stop` → 明确返回「未知任务（可能来自其他会话或已过期）——不要假设它运行过」语义；**不猜测状态、不伪造日志**。

**判失败**：未知任务号返回空成功或编造状态；跨会话能读到别人的任务。

### F7 kill-timeout 的诚实文案

用忽略 SIGTERM 的子进程模拟终止预算内未收口 → 状态 `kill-timeout`；工具文案明确「可能仍在运行，请如实告知客户」，**绝不写「已停止」**；诊断 `background.stop.timeout` 记录。测试必须证明观察到了未收口，而不是预置文案。

### F8 凭据剥离与 cwd

1. 用哨兵环境变量（如测试专用凭据名）验证：后台进程的环境里**没有**该凭据；环境由同一个 `buildShellEnv(process.env, extraCredentialEnvVars)` 构造。
2. 后台进程的 cwd 等于会话 `shellCwd`（默认项目根）；`start_background_task` 不接受调用方指定 cwd（schema 无此参数）。
3. 环境/路径构造与 `run_shell` 同源，不是第二套实现。

**判失败**：凭据出现在子进程 env；cwd 可由模型指定或落在项目根之外；复制了第二份环境构造逻辑。

### F9 判断会话与无 ShellGate 会话看不到四工具

1. 判断会话（`buildShellJudgeTools` / `buildGovernanceJudgeTools`）的工具清单**不包含**四个后台工具，且不创建管理器。
2. 没有注入 `ShellGate` 的普通会话也不注册四工具。
3. 判断会话原有的工具清单与行为不变（回归通过）。

**判失败**：判断会话能启动/读取/停止后台任务；无 ShellGate 会话获得四工具；靠运行时开关而不是结构性装配隔离。

### F10 对已结束任务 stop 不谎报

对已自然退出或已被停止的任务再次调用 `stop` → 如实返回原状态与退出码（如 `exited`/`stopped` + `exitCode`），不声称「刚刚停止」。

### CC1 并发检查在 ShellGate 之前

- **要求**：第 9 个并发 `start` 在调用 `ShellGate` 之前被拒；`shellGate` 零调用、无审批卡/审核请求；零 spawn；诊断 `background.limit`。

### CC3 诊断只用白名单字段，未修改 `diagnostics.ts`，不依赖 taskId

- **要求**：
  1. `src/common/shared/diagnostics.ts` **零 diff**（项目管理属主文件，运行时核心无权修改）。
  2. `background.*` 与复用的 `shell.*` 事件字段全部落在该文件 `FIELD_NAMES` 白名单内；本设计用到的字段集合不超出 `{turnId, toolCallId, toolName, pid, state, exitCode, signal, durationMs, reasonCode, count, decision}`。
  3. **不使用 `taskId` 作为诊断字段**，也不依赖诊断里的 taskId 做任何判断；任务号只出现在工具结果与聊天行。
  4. `background.limit` 用 `reasonCode`、`count`；不能因为字段被静默丢弃而让诊断看起来「缺失」。
- **证据**：代码检查 + 测试断言（诊断 spy 记录的字段集合），以及 `git diff` 证明 `diagnostics.ts` 未改。

## 七、判定规则

### 7.1 三种结论

| 结论 | 条件 | 后续 |
| --- | --- | --- |
| **通过（pass）** | B1–B4 交付齐全；S1–S6、F1–F10、CC1–CC3 全部满足；E1–E7 证据完整且绑定当前候选；无未解决失败；O1–O5 未实施；适配器与诊断共享文件零 diff；文档如实 | 交可信启动端/统筹记录该阶段完成。通过只覆盖「Windows（或实际记录平台）上运行时核心 B1–B4」范围，不授权提交/推送/发布/部署，不替代测试角色的真实入口跨角色联调阶段 |
| **返工（needs-work）** | 已有证据表明不满足标准：例如审核拒绝仍 spawn / 并发检查在审核之后或弹审批 / 判断会话可见四工具 / 未知任务号或 kill-timeout 文案撒谎 / 凭据未剥离 / cwd 可指定 / 适配器或 `diagnostics.ts` 被改 / 诊断使用 taskId 或白名单外字段 / 上限与设计不符且无客户意见 / 功能文档缺失 / O1–O5 被实施 / 断言被放宽或测试被删 | 在验收报告中列出条目、原始证据、差异与应回到的所有者（运行时核心，越权处还需项目管理/团队组建处理）；由可信启动端安排修复与复测，保留原失败记录 |
| **证据不足（missing-evidence）** | 无法判断：测试未实际运行、只给自述/截图；缺少命令、退出码或原始输出；关键场景被 skip 或未覆盖；证据绑定的是旧候选/另一版本（HEAD 或工作树不符）；E1–E7 任一必需项缺失；环境未记录导致无法复核；候选尚未冻结或实施未完成 | 写明缺什么、由谁补、补证后重判；**不能记通过**，也不能把「没有证明失败」当成通过 |

### 7.2 必须判「证据不足」的情形（不穷举）

1. 声称测试通过但没有实际运行记录、退出码或原始输出。
2. 测试输出对应的候选与当前工作树不一致（版本不符、证据过期）。
3. 关键标准只有代码阅读/设计论证，没有动态证据（尤其是 S1 立即返回、S3 dispose、S4 轮次中止、F3 四类审核失败、F4 并发顺序、F7 kill-timeout）。
4. 测试跳过实质断言或只跑旧基线，未覆盖新增行为。
5. 既有 shell 回归未跑、失败未解决或结果不完整。
6. 必需文档缺失导致无法核对实际行为与限制（若文档存在但内容与实现不符，按 needs-work）。
7. 平台/环境未记录，或只提供其他平台证据却宣称本平台行为。

### 7.3 证据失效与不降低标准

- 产品代码、测试、断言、配置或依赖在证据生成后变化 → 受影响证据失效，需在新候选上重跑受影响门；不能拼接不同候选的输出。
- 同一候选同一范围已有有效结论可复用；设计/标准实质修订后，按原确认流程更新并重判受影响项。
- 验收不为了通过而放宽标准：不接受自述代替原始输出、代码阅读代替行为测试、单引擎代替三引擎、POSIX 结果代替 Windows 结果、探针代替正式测试。
- 验收报告至少包含：任务/阶段、设计与本标准版本（含设计 SHA-256）、候选身份、实际改动范围、逐条 S/F/CC 结论、原始证据链接、剩余问题与理由。
