# 角色能力安装（技能＋MCP）（G-4 设计提案）

一句话结论：给 su 增加**能力安装工具**——`install_skill`/`uninstall_skill`（V1，内容与运行时无关的纯文档面）与 `install_mcp`/`uninstall_mcp`（V2 占位，机制待运行时核心评估回填）。安装＝「**先落盘**（技能文档 `docs/skills/<name>/`、MCP 声明 `docs/mcp/<name>.md`，项目内可见）→ **工具校验并激活**（重建目标角色会话）→ **三态如实回执**」；**不设二次确认卡**（客户在会话中的指令即授权；su 不自主发起，卡文本与工具说明写死「仅客户明示时安装」）。技能经**会话开局注入**（系统提示新增「本角色已安装技能（先读）」指针节：路径＋运行期算的 digest＋一句话用途——内容仍在文件、读不受边界约束）落到角色的每一个新会话，覆盖派发、客户直聊、看护系统消息全部触发面；MCP 面在评估回填前**只落设计与占位、不承诺实施**。全链**可见**（工具行＋`[系统·安装]` 系统行＋项目内登记文件＋诊断）、**可撤**（卸载工具＋重建，登记改写语义、文件保留如实说明）；**零权限面放松**——技能是必读资料不是边界、安装不改变任何写权，外来 MCP 的新动作面边界由评估与裁定钉死。

本记录是**设计提案**，不是实施授权：**未实施、未测试**。本轮只读源码、证据与技能文档并形成判断；没有改任何 `app/`、`src/`、`test/`、证据目录，没有 git 提交，没有操作任何真实项目与轮次目录。涉及实施的部分须经客户确认文档后由项目管理派发属主角色；MCP 三平台机制与运行时核心的**跨平台可行性评估并行在跑**，本文相关节全部留**占位**、以彼评估为准回填。

## 来源与动机（依据）

- 客户原问（PM 评审批次登记原文）：「这个 su 应该有个工具，可以给其他的角色安装 mcp……或者安装技能」。
- **客户已定授权口径（原话）**：「这个 MCP 也不需要吧，**这两个都是我确认他让他安装他才去给其他的角色安装，这个确认也没必要啊**」＝**不设二次确认卡**——客户会话中指令 su 安装即完成授权；su 不自主发起；安装动作与产物**可见、可撤**即可（[PM 评审批次 §候选 G-4](../../../项目管理/docs/change/2026-10-15_change_kanban-fixes-pm-review.md)，2026-10-16）。
- PM 复核并登记的现状事实（登记原文直接引用）：技能——`skillRoot` 机制已有（`ANS_SKILL_ROOT`、门禁把它当独立写权根 project/skill 之一）；G-1 裁定 #5 「技能文档（仓库外）增补属另行治理」为该方向已登记事项——**本方向是它的后续**（安装落到**项目内**，仓库外技能文档增补仍按 #5 另行治理，两者不混）。MCP——ANS 自身即以 MCP 通道向 Claude/Codex 注入内置工具（管道已验证可用）；**外来** MCP 现被三重封死（Claude 路径 `strictMcpConfig`＋hook 兜底＋canUseTool deny-all；Codex 路径起线程前全量 disable＋「残留即拒绝启动」硬校验；Pi 路径无 MCP 面）。
- PM 登记的待解设计点（本文逐一对齐）：su 工具面（install/uninstall、技能与 MCP 是否统一）；技能落盘位置与角色加载路径（含 su 预授权写权是否扩列）；MCP 三平台机制（Claude 放行面／Codex 白名单化／Pi 支持性）；产物可见性、留痕与卸载；第三方 MCP 进程的环境/凭据面。
- 场景约束：客户单用户本机应用；客户讨厌多余摩擦（此前 5 min 收束即被裁到 30 s 的先例）——「不设二次确认卡」是客户对摩擦的又一次显式取舍，本设计不得以任何形式把它加回来。

> 行号说明：本提案引用的行号为 2026-10-16 写作时点的**工作树**读数；当时工作树含 G-1/G-2 实施、三平台搜索批、工具行折叠批等未提交修改，实施派发前请以当轮基线复核行号。

- 各运行时的**原生技能通道全部关闭**：Claude `settingSources: []`＋`skills: []`＋`plugins: []`（`src/provider/claude/session.ts:234-235`）；Pi `noSkills: true, noPromptTemplates: true, noThemes: true, noContextFiles: true, noExtensions: true`（`src/common/pi-adapter/real-adapter.ts:1055-1067`）；Codex 禁用 `plugins` 等原生特性（`src/common/codex-adapter/config.ts:6-15` `DISABLED_NATIVE_FEATURES`）。**结论：不存在可搭车的「原生技能自动加载」通道**——「技能」要到达角色，只能走「系统提示／派发文本／角色自读文件」三条既有通道之一（§4.2 选型）。

### 1.2 su 写权与预授权（无卡授权的唯一机制出口）

- 写入唯一路径＝`write_file`/`edit_file` 过门禁（F4 写集精确匹配、F6 接受门、F7 真实路径复核）；**工具自己不写盘**（对照：`dispatch_task` 只交载荷、`submit_report` 只交报告——`src/provider/runtime/tools.ts:56-81, 946-1073`）。
- **su 预授权写目录（客户裁定 2026-10-16）**`SU_PREAUTHORIZED_WRITE_DIRS = ["docs/su", "docs/contracts"]`（`src/pipeline/orchestration/run-role.ts:900-942`）：内置治理角色（`kind === "built-in-governance"`，`:445`）会话的**初始 writeSet 恒含**这两棵目录树，不经确认发行器、开会话/重建均生效；其余一切路径照旧「preview 逐条列路径＋`confirmed:true` 才发行」（`confirmed-writes.ts`）。这是「su 直写不弹卡」的**唯一既有机制出口**——G-4 的无卡口径若要技术上成立，落点必在此处（扩列与否＝待裁项，§4.6）。
- su 卡文本已同步写明「两棵目录写盘许可已预置，其余一切写盘仍须确认」（`src/common/门禁引擎/boundary-core.ts:89-190`，`BUILT_IN_ROLE_CARD_TEXT` 的「确认制要点」段 `:133-141`）；J-1 措辞守卫（避让未否定的「授权/获准/放行」小句）为既有测试约束，G-4 增补段须同口径避让。
- su 的 shell 是**只读档**（白名单外一律拒，不打扰客户——`run-role.ts:407-419` 注释），故安装不可借 shell 落盘。

### 1.3 角色加载路径的现状（三条既有通道）

1. **系统提示**＝角色卡文本＋边界来源（`renderSystemPrompt`：`src/common/pi-adapter/real-adapter.ts:320-322`、`src/provider/pi/session.ts:37-47`；Claude/Codex 各自内联拼装 `src/provider/claude/session.ts:66-72`、`src/provider/codex/session.ts:236-242`）——**会话开局渲染一次，在跑会话不随文件更新**（重建才刷新；重建由 O-1 陈旧检测触发，见下）。角色卡正文在会话开局由 `resolveRole` 读盘（`src/service/role/resolve-role.ts:44-64`）。
2. **派发必读块（G-1）**：派发文本引用 `docs/contracts/*.md`／`docs/workflow.md` 时，投递系统在投递当刻算 sha256 附「必读（按序）」块（提取面 `src/common/编排/handback.ts:285-299`，判据/渲染 `:312-348`；**提取面只认这两个前缀**——技能路径不在内）。
3. **角色自读文件**：`read_file` **不经过写门禁**（工具头注 `tools.ts:291`；绝对路径原样读 `:300`）——任何角色可读项目内任何文件（含已安装技能），也可读技能根的绝对路径。"读不受边界约束" 是 G-1 已复核的前置事实。
- **O-1 会话陈旧检测**：活会话定格「角色边界文件＋治理边界文件＋`.ans/project.json`」内容指纹（`app/desktop/session.ts:450-457, 803-809`），变更 ⇒ 无卡作废重建（在跑不打断，settle 后/下次发言再查 `:821-853`）。**角色卡文件与任何技能文件均不在指纹集内**——改它们不会触发重建（G-1 §七.3/A6 曾登记「指纹集扩展」为待评估候选，G-4 使该需求更具体）。

## 二、设计总览

```
   客户（su 会话）：「给<角色>装技能<name>」 /「给<角色>装 MCP <name>」   ← 指令即授权（无二次卡）
        │
        ▼
   su：① 落盘（write_file，预授权直写；可见、进项目文件）
         docs/skills/<name>/SKILL.md + install.md      （技能）
         docs/mcp/<name>.md                            （MCP，声明文件）
        │
        ▼
   su：② 调工具 install_skill / (V2) install_mcp ———— 只给 su 注入（「注入才注册」先例）
        │
        ▼  桌面主进程（新能力 handler，同 dispatch_task/角色 status 先例）：
        校验（角色存在且非 su；登记文件存在且格式合法、含该角色）
        → 激活（重建目标角色会话；在跑不打断 ⇒ 如实「下一会话生效」）
        → 三态回执（applied / rejected(如实原因) / deferred-busy）＋UI 系统行＋诊断
        │
        ▼
   目标角色：新会话系统提示含「已安装技能（先读）」指针节（路径+digest+用途）
             → 模型按既有「必读」纪律 read_file 全文（读不受边界约束）
        │
        ▼
   卸载：su 改登记（移除角色条目）→ uninstall_skill 校验登记确已撤销 → 重建 → 如实回执
        （文件保留；「效果已撤」与「文件仍在」如实区分）
```

**一条原则**：安装**不改判定链**——写入照走 `write_file`＋门禁（预授权与否只影响「要不要确认卡」，不影响任何放行语义）；工具不写盘（只校验+激活+回执）；激活只复用既有重建；**安装不改变任何角色任何写权**（技能是必读资料，不是边界；su 卡文本写明）。一切失败路径 fail-closed（最坏情形＝这次安装没发生，现状语义不变）。

**非目标（V1 不做）**：自动/自主安装（永远需客户明示）；远端技能市场/网络获取（技能内容由客户在对话给出或 su 整理）；对仓库外技能根的任何写（G-1 #5 另行治理）；MCP 的任何实施（评估回填后另批）；删除工具/文件级删除原语（§4.4 登记）；技能与 MCP 对**已开跑**会话的即时热生效（不打断在跑轮次，沿 G-2 语义）。

## 三、su 工具面（形态建议）

### 3.1 技能与 MCP：**分开**（两对工具），不统一为单工具

| 理由 | 说明 |
| --- | --- |
| 生命周期不同 | 技能＝纯文档、项目内、各运行时一致；MCP＝声明＋进程＋凭据＋平台各异，且目前**评估未回填**——分期天然是工具级的（技能 V1 落地、MCP V2） |
| 参数面不同 | 技能＝`{roleId, name}`；MCP 若统一需并出 command/args/env 等一整套只在 MCP 时有意义的字段——模型填错面变大、校验分支变多 |
| 失败面不同 | 技能失败＝登记缺/角色不存在/在跑延迟；MCP 失败＝还有「运行时无 MCP 面（Pi）」「进程启动失败」「凭据缺失」等——统一工具的错误枚举会互相污染 |
| 先例一致性 | 本仓工具均单职（dispatch_task / role_status / propose_recovery…）；G-2 当时也刻意三工具分列而非合一 |

### 3.2 工具清单与签名草案（V1 面板＝技能一对；MCP 二对为占位）

```text
install_skill(roleId: string, name: string)          // V1
uninstall_skill(roleId: string, name: string)        // V1
install_mcp(roleId: string, name: string)            // V2 占位——运行时核心评估回填后定形
uninstall_mcp(roleId: string, name: string)          // V2 占位
```

- **只给 su 注入**（「注入才注册」——`AdapterCapabilities` 增 `installSkill` 等能力位；判据复用既有先例：桌面 `role.builtIn === true`／编排 `kind === "built-in-governance"`；项目角色不给）。
- **工具＝校验＋激活＋回执，不写盘**：落盘永远由 su 的 `write_file` 完成（同 `dispatch_task`「只交载荷」纪律的反向对称——「先落盘再激活」＝G-1「先落盘再派发」的镜像）。参数因此极小，内容不进工具调用（也避免大内容挤进工具行显示）。
- **回执三态**（形状单一来源＝契约家 `src/model/runtime.ts`，同 `DispatchTaskFn`/`RecoveryReceipt` 先例）：三态＝applied（`effective:"rebuilt"`，当场生效）／deferred（`effective:"next-session"`，在跑不打断）／rejected（`ok:false`＋如实原因，零副作用）：

```text
{ ok: true,  action: "installed" | "uninstalled", roleId, name,
  path, digest,                     // SKILL.md 路径 + 运行期算的 sha256（前 12 位展示可）
  effective: "rebuilt" | "next-session",   // 已重建生效 / 在跑不打断、下一会话生效
  note?: string }
{ ok: false, reason: "<如实原因枚举见下>", message: "<一句人话>" }   // rejected；零副作用
```

### 3.3 失败如实文案（枚举草案；全部 fail-closed＝未执行、零副作用）

| 情形 | 回执文案（草案） |
| --- | --- |
| 落盘不存在 | `技能未登记：docs/skills/<name>/install.md 不存在——先落盘再安装；未执行。` |
| 登记未含目标角色 | `登记中未包含角色「<roleId>」——未执行；如确要安装请先更新登记。` |
| 角色不存在 / 是 su 自己 | `角色「<roleId>」不是本项目项目角色（或为治理角色 su）——未执行。` |
| 目标在跑轮次 | `已登记；该角色正在运行轮次，不打断——新会话起生效（effective: "next-session"）。`（ok:true 的延迟态，不是错误） |
| 工具未接线（桌面未注入） | 工具**不注册**（结构保证，无文案面）。 |
| 运行时无 MCP 面（Pi，V2） | `运行时「Pi」暂无外来 MCP 支持——未安装（如实：该面不存在）。` |
| 卸载时登记未变 | `登记仍含角色「<roleId>」——先改登记再卸载；未执行。`（防「工具说撤了、登记没变」） |

- 纪律：回执**不夹带授权语义**（沿 F-5-opt1 `REBUILT_SESSION_WRITE_PERMITS_NOTICE` 先例）；失败绝不假装成功、绝不静默。

## 四、技能安装设计（V1 主体）

### 4.1 技能文档形态与落盘位置

- 位置：**目标项目内** `docs/skills/<name>/`（项目根相对；`<name>` 稳定短 slug，与目录名一致）。选 `docs/` 树与 G-1 的 `docs/contracts/`、`docs/workflow.md` 同属「项目级文档面」，语义并列不混淆（契约＝跨角色冻结接口；技能＝角色能力资料）。
- 两文件形态（内容与登记分离——卸载只动登记、不触内容）：

```markdown
docs/skills/<name>/SKILL.md        ← 技能内容（角色读这个）
---
skill: <name>
purpose: <一句话用途>
---
# 技能：<name>
<正文：工作方法／领域知识／检查清单……；宜短小，角色自读全文>

docs/skills/<name>/install.md      ← 安装登记（su 写；系统读）
# 安装登记：<name>
- 用途：<一句话>
- 适用角色：<roleId>、<roleId>          ← 卸载＝从此列表移除（或整份置 status: uninstalled）
- 状态：installed
- 安装日期：2026-10-16（按客户指令）
```

- 内容来源（V1，无网络面）：客户在对话中给出内容；或 su 整理/撰写；或 su 从**可读**的既有文档（含仓库外技能根绝对路径——读不受边界约束，`tools.ts` 读工具 `:300`）摘编**到项目内**（摘编动作本身是普通 `write_file`，可见可审）。技能根文档的**修改**不在此列（G-1 #5 另行治理）。
- 建议在 su 卡文本/工具说明给一个「最小可抄」技能模板（同 `BUILT_IN_ROLE_CARD_TEXT` 给 boundary.yaml 最小示例的先例，防格式漂移）。

### 4.2 角色加载路径（三方案对比；推荐＝**会话开局注入**）

| 方案 | 机制 | 生效面 | 成本 | 缺点 |
| --- | --- | --- | --- | --- |
| A 角色卡必读 | su 编辑目标角色 `role-card.md` 的必读资料段，指向技能路径 | 新会话（角色卡在系统提示内） | 零注入代码 | ①`角色卡/**` 未预授权——每次安装要确认卡（**与客户裁定冲突**）或再扩预授权（面更大）；②改角色身份文档，语义混；③在跑会话不更新且**无任何指纹触发重建**；④卸载＝再编辑，链长 |
| B 派发引用 | 技能路径进派发文本；G-1 必读块提取面扩到 `docs/skills/**`（`extractDispatchReadPaths` 小改） | 每次**派发**触发的轮次，哈希绑定 | 中（编排小改） | 只覆盖派发轮次——客户与角色的**直接聊天**、看护系统消息、su 自身轮次不带；「已安装能力」语义弱化为「任务附件」 |
| C **会话开局注入**（推荐） | 系统提示新增「本角色已安装技能（先读）」**指针节**：路径＋digest＋一句话用途；渲染单一来源在编排，各适配器拼接一行 | **每个新会话**（三运行时/全触发面覆盖） | 中（编排渲染＋三适配器各一行＋登记读取；digest 由代码算——「哈希只能由代码算」沿 `finalize.ts:2-3` 先例） | 在跑会话不自动更新（需重建或指纹扩展——§4.3）；提示体积（**指针化**可控：注入只含路径/用途/哈希，不含正文） |

**推荐 C，理由**：①语义正确——「安装到角色」＝角色的**能力面**，天然应在每个会话开局可见（派发、直聊、看护触发一律覆盖），而不是搭任务的便车；②不碰 `角色卡/`（避开方案 A 的写面与身份文档混杂）；③三运行时一致（系统提示拼装是各适配器共同的入口层）；④与「读不受边界约束」配合——注入的指针就是既有「必读资料」纪律的机械化：模型收到指针→按纪律 `read_file` 全文→校验 digest。**B 作为增强候选**（对跨角色协作轮次给出投递当刻哈希绑定；提取面扩列＝编排小改，列待裁）；**A 不做**（除写面问题外，角色卡是 su 规划角色时写给角色看的身份文档，塞入易变的技能清单会让它随安装/卸载高频漂移）。

注入节草案（系统提示内，数量为零时不渲染）：

```markdown
## 本角色已安装技能（动手前先读，按序）
1. docs/skills/<name>/SKILL.md（用途：…；sha256:<hex>；安装于 2026-10-16）
内容以文件当刻字节为准；读到与派发描述/版本不符 ⇒ 停止并交 blocked 报告（不得猜）。
```

- 登记解析纪律（沿角色枚举的防御先例 `resolve-role.ts:222-248`：坏件跳过不崩）：`install.md` 缺失/解析失败 ⇒ 该条不注入＋写诊断；**绝不**因技能登记坏件拒开会话。

### 4.3 生效、变更与重建语义

- **激活＝重建目标角色会话**（复用 G-2/W4 `rebuildSession`，`session.ts:1980-1997`）：idle ⇒ 当场重建（`effective: "rebuilt"`，新会话即刻含注入节）；busy ⇒ **不打断**（沿 G-2 语义）——如实回执 `"next-session"`，轮次结束后的既有陈旧检查/下次开启自然带上新内容。
- 候选增强（待裁，沿 G-1 A6 同款待评估项）：把**已安装技能的登记文件**纳入 O-1 会话指纹集（`boundaryPaths/Prints`，`session.ts:450-457`）——安装/卸载后于 settle 自动重建，`"next-session"` 收敛为「settle 即生效」。V1 不做则如实登记延迟窗。
- **技能可迭代**（与契约的冻结版本化**刻意不同**）：技能是能力资料，迭代是常态；引用语义是「以文件当刻字节为准」而非 G-1 式冻结哈希——变更＝su 编辑 SKILL.md（预授权树内）＋重装（再调一次 `install_skill` 触发重建、回执记新 digest）。变更与安装同链、同回执、同可见性。若产业上出现「必须按版本冻结」的技能诉求，走 G-1 式另立版本文件（后备，不预设）。

### 4.4 卸载与可撤（「可撤」的钉死语义）

- **V1 卸载＝停用（登记语义）**：su 先把 `install.md` 中该角色条目移除（或置 `status: uninstalled`）——普通 `edit_file`；再调 `uninstall_skill` 校验「登记确已撤销」→ 重建目标会话（新会话不再注入）→ 三态回执。
- **文件保留、如实说明**：本仓**没有删除原语**（工具面只有 read/write/edit——`tools.ts:207-309`；su shell 只读）——V1 不动 SKILL.md 文件本体，卸载回执写明「效果已撤；文件保留于 `docs/skills/<name>/`（如需连文件一起清掉，目前需客户手动删除，或等后续版本给删除动作）」。**「效果已撤」与「字节已清」是两个事实**，不合并陈述。
- 候选（登记，不承诺）：后续版本给「删除」能力（门禁复核的 unlink；需要新原语与测试面，不在 V1）。
- 回撤的可见性：卸载与安装同链——工具行、系统行、登记文件、诊断四层全同（§6.4）。

### 4.5 与 G-1 契约模式的关系

| 维度 | G-1 契约 | G-4 技能 | 关系 |
| --- | --- | --- | --- |
| 落点 | `docs/contracts/<name>-v<N>.md` | `docs/skills/<name>/` | 同级项目文档面；若裁定扩预授权，两树并列（§4.6） |
| 可变性 | **冻结不可变**（变化出新版本文件） | **可迭代**（文件当刻字节为准；变更走重装回执） | 刻意不同（§4.3 理由）；互不要求对方遵守自己的可变性 |
| 到达角色的方式 | 派发必读块（路径＋投递时哈希） | 会话开局注入（路径＋开局哈希） | 同一「指针+运行期哈希」家族；G-4 索引面覆盖全触发面 |
| 「先落盘再 X」 | 先落盘再**派发**（J-1） | 先落盘再**激活** | 镜像纪律，同一句式进 su 卡文本 |
| 预授权 | `docs/contracts` 已预授权（G-1 同批客户裁定） | `docs/skills` 是否扩列＝**待裁**（§4.6） | 若扩列＝同族机制复用；不扩＝无卡口径无法成立（如实汇报） |
| 仓库外技能根 | #5「技能文档（仓库外）增补属另行治理」 | 同——G-4 **不碰**技能根写面 | 两条线并行不混；G-4＝#5 的「项目内」后续 |

### 4.6 su 预授权写权是否扩列（**列待裁项，不预设**）

- 事实链：无卡口径（客户原话）⇒ 安装落盘不能走「preview＋confirmed:true」（那正是被裁掉的卡）；⇒ 落盘路径必须在 **su 初始 writeSet** 内 ⇒ 唯一既有出口＝扩 `SU_PREAUTHORIZED_WRITE_DIRS`（`run-role.ts:912`）。
- 候选（**待裁，不在本文预设**）：
  - **候选 1（本提案推荐倾向，仅供裁定参考）**：扩 `docs/skills`（MCP V2 时再议 `docs/mcp`）。范围与 `docs/contracts` 同构（项目级文档树、纯文本、无执行面）；扩列实现＝`run-role.ts` 常量加一项＋su 卡文本同批修订＋测试面更新。
  - **候选 2**：不扩预授权，安装落盘复用 `docs/contracts/` 已预授权树的从属目录（如 `docs/contracts/skills/`）——零机制改动但**语义污染**（契约目录被塞入非契约物），不推荐但列全。
  - **候选 3**：不扩，接受「安装时弹一次确认卡」——与客户裁定原话**直接冲突**，仅作对照列出（若客户改口再启用）。
- 边界钉子（无论哪案）：扩列**只扩写权不做任何其它语义**——F4/F6/F7/边界条目/条件激活逐字不变；扩列不改变任何其它角色；安装动作与写权授予是两回事（安装不改变任何角色的边界与写权——卡文本写明）。

## 五、MCP 安装设计（**三平台机制全留占位：待运行时核心评估回填**）

> 本节只钉**产品面契约**：落点、按角色生效、呈现、卸载。所有平台机制细节（Claude 放行面、Codex 白名单化、Pi 支持性、进程/凭据/失败面）**一律以运行时核心并行评估的行级实证为准**，评估回填前本节不下实施承诺。MCP 工具（`install_mcp`/`uninstall_mcp`）随评估结论并入 V2 批次。

### 5.1 安装产物与配置落点

- **声明文件（唯一持久产物）**：`docs/mcp/<name>.md`（项目内、可见、可审、进 git）：

```markdown
# MCP 声明：<name>
- 用途：<一句话>
- 启动：command / args（stdio 形态；传输形态与字段以评估回填为准）
- 环境：只记**环境变量名**引用；凭据值不进本文件（值由客户在本机环境提供；「对话直接给值」的落位与形态＝待裁项）
- 适用角色：<roleId>、…
- 状态：installed ｜ 安装日期：2026-10-16
```

- **不写平台原生配置**（不动 `~/.claude`、不动 Codex 原生 home、不动 `.ans/`）：外来 MCP 一律由 ANS 在**会话构造时程序化注入**（与 `ans`/`ans_codex` 服务器同构——§1.5 已验证管道）。收益：卸载＝改声明＋重建，**零平台残留**；且注入点在代码可见可审，不给「文件一写、行为静默变」留口子。
- 声明文件解析与注入的严格面（目录穿越、字段白名单、失败 fail-closed 拒绝注入并如实回执）＝运行时核心评估一并钉。

### 5.2 按角色生效（契约层）

- 生效粒度＝**角色×声明**：声明文件列 `适用角色`；角色会话构造时按列表装配（未列角色的会话对该声明完全不可见）。
- 生效时机与技能同口径（§4.3）：安装/卸载经重建；在跑不打断。

### 5.3 三平台机制（占位，逐平台登记现状锚点）

| 平台 | 现状锚点（§1.5） | 目标形态（**待运行时核心评估回填**） |
| --- | --- | --- |
| Claude | `strictMcpConfig:true`＋`canUseTool` deny-all＋PreToolUse deny 兜底 | 放行面扩展：受声明白名单的外来 server 如何进 `mcpServers`；放行粒度（全工具/清单/逐次询问）；外来工具调用的显示与脱敏 |
| Codex | 起线程前全量 disable＋残留拒启＋空目录硬校验 | 白名单化：仅声明 server `enabled=true`＋「目录＝声明集」等价校验替换空校验；失败与凭据面 |
| Pi | 无 MCP 面 | 支持性评估（V1 口径：如实「暂不支持」，不假装） |

- **诚实面（产品视角必须写明）**：外来 MCP 工具的执行**不经过 ANS 写门禁**（它们在 server 进程内运行，不属于 `write_file`/`run_shell` 任一受治理面）——安装一个 MCP＝给该角色开了一片**门禁之外的新动作面**，动作面边界＝server 自身提供什么。因此：①「客户指令即授权」在这里承载的实际分量比技能大（技能只是资料，MCP 是真能力）；②放行粒度、进程环境、凭据处理的最终边界必须由评估给出事实后再呈客户；③评估前**不得**在任何面向客户的文案里承诺 MCP 已支持。

### 5.4 聊天中的呈现（安装行／使用行）与卸载

- **安装行**（su 会话）：`install_mcp` 调用按既有工具行渲染＋激活后一条定格系统行（沿 `[系统·<子类>]` 形态，如 `[系统·安装]`；不可撤回面同 `system` kind）＋su 的如实话术（§6.2）。**使用行**（目标角色会话）：该角色会话内外来 MCP 工具被调用时，按既有工具行口径渲染一条（工具名/参数摘要/结果）——**具体呈现形态（外来工具名映射、行样式、折叠语义）待运行时核心评估＋桌面UI 回填**；原则＝「用了什么就让客户看得见」，不新造一套行体系。
- V2 候选（登记不承诺）：角色会话开局系统行「本会话已加载外来 MCP：<清单>」（技能已由注入节覆盖，不必重复）。
- **卸载**：改声明（移除角色/置 uninstalled）→ `uninstall_mcp` 校验 → 重建（进程随会话消亡）→ 回执如实；零平台残留（§5.1 的直接推论）。

## 六、「客户指令即授权、不设二次确认卡」的落点

### 6.1 语义与机制落点

- **语义**（客户原话，入 PM 记录）：客户在会话中指令 su 安装＝完成授权；不设二次确认卡；su 不自主发起（「仅客户明示时安装」写进**工具说明＋promptGuidelines＋su 卡文本**三处）。
- **机制落点**（与语义对齐的三个事实）：
  1. 落盘走**预授权直写**（§4.6 扩列裁定后）——不经 `request_confirmation`，故**不产生任何卡**；
  2. 安装工具**没有确认通道**（handler 只校验/激活/回执——结构上没有可弹的卡）；
  3. `request_confirmation` 的既有语义**不变**：它服务的是「preview 列路径＋confirmed:true 发行治理写权」，与安装动作无交集——本设计不新增任何确认面，也不复用确认卡做二次授权。
- 对照：G-2 恢复动作要卡（执行有破坏性、单点重）；G-4 安装不要卡（客户已裁定、动作可撤、产物可见）——两处口径不同是刻意的，按动作破坏性与客户裁定分别钉。

### 6.2 安装完成后的如实话术（su 报告模板，草案）

```text
已安装：技能 <name> → 角色「<roleId>」
- 内容：docs/skills/<name>/SKILL.md（sha256 <前 12 位>）
- 生效：<已重建该角色会话，即刻生效 ｜ 该角色正在跑轮次（不打断），新会话起生效>
- 撤销：对我说「卸载 <name>（从 <roleId>）」即可；登记随时可查：docs/skills/<name>/install.md
- 说明：本次安装未改变任何角色的写边界——技能是必读资料，不是权限。
```

- 卸载同构：`已卸载：…（效果已撤；文件保留于 …）`。MCP 版增加一行诚实告知：「外来 MCP 工具在 ANS 门禁之外执行（本次安装未改变任何角色的写边界）」——终稿措辞随评估回填后定。
- 纪律：话术由 su 生成，但**内容面**（路径/digest/生效态/撤销路径/边界不变声明）以工具回执为单一事实来源，su 不得自行扩写授权语义。

### 6.3 可撤性（「可撤」的三个钉死点）

1. 撤销路径存在且低摩擦：一句「卸载 X（从 Y）」→ su 改登记＋调 `uninstall_skill`（§4.4）；
2. 撤销**如实**：回执三态＋「效果已撤/文件保留」二分陈述；撤销失败（如登记未改、在跑延迟）逐字报因；
3. 撤销**可见**：与安装同层（工具行/系统行/登记/诊断）——撤销动作本身也是可被客户看到的。

### 6.4 偏离可见性（su 若非客户明示发起安装，客户如何看到）与可选机械护栏

- **四层可见**（机制内建，不依赖 su 诚实）：
  1. su 会话聊天流：工具行（`install_skill` 调用本身成行）＋`[系统·安装]` 系统行；
  2. 项目内：`docs/skills/**`、`docs/mcp/**` 的新文件/改动（文件系统与 git 双重留痕——单用户本机、进 git 即不可悄悄抹去）；
  3. 诊断：安装/卸载事件入 `ans-diagnostics.jsonl`（元数据白名单）；
  4. su 的安装报告话术（§6.2）——四层互相印证。
- **可选机械护栏（候选，待裁；本提案推荐「可加」）**：`install_*`/`uninstall_*` 仅在**客户消息（kind:"message"）发起的轮次**中执行——桌面 handler 读该角色当前 `activeDeliveries` 的 kind 即可判定（状态已在手，`session.ts:460-485`）；非客户触发轮次（派发回执/看护系统消息/回交等打开的轮次）调用 ⇒ 如实拒绝「本动作仅可在客户消息发起的轮次执行」。分析：它**机械兑现**「我确认他让他安装」的语义（且不引入任何卡）；假阴性面（客户指令被排在别的轮次后）由「客户消息始终自带一个轮次、su 在该轮次内执行」化解；是否加、加的精确判据（如客户消息排队紧邻性）留 PM/客户裁定。**V1 若不加**：如实登记残余（模型纪律靠卡文本＋工具说明，机制无强制——沿 G-1「su 内嵌全文无机械拦截」同类残余先例），偏离仍可经四层可见性发现并撤销。

## 七、与既有机制的衔接

1. **G-1（契约/工作流/必读块）**：见 §4.5 对照表。「先落盘再激活」与「先落盘再派发」同为纪律句入 su 卡文本；`docs/skills/**` 若进必读块提取面（候选 B）＝`extractDispatchReadPaths`（`handback.ts:285-299`）一处扩展。
2. **G-2（看护/收束/重建）**：激活复用 `rebuildSession`（W4）；`system` kind 与 `[系统·<子类>]` 形态直接复用；在跑不打断语义逐字沿用。
3. **O-1（陈旧重建）**：技能登记纳入指纹集＝候选（G-1 A6 同款待评估项，§4.3）；不做则如实登记延迟窗。
4. **pin（`.ans/project.json`）**：**不并入**——技能/声明不是边界面；G-1 已裁「契约不并入 pin」（并入会让正常变更触发全体边界未接受），技能同理由拒绝并入。留痕走项目内文件＋诊断。
5. **投递机**：安装不造第二套投递；系统行与（若做）目标角色开局行走既有通道。
6. **「注入才注册」**：四个新工具全部结构性地「能力未注入⇒不注册」（desktop 未接线时项目角色与 CLI 会话零感知）。
7. **客户口味五条**：安装行/系统行只进聊天流（不弹窗不出 OS 通知）；「没用就删」——不为安装再造只读查询工具（su 直接读登记文件即可）；「诚实呈现」——回拒/延迟/不支持逐字报因（§3.3/§5.3）。
8. **三平台搜索批（G-3，在飞）**：其「默认关＋开关开启」先例对 MCP V2 可参考（外来 MCP 放行是否也要开关＝评估后由 PM 定）；本提案不触碰其在飞文件。

## 八、失败模式与 fail-closed 边界

| 失败 | 检出点 | 行为（口径） |
| --- | --- | --- |
| 登记文件缺失/格式坏 | `install_skill` 校验（桌面 handler） | 拒绝＝未执行＋如实回执；登记坏件在**注入侧**同样跳过＋诊断（不崩会话） |
| 预授权未扩列却要无卡安装 | 设计前置（§4.6 裁定） | 若裁定不扩：安装落盘会经确认卡——**如实向客户说明与裁定的冲突**，不硬造旁路 |
| 目标在跑轮次 | 重建入口（在跑拒绝） | `effective:"next-session"` 如实（不是错误）；有指纹扩展则 settle 后自动生效 |
| 重建失败 | `rebuildSession` 三态 | 回执如实（不假装已生效）；安装登记仍在——可在下一会话生效，su 按回执如实报客户 |
| 卸载时登记未撤销 | `uninstall_skill` 校验 | 拒绝＋「先改登记再卸载」；**绝不**出现「说撤了、实际没撤」 |
| 注入节解析/渲染异常 | 会话构造 composeContext | 该条跳过＋诊断；会话照常开启（技能是资料不是判定链，永不因它拒开会话） |
| 工具未接线 | 能力未注入 | 工具不注册（结构性，不产生半可用面） |
| MCP 运行时无面（Pi）/评估未回填 | 工具校验（V2） | 如实「暂不支持/未支持」；**评估回填前不实施、不承诺** |
| MCP 进程/凭据失败（V2） | 评估回填后钉 | 占位——由评估给失败面清单后补齐本表 |

补充纪律：安装链**永不**放行任何写入（写权仍由门禁裁决）、**永不**改变任何边界/pin、**永不**打断在跑轮次；性能上注入＝会话开局一次目录扫描＋小文件哈希，量级与既有角色枚举同级。

## 十、测试/验收思路（含真机断点观测项）与风险

**单测（离线；供实施轮与独立验证轮参考，本轮未做）**

- 工具：校验全分支（登记缺失/不含角色/角色不存在/su 自身/卸载未改登记）；三态回执形状；「能力未注入⇒不注册」；文案不含授权语义（J-1 守卫词表扫描）。
- 注入：登记解析（好件注入/坏件跳过＋诊断）；digest 计算与展示；零技能时零渲染；在跑延迟态。
- 重建：安装→idle 角色即刻重建；busy 角色 `next-session` 如实；重建失败三态。
- 卸载：登记改写→校验→重建链；「效果已撤/文件保留」二分陈述。
- 回归：既有 `dispatch_task`/G-2 工具语义逐字不变；系统提示既有部分（角色卡/边界来源）逐字不变；跨运行时一致（Claude/Codex/Pi 注入节同源渲染）。

**真机 E2E 断点观测项（绝对路径 OUTDIR）**

1. **装-看-用-撤全链**：客户对 su 说「给测试角色装技能 X」（内容当场给出）→ 观测：无任何确认卡；su 落盘文件（可见）；`install_skill` 工具行；`[系统·安装]` 系统行；su 报告话术含 path/digest/生效/撤销。
2. **注入生效**：开启目标角色新会话 → 系统提示含「已安装技能」节（断点：会话轨迹或模型首轮引用技能内容）；模型按纪律读 SKILL.md（工具轨迹）。
3. **在跑不打断**：目标角色 busy 时安装 → 回执 `next-session` 如实；轮次结束/下次开启后生效；无轮次被打断。
4. **卸载**：说「卸载」→ 登记先改、工具后撤、重建；新会话无注入节；文件仍在且回执如实说明。
5. **偏离可见**（护栏若未加时的残余观测）：安装行为在四层可见（工具行/系统行/文件/diagnostics 抽查）可被发现与复原。
6. **零泄漏/零误伤**：注入节与回执抽查明文不含凭据；未安装技能的角色会话逐字无变化（对照组）；MCP 面在 V2 前全链不出现（工具不注册）。

**风险**

- **模型不照做（su 自发起安装）**：V1 无机械拦截（护栏为候选）；缓解＝卡文本＋工具说明纪律＋四层可见性＋低摩擦撤销；残余如实登记（G-1 同类先例）。
- **注入节膨胀**：多条技能＝多行指针——指针化（不含正文）＋真实使用中技能数极少；以观测项 2/6 验证。
- **预授权扩列的面**：`docs/skills` 与 `docs/contracts` 同为纯文本项目文档树；扩列是本次唯一的写权面变化——待裁项明示、范围最小化（单树）。
- **MCP 面过度承诺**：评估未回填前一切 MCP 细节只在本文占位；面向客户的排序＝技能先落地先用，MCP 待事实齐再裁。
- **实现复杂度**：I4 触及三处系统提示拼装（既有三份副本的现实）——以「渲染单一来源＋各端拼接一行」控制漂移，测试面钉跨运行时一致性。
