# 基础动作已顺了，下一步让人更快读懂结果和待处理工作

**整体判断：基础动作已顺了，界面也明显干净；下一步应把常规运行记录退到按需查看，让用户更快知道现在答什么、工作做到了哪一步，同时消除全窗横向溢出。**

本次是客户要求的产品重新评审，只交指导意见。没有改应用、测试、边界或配置，也没有发用户聊天或真实模型任务。本文尚未经过项目管理实施评审，**不是实施授权**。旧提案保留历史，当前状态以本评审核实的版本与各属主交付为准。

## 下一轮最值得做的三个改进

这里的优先级是产品建议的排期先后，三项均待客户选择及项目管理评审。没有本轮证据支持新增 P0。

### UI-1（P1，先处理）：收好窗口与抽屉边界，基本操作始终清楚

**观察。** S1 在窗口底部出现跨全窗的水平滚动条；S2–S4 打开抽屉后该条消失。这与代码块或宽表格在自身容器里横向滚动不同。S4 内层「Pi 配置」被长文件路径挤成「Pi/配/置」纵排，外层和内层各有一个标题、一个收起入口。S2–S4 覆盖了输入区右侧发送按钮，顶部写入说明也被遮挡：这是覆盖层的既定结果，应明确临时退出和聊天操作的关系，不能混为窗口溢出的同一现象。

**代码事实与待定位原因。** `styles.css:123` 的 `.app` 是两列 grid；`:135` 的关闭抽屉仍 `transform:translateX(102%)` 并 `visibility:hidden`，抽屉内部 `overflow:hidden` 只管自身内容；html/body/.app 没有外层溢出隔离。`:438` 的 `.runtime-note` 还是不可收缩的 flex 项。这些是候选成因；本轮未测 DOM scrollWidth，**不宣称已经定因**。Pi 内层头在 `index.html:176` 和 `styles.css:926` 把标题、路径、收起放同一 flex 行，外层头由 `renderer.js:2352` 已经提供。

**用户影响（推断）。** 页面可被整体横移，形成「还有一块没看到」的错觉；窄窗还可能使说明或按钮落到可见范围外。用户本应只沿聊天上下滚动，查看辅助资料后回到对话。

**拟采用交互。** 保持现有两栏和覆盖抽屉：关闭抽屉不能扩大页面可滚动范围，打开后仅抽屉内部垂直滚动；标题和输入区始终位于窗口内。普通长路径可换行或按需显示完整路径，代码块/宽表格保留其内部横向滚动。实现角色先用关闭/打开抽屉时的实际 DOM 尺寸定位，再选择外层裁剪、脱挂关闭面板或必要收缩规则；不能用隐藏全局滚动条掩盖仍然被裁掉的操作。

Pi 只保留外层一个标题与一个关闭入口，保存位置放单独的次级行/详情，不挤标题；保存按钮仍在设置自己的上下文。覆盖输入区时，将抽屉底边止于 composer 上方，使发送/停止仍可操作，不挤压聊天列宽、不改常驻侧栏；关闭仍可通过图标、×、Esc。设置面板正常关闭不生成聊天消息。若后续交互评估选择抽屉打开时先关闭再发，也必须保持草稿并在真实入口明确验证，而不是留一个看不见的发送按钮。

**验收标准（待实现后验证）。** 后续真实 Electron 在 1360×860、960px 逻辑宽度（该档本轮未测，需同时符合现有最小窗口约束）下，抽屉关闭/资料打开/Pi 打开/关闭后都没有 body/.app 水平溢出；发送、停止（工作态）、抽屉关闭、窗口控制按钮均可见可点。Pi 标题不会逐字竖排，只有一个标题与关闭入口，保存位置可按需读完整。长路径、代码块和 Markdown 宽表格不把整页撑宽，内嵌滚动仍可读全文；抽屉开关不改变聊天列宽与当前阅读位置，输入草稿保留。

**建议属主/成本。** 桌面应用，预计小至中：布局容器、关闭面板行为、去重 Pi 内层头及抽屉底边，具体原因定位后定范围；验收覆盖真实窗口与内嵌滚动。此前「Pi 输入字段堆叠不溢出」已完成，S4 可见，本条不把它写成未修；这里是全窗滚动范围、标题行和基本控制的后续收尾。

### UI-2（P1）：把常规执行记录收起来，让结果和需要回答的内容成为对话主体

**观察。** S1 顶部相邻显示两句几乎相同的治理/边界说明；聊天里有「调用工具 run_shell」「run_shell 已执行…」「调用工具 read_file」「read_file: 长路径」等多行。AX 记录这次探查有 18 条工具调用/结果行，随后才是最终答复。当前模型答复已经把待补问题写清楚，无须重写或代答。

**代码事实。** `renderer.js:146` 的角色副句和 `:1431` 的 WRITE_NOTE 重复说明边界约束；`:1382` 起实时 tool_call/accepted 各落一行，`:1940` 起回放工具行同样独立呈现；`tool-rows.js:27` 只瘦身单行文字，不聚合活动。`session-history.ts:134` 提供调用行，回放不应仅从「有文件路径」推断成功。正文/工具输出已经按旧要求隐藏，本条只处理逐事件行仍过多的问题。

**用户影响（推断）。** 用户需要辨认「这次要我答什么」，却先读了许多开发者运行细节；大量正常活动还会把失败与确认埋在同样的灰色文字里。两句常驻安全说明占了本可用于当前对话的注意力。

**拟采用交互。**

1. 同轮、同角色、相邻的常规工具活动归入一条可展开「查看执行记录」，展开保持原始时序、状态和目标，继续不展示文件正文或工具大输出。失败、拒绝和交互卡仍在原位置直接可见，不能被常规记录的折叠隐藏。
2. 工作中保留当前真实动作，例如「正在读取 src/App.jsx」；没有可靠动作字段就显示「正在工作」，不制造阶段名称、百分比或预计时间。每个成功调用结束后不额外留一条同义「调用」行；缺少配对标识时只做相邻分组，不假装识别同一个调用。
3. 轮末默认折叠常规活动，但用户主动展开的记录保持展开，新增消息不强迫用户收起或跳底。聊天、回放使用相同展示口径。组边界不能跨客户消息、助手答复、拒绝/确认卡或角色。
4. 去掉聊天头重复的角色副句，保留一份简短写入事实即可；进一步移入角色资料是否合适由客户确认。异常/需行动提示仍就地出现，不加另一块状态面板，不恢复已经删除的聊天状态 pill。

**验收标准（待实现后验证）。** 对相同 18 条活动记录，普通阅读视图不再逐条铺开成功调用与结果，最终答复可直接阅读；展开后原顺序和目标不丢。插入 read_file 失败、shell 非零退出、拒绝、未决卡时，原因和答题按钮无需展开成功活动即可看到。来源/结果不明的旧回放保持「状态未记录」，不制造成功数。超过 150 行的虚拟聊天中展开/收起、实时增量、settled 都保持真实可见行与用户滚动位置；未决卡定位、报告单一展示和回放去重不回归。顶部边界说明只出现一次。

**建议属主/成本。** 桌面应用，预计中：触及实时/回放行模型、聚合视图高度及虚拟渲染。先评估现有事件字段能否区分成功/失败；如需公共事件或 ReplayRow 结构扩展，再由项目管理协调相应属主。不能为了本条把状态判断复制进前端，也不要把模型答复自动转成前端假结论。

### UI-3（P1）：角色抽屉先回答「这个角色现在有哪些工作」，资料按需读

**观察。** S2 打开角色资料后，默认展开的长 su 角色卡占了抽屉主要位置；其后「待办/队列」显示「无」和「（无待办）」，再有「队列概览 无」。S3 手动折叠后才让这些内容上移，两个空节仍然重复。当前只有空闲态，不把这张截图描述成「忙时找不到待办」。

**代码事实。** `renderer.js:2377` 起固定先打开角色卡，再打开待办/队列，队列概览只读同一队列的另一视图；`:2192` 已有全文/撤回操作；`:2300` 的资料图标数字角标来自当前角色进行中+排队。由此**推断**：用户因为角标进去查工作时，仍然先读职责正文；同一排队列表在两节出现，增加判断成本。

**拟采用交互。** 保留右上角两枚图标与覆盖抽屉，所有内容继续跟随当前角色。抽屉顶部标角色名；有真实进行中/排队时先显示「当前工作」和同一列表的排队条目，默认展开；角色卡、边界、变更、文档收起在后。点击数字角标等同打开这份工作列表，不另造待办中心。空闲时只留一处「无进行中或排队消息」，角色卡仍可主动展开阅读。合并重复的「队列概览」，位次、来源、入队时间、全文、仅未投递客户消息可撤回的权限保留。切换角色时标题、条目和角标同步，不沿用上一角色任务。

**验收标准（待实现后验证）。** 受控工作态有一个进行中+三条排队时，点击资料图标，首屏就看到角色名、当前条目和排队位次，不必先滚过角色卡。空闲角色不会出现两处同义空队列。两角色切换后条目不会串；长全文可读；撤回客户排队消息后只更新同一真实快照，派发/回交和进行中无撤回入口。手动展开资料后收到状态刷新，不无故把阅读状态重置。

**建议属主/成本。** 桌面应用，预计小至中：重排并合并现有抽屉分组，复用既有快照和操作，无需新增投递机制；主要成本是展开态与角色切换的交互验证。

## 可后置的建议
