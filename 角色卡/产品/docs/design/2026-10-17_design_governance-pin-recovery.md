# 治理记录 pin 不符的重新接受恢复（设计提案）

一句话结论：**当 `.ans/project.json` 存在且可解析、但 pin 与盘上边界文件不一致时，项目应进入一个可被看见、可被显式恢复的 `pin-mismatch` 状态。** 恢复只做两件事：把当前盘上内容的 SHA-256 重算后写回 `.ans/project.json` 的 pin 列表，并重新生成 `docs/bootstrap-manifest.md`（追加一条「重新接受」留痕）。**不修改任何边界文件内容，不自动接受，不在未确认前写任何文件、不开会话。** 这延续既有口径：pin 是「授权证据」，不是「盘上校验和镜像」；重新接受必须是一次操作者显式动作。

本记录为**设计提案（proposed）**：未实施、未测试。客户方向已定（逐字见下），实施须经项目管理评审并按角色边界拆发。

## 一、问题与现场

### 1.1 客户现场（已由顶层诊断确认，本提案不另起结论）

- 项目 `D:/work/vibe-code/codeagent` 的 `.ans/project.json` 里，治理记录的 pin 钉住了 **9 个边界文件**：1 个 `角色卡/governance-boundary.yaml` + 8 个项目角色的 `boundary.yaml`。
- 操作者在 su 会话之外修改了 `角色卡/assembly/boundary.yaml`（随后提交进 git）。
- 下一次打开 su 会话时，`openGovernanceSession` 直接抛出「治理边界解析失败：边界未通过 SHA-256 pin 校验：…」，**所有角色**一起不可用——不是某一个角色坏了。

### 1.2 机制事实（只读复核，行号为写作时点工作树读数，实施前复核）

1. **pin 校验是全局的，不是逐文件的局部判定**。
   `src/common/门禁引擎/boundary-core.ts:374-394` 的 `verifyPins(fileAbs, projectRootAbs, pins)` 在加载**任意**边界文件时，遍历 pin 列表里的**每一个**文件：
   - 任一文件不可读 → 返回失败；
   - 任一文件的实际 SHA-256 与 pin 不符 → 返回失败；
   - 加载中的边界文件还必须被至少一条 pin 覆盖。
   `loadBoundaryFile` 在 `boundary-core.ts:447-452` 把失败统一转成 `unaccepted(...)`：条目清空、`accepted:false`、原因写入 `parseError`。
2. **打开 su 会话时按错误直接失败**。
   `src/pipeline/orchestration/govern-session.ts:150-155`：`resolveRole` 得到治理边界后，只要 `parseError` 非空就 `throw`。pin 不符必然带 `parseError`，所以会话在发起任何一轮之前就结束。
3. **其他角色同样受影响**。门禁对每个角色的边界加载都走同一份 pin 列表；一个文件的变化让所有边界回落为未接受。
4. **现有「建立治理记录」不覆盖已存在记录**。
   `src/common/编排/finalize.ts:709-721`：`.ans` 状态为 `usable` → `already-established`；为 `invalid` → `invalid-record`。两者都明确「本次未写入任何文件」，V1 不覆盖。
5. **自动重 pin 只在 settle 之后运行**。
   `src/pipeline/orchestration/run-role.ts:901-914`：`settled` 事件后才调用 `repinIfBootstrapped`。会话开不起来 ⇒ 永远没有 settle ⇒ 自动重 pin 永远不触发。
6. **自动重 pin 自己也要过门**。
   `finalize.ts:189-240` 的 `precheck` 对每个待写路径调用 `resolveWrite`；`run-role.ts:907` 传入的是本次会话的 `setup.role.boundary`——pin 不符时它已经是 `accepted:false`。因此写 `.ans` 同样被 F6 拒绝（`finalize.ts:871-886` 的 `gatedAtomicWrite` 写前再求一次）。
7. **桌面当前不区分 pin 不符**。
   `app/desktop/project.ts:184-245` 的 `deriveGovernanceRecord` 只派生 `present / missing / invalid`，注释明确写着「不声明 pin 逐文件匹配；S4 pin 不符仍显示 present」。这就是为什么现场在打开会话前看不到任何异常信号。

### 1.3 客户方向（逐字）

> 「这个恢复入口按角色链做一下」

此前顶层已向客户说明并获认可：**不采用「文件一改就自动 hash」**，因为那会让 pin 失去「授权证据 + 篡改检测」的意义。本提案按这个方向展开。

## 二、为什么现有路径都堵死

| 路径 | 现状 | 为什么救不了现场 |
| --- | --- | --- |
| 自动重 pin（`repinIfBootstrapped`） | 每轮 su settle 后运行 | 会话开不起来 → 没有 settle → 不运行；且写 `.ans` 本身被未接受边界拒绝 |
| 「建立治理记录」（`establishGovernanceRecord`） | `.ans` 存在即 `already-established`，不可解析即 `invalid-record` | V1 明确不覆盖；现场 `.ans` 可解析且存在 |
| 手动改 `.ans` 的 pin | 技术上可做 | 不是产品路径；操作者要自己算 SHA-256，且没有留痕、没有校验、容易写坏记录 |
| 删除 `.ans` 再建立 | 技术上可做 | 会丢掉原治理记录与授权来源，退化为「重新创世」；且把「一次边界修改」升级成「治理记录重建」，代价与风险不相称 |
| 什么都不做，等下一轮 settle | 行为上等于永久不可用 | su 自身不可用，其他角色也全部不可用 |

结论：**缺的不是「再算一次 hash」的能力，而是一个位于「会话之前」、只读可见、由操作者显式确认的恢复入口。** 这个入口必须能在边界未接受的状态下，仍然安全地只写两处治理记录文件。

## 三、目标体验

### 3.1 入口位置

沿用 I3「建立治理记录」已经建立的三个位置，不新增模态、不新增第四个入口：

1. **su 空态**（`.chat-empty`，现有「建立治理记录」卡的位置）；
2. **提示条状态行**（`.session-notice` 里的 `#governance-status`）；
3. **非模态预览面板**（`#governance-preview`，点击后在同一位置展开）。

三处的可见判据收敛到 `ui-labels.js` 的**单一谓词**，渲染侧不直接比较状态字符串（现有测试已经对 `state === "missing"` 的直接比较设了禁线，新状态沿同一纪律扩展）。

### 3.2 界面文案建议（可直接作为实现蓝本）

**状态行（`pin-mismatch`）**

> 治理记录与盘上边界不一致：9 个边界文件中有 1 个在记录建立后被修改。未确认前，会话不能开启、写入会被拒绝。
>
> ［检查并重新接受］

**su 空态**

- 标题：`治理记录与盘上边界不一致`
- 说明：`有边界文件在治理记录建立后被修改。确认接受后只会刷新 SHA-256 与留痕，不会修改任何边界文件内容。`
- 主按钮：`检查并重新接受`
- 次行（可选，保留既有出路）：`也可在终端核对 git 历史后再处理。`

**预览面板（点「检查并重新接受」后展开，非模态）**

- 标题：`重新接受治理边界（预览）`
- `变更文件（1）：`
  - `角色卡/assembly/boundary.yaml — 内容已变更（pin a1b2c3d4… → 现 9f8e7d6c…）`
  - 缺失文件单独一行：`角色卡/<id>/boundary.yaml — 文件缺失（无法重新 pin）`
- `将写入：.ans/project.json、docs/bootstrap-manifest.md`
- `将重算这 9 条 pin；不新增、不删除 pin 条目，不修改任何边界文件内容。`
- `确认后，这些文件的当前内容即被视为已授权；本次变更会记入 docs/bootstrap-manifest.md 的「重新接受记录」。`
- 警示行：`如果不认识这些改动，请先通过 git 历史或备份核对，不要直接接受。`
- 按钮：`［确认接受］［取消］`

**成功**

> 已重新接受：更新 1 条 pin（共 9 条），写入 `.ans/project.json` 与 `docs/bootstrap-manifest.md`。项目已恢复可用。

成功后刷新项目列举，状态回到 `present`；**不自动打开 su 会话**（与「不在导入/恢复时自动起会话」的既有口径一致）。

**失败**

- 守卫/预检失败（零写入）：原文原因 + `本次未写入任何文件。`
- 写入阶段失败：`写入中断：<原因>；可能已写入部分文件（.ans/project.json 与 docs/bootstrap-manifest.md 不保证齐全），请核对现场。` 绝不出现「已恢复」「已成功」。
- 预览后文件又变：`预览后边界文件又有变化，已取消本次写入；请重新检查。`

### 3.3 体验原则（沿用本角色已定的五条口味）

- 只在异常时出声：`present` 不显示任何东西。
- 信息在对的上下文：文件明细在预览里，不铺在空态。
- 诚实呈现：失败不假装成功；缺失与不可读如实区分；不显示无法证明的「已恢复」。
- 每样东西有用：不加「稍后提醒」「记住选择」「本会话忽略」。

## 四、状态机

### 4.1 四态定义

| 状态 | 判据（按优先级从上到下） | 界面 | 可用动作 |
| --- | --- | --- | --- |
| `missing` | `.ans/project.json` 不存在 | 现有 S1「尚无治理记录」 | 「建立治理记录」（现有流程） |
| `invalid` | `.ans` 存在但不可解析/结构无效；或 `accepted !== true`；或治理边界路径为空 | 现有 S3「治理记录不可用：<原因>；本版不自动覆盖」 | 无（V1 不自动覆盖） |
| `pin-mismatch` | `.ans` 可解析、`accepted === true`、pin 形状合法且非空；至少一条 pin 目标缺失、不可读或 SHA-256 不符 | 新增：不一致说明 + 变更明细 | 「检查并重新接受」 |
| `present` | `.ans` 可解析、`accepted === true`、pin 形状合法且非空；全部 pin 目标可读且哈希一致 | 不显示 | 无 |

**优先级说明**：先判存在性，再判可解析性/接受状态，最后才逐文件比对哈希。`missing` 与 `invalid` 的现有行为**逐字不变**；`pin-mismatch` 是 `present` 之前的唯一新增分支。

### 4.2 逐文件明细的形状（产品口径）

每条至少包含：

- `path`：项目相对路径（posix）；
- `pinned`：记录里的 SHA-256；
- `actual`：当前盘上 SHA-256；缺失/不可读时为 `null`；
- `status`：`modified`（可读且不等） | `missing`（不存在） | `unreadable`（存在但读失败）。

明细是预览的唯一事实来源；确认写入时**必须重新求值**，不得复用预览快照。

### 4.3 状态转换

- `present --(外部修改边界文件)--> pin-mismatch`
- `pin-mismatch --(操作者确认接受，写入成功)--> present`
- `pin-mismatch --(取消 / 关闭 / 任何校验失败)--> pin-mismatch`
- `missing --(建立治理记录成功)--> present`（现有流程，不在本提案范围）
- `invalid` 不因本提案发生转换。

## 五、恢复流程与守卫

### 5.1 流程（两步，缺一不可）

1. **只读检测**：加载项目时，对 `.ans` 中的每条 pin 计算盘上实际哈希，得到 `pin-mismatch` 状态与逐文件明细。检测**不写任何文件、不开任何会话**。
2. **操作者点「检查并重新接受」**：进入预览。预览阶段再次只读求值，显示变更文件、变更前后哈希、将写入的两个路径、pin 条目数。**此时仍未写盘。**
3. **操作者点「确认接受」**：执行一次受控写入：
   - 重算**现有 pin 列表全部条目**的 SHA-256（不增不删条目），写回 `.ans/project.json`；
   - 重新生成 `docs/bootstrap-manifest.md`，追加一条「重新接受记录」；
   - **不修改任何边界文件内容**，不改 `.ans` 的 `roles` 映射，不改 `acceptance.source`（V1，见开放问题）。
4. **结果如实呈现**：成功则刷新状态为 `present`；失败按 §3.2 的失败文案呈现。

### 5.2 必须实现的守卫

| # | 守卫 | 判据与行为 |
| --- | --- | --- |
| G1 | 仅 `pin-mismatch` 可进入 | 写入前重新求值状态；`missing` / `invalid` / `present` 一律拒绝，零写入，并提示当前实际状态 |
| G2 | 只写两个路径 | 机制内部**硬编码** `.ans/project.json` 与 `docs/bootstrap-manifest.md`；**不接受调用方传入写路径**（沿用 I3「机制不接受调用方提供边界/授权来源/写路径」的纪律） |
| G3 | 写仍过门 | 复用 `resolveWrite`：为本次显式动作构造**一次性内存种子边界**（沿 I3 的 `buildGovernanceSeedBoundary` 先例，条目仍只含 `角色卡/`、`docs/`、`.ans/`），每个待写路径前置求值、全部放行才逐笔原子写；**不新增持久化绕过、不把恢复入口暴露成模型工具** |
| G4 | 预览后再次变化则拒绝 | 写入前重新计算全部 pin 目标哈希；与预览快照不一致 → 中止、零写入、提示重新检查 |
| G5 | 缺失文件阻断 | 任一 pin 目标 `missing` / `unreadable` → 拒绝接受（无法为不存在的文件写 pin）；明细如实列出。V1 不为「删除角色」提供隐式修复 |
| G6 | 内容可解析预检 | 写入前用门禁同一套解析器检查每个**将重新 pin 的边界文件**：不可解析或 Section 1 为空 → 拒绝，并点名文件。否则会出现「pin 刷新成功但项目仍不可用」的假成功 |
| G7 | 同项目互斥 | 预览/写入按项目根加进程内互斥（沿 `governanceEstablishInFlight` 先例）；跨进程无全局锁，如实登记 |
| G8 | 写入原子性 | 每个文件同目录临时文件 + rename（沿用 `gatedAtomicWrite`）；失败不自动重试、不清理已写产物，如实返回 |

### 5.3 留痕（`docs/bootstrap-manifest.md`）

重新生成 manifest 时，保留现有 pin 表与创建路径信息，并新增一节：

```text
## 重新接受记录（治理记录 pin 刷新）

- 2026-10-17T02:34:56.789Z：操作者在桌面应用确认重新接受；变更 1 个边界文件（本次刷新 9 条 pin）
  - 角色卡/assembly/boundary.yaml（旧 pin a1b2c3d4… → 新 pin 9f8e7d6c…）
```

要求：

- 每次重新接受**追加一条**，历史条目保留；读取旧 manifest 失败或找不到该节时，如实写一行「此前的重新接受记录不可读取，未保留」，不得静默丢弃。
- 至少包含：时间（ISO 8601）、触发方式（操作者确认）、变更文件数、逐文件路径、旧 pin 与新 pin。
- manifest 头部现有「pin 每轮 su settle 后自动刷新」的说明需补一句：另有操作者显式「重新接受」这一手动路径。

## 六、不做什么（含自动 hash 的取舍理由）

1. **不做「文件一改就自动 hash / 自动 re-pin」**。理由（沿用客户已认可的方向）：
   - pin 的语义是「**授权证据**」——它记录的是某次明确同意时盘上的内容，不是盘上内容的一面镜子；
   - 自动刷新会把「未经授权的改动」在无人决策的情况下转成「已授权」，`accepted` 随即失去意义；
   - 任何能写边界文件的进程都能触发自动接受，等于让被约束方自行签发授权，直接违背 fail-closed；
   - 自动刷新会抹掉「发生了外部改动」这一唯一可用的异常信号。
   - 代价如实承认：合法修改现在需要一次显式点击；这正是该机制要保留的成本。
2. **不做「重复命令自动接受」「记住选择」「本会话忽略」「总是允许」**。没有隐藏开关、没有环境变量、没有第二次点击即视为同意的捷径。
3. **不修改任何边界文件内容**。即使发现格式问题，也不在恢复流程里顺手改写；格式问题走各自属主。
4. **不处理 `.ans` 缺失或不可解析**。前者走「建立治理记录」，后者保持「本版不自动覆盖」。
5. **不新增、不删除 pin 条目**（V1）。恢复只刷新现有 pin 列表；新出现的角色边界文件由会话恢复后的自动重 pin 吸收。
6. **不由模型或后台触发**。恢复入口只存在于桌面操作者界面；su 的工具面不注册任何恢复工具。
7. **不自动打开会话**。成功后回到项目空态，由操作者自己继续。
8. **不承诺「钉死不动的篡改检测」**。pin 在每轮 settle 后仍会自动刷新；本提案只是把「外部改动 → 下一次 settle 吞掉」的窗口，改成一个可见、需确认的步骤。

## 七、验收口径（可测量）

| # | 场景 | 可测量断言 |
| --- | --- | --- |
| AC1 | 9 条 pin 全部一致 | `governanceRecord.state === "present"`；不出现任何恢复文案/按钮 |
| AC2 | 修改 1 个被 pin 的 `boundary.yaml` | 打开项目后状态为 `pin-mismatch`；明细恰好 1 条 `modified`；`pinned !== actual`；`.ans/project.json` 的 mtime 与内容哈希不变；未创建任何新文件 |
| AC3 | 修改 2 个 + 删除 1 个被 pin 文件 | 明细 3 条（2 `modified` + 1 `missing`）；预览可见；「确认接受」被 G5 阻断，零写入 |
| AC4 | 预览后点取消 | 零写入（全部相关文件 mtime/哈希不变）；状态仍为 `pin-mismatch`；未开启任何会话 |
| AC5 | 正常确认接受 | 仅 `.ans/project.json` 与 `docs/bootstrap-manifest.md` 变化；`.ans` 的 pin 路径集合与条数与写入前**完全相同**；8 个角色边界与治理边界文件的内容哈希不变；manifest 出现一条含时间/变更数/逐文件路径/旧新哈希的记录 |
| AC6 | 接受后重新加载 | 同一检测路径返回 `present`；`resolveRole` 对 su 得到 `accepted:true`、`parseError` 为空；测试用会话入口（无需真实模型）能成功开启 |
| AC7 | 预览后、确认前再次修改文件 | 拒绝写入；提示「预览后边界文件又有变化」；零写入 |
| AC8 | 变更文件是坏 YAML / Section 1 为空 | 预览阶段即拒绝接受并点名文件；零写入；状态保持 `pin-mismatch` |
| AC9 | `.ans` 缺失 | 状态 `missing`；只出现「建立治理记录」；不出现「重新接受」 |
| AC10 | `.ans` 不可解析 | 状态 `invalid`；只显示原因与「本版不自动覆盖」；不出现「重新接受」 |
| AC11 | 写入阶段人为抛错 | 返回失败；文案不含「已恢复/已成功」；若可能已写部分文件，明确提示核对现场 |
| AC12 | 回归 | `node --test "test/**/*.test.ts"`（三层 glob，禁止两层）全绿；现有 `deriveGovernanceRecord` 的 `present/missing/invalid` 用例逐字保持 |

## 九、风险

| # | 风险 | 影响 | 缓解 |
| --- | --- | --- | --- |
| R1 | 操作者盲点：直接点「确认接受」 | 把不认识的改动一并授权 | 逐文件明细 + 旧/新哈希 + 警示行；不提供「全部接受」以外的批量简化；不做「记住选择」 |
| R2 | 多次外部改动被一次确认吞掉 | 留痕只能看到「当前结果」，看不到每一次中间改动 | 留痕记录本次变更文件数与逐文件旧/新哈希；文案明确「接受的是当前盘面」；提示先用 git 历史核对。**不声称这等于完整变更历史** |
| R3 | 审计留痕本身可被改 | manifest 在 `docs/` 下，不在 pin 保护内，任何本地写者都能改 | V1 如实登记局限；是否在 `.ans` 增机器可读的重新接受记录，列为开放问题 |
| R4 | 缺失文件无法恢复 | 合法删除角色也会落入 `pin-mismatch`，且被 G5 阻断 | V1 明确阻断、如实说明；删除角色应有独立的角色移除流程（后续版本），不在本入口偷偷改 roles |
| R5 | 未被 pin 覆盖的新边界文件不在本状态内 | 项目显示 `present`，但新角色的边界仍因「未被任何 pin 覆盖」不可用 | 状态定义只覆盖 pin 列表内的文件；恢复后下一轮 settle 的自动重 pin 会吸收新文件；文档与预览如实说明 |
| R6 | pin 一致但边界内容不可解析 | 状态显示 `present`，会话仍可能因解析错误失败 | 本提案不扩展 `present` 的判据（避免把内容健康检查混进 pin 状态）；列为已知盲点，后续独立处理 |
| R7 | 预览与确认之间的竞态 | 确认到未看过的内容 | G4 写入前重算并比对预览快照；不一致即拒绝 |
| R8 | 多实例并发 | 两个桌面实例可能同时操作同一项目 | 进程内互斥 + 原子写；跨进程无锁（既有先例），最坏写出同构产物，不扩大权限 |
| R9 | 恢复机制被误当成「pin 不重要」 | 用户习惯性点接受，tamper 信号退化 | 文案把「未确认前不能用」和「接受即授权」说透；不在状态行提供一键接受；入口只在异常态出现 |
| R10 | 留痕时钟/真实性 | 时间来自本机系统时钟，未签名 | 与现有 manifest 同级；不承诺防伪，只承诺可追溯 |

## 十、待 PM / 客户拍板的开放问题

| # | 问题 | 推荐默认 | 备选 |
| --- | --- | --- | --- |
| 1 | 被 pin 文件**缺失**时是否允许「接受删除」并在同一动作里同步移除 roles 映射 | **不允许（V1 阻断）**；删除角色走独立流程 | 允许显式第二选项「该文件已删除，接受删除」——需同时改 `.ans roles`，超出「只刷新 pin」范围 |
| 2 | 是否在 `.ans` 里增加机器可读的重新接受记录（时间/变更数/旧新哈希） | **V1 不加**，留痕只在 manifest | 加可选字段；需定义 schema 与兼容策略 |
| 3 | 是否在预览里展示内容 diff | **V1 不做**（旧内容已被覆盖，只有旧哈希可用） | 接 git 历史或备份做 diff——依赖项目是否在 git 且无未提交改动，不普遍可靠 |
| 4 | 新出现、未被 pin 覆盖的角色边界是否在同一次接受里纳入 | **不纳入**（V1 只刷新现有 pin） | 同一动作扩展 pin 集合——等于扩大治理范围，应单独确认 |
| 5 | CLI 是否提供等价恢复入口（如 `ans govern --reaccept`） | **V1 只做桌面**；CLI 可后续补 | 现在就做，需定义终端确认文案与退出码 |
| 6 | 成功后是否自动打开 su 会话 | **不自动**，回到空态 | 自动打开——与「不自动起会话」先例冲突 |
| 7 | `.ans` 的 `acceptance.source` 是否改成「操作者重新接受」 | **V1 不改**，保持原授权来源 | 改写为本次动作来源；会让「最初授权」与「最近一次刷新」混在一起 |
| 8 | 状态行与 su 空态是否同时出现 | **同时出现**（同一谓词、同一动作） | 只在空态出现——异常态更不容易被看见 |
