# 设计：ANS 桌面应用（Electron）

> **状态：已实施（交互模型客户定稿并落地；实现见 `app/`，单测与端到端全绿）。**
> **客户已否决分期**：左树、聊天、资料三栏**一次做全**。

## 1. 目标

把受治理会话从命令行搬到人直接可用的界面。三栏结构（客户描述）：

- **左**：导入项目；点项目展开，列出该项目下的各个角色。
- **中**：与角色会话的聊天。
- **右**：角色说明、边界、变更记录、文档索引等资料。

## 2. 定位：同一个引擎的第二个前端

**这不是另一个引擎，也不是另一个仓库。** CLI 与 App 共用现有的 `Service` / `Pipeline` / `Provider`：

- 路径判定**一律**调门禁引擎的 `resolveWrite`；
- Pi 调用**一律**经 Pi 适配器的 `RuntimeAdapter`；
- 边界解析与角色解析**一律**调门禁引擎（含 YAML 严格解析与 fail-closed）。

**渲染进程里不得出现任何第二份边界判断实现。** 两套真相源必然漂移——本项目已经吃过一次同类亏（配置重复）。

## 3. 技术选型

**Electron。** 整条栈是 TypeScript + Pi 的 Node SDK，Electron 主进程本身就是 Node，`resolveWrite`、Pi 适配器、角色机制可以**同进程**直接调用，不需要 sidecar，也不引入额外的跨进程协议。

反面：Tauri 体积更小，但需外挂 Node 进程，多一层转发——而本项目的核心主张恰是「进程边界即角色边界」，多一层转发会把这层含义搅浑。

代价（已知）：包体积大、内存占用高。

## 4. 分层映射

| 位置 | 归属层 | 说明 |
| --- | --- | --- |
| Electron 主进程（`app/main.ts`） | 根入口 + Interface 生命周期 | 持有 Interface 句柄，不直接导入 Service/Provider 对象 |
| preload 桥（`app/preload.ts`） | Interface | 只暴露受限 IPC 通道，不暴露 Node 能力 |
| 渲染进程前端（`app/renderer/**`） | 视图 | 不接触文件系统；只经 preload 调用 |

调用方向仍为 `入口 → Interface → Pipeline → Service → Provider`。

## 5. 范围（不分期）

### 5.1 项目与角色（左栏 + 右栏）

- 通过**系统文件夹选择器**导入项目（选择器本身就是人类的显式授权）；
- 枚举该项目下的角色（**由门禁引擎提供**，不在界面里重写解析）；
- 点角色 → 右栏显示：角色卡正文、Section 1 边界条目（`kind` / `path` / `purpose` / `condition`）、变更记录索引、`docs/` 目录索引。

### 5.2 会话（中栏）

- 在界面上点一个角色即建立受治理会话（§5.3），发消息，事件实时刷出：`tool_call` / `denied` / `accepted` / `message` / `settled`。
- 会话能力来自**编排**的 `openRoleSession`；Pi 适配器由注入的工厂提供（`--runtime` 等价选择在界面上给出）。

### 5.3 会话授权（客户最终定稿）

> **导入项目这个动作本身就是授权。** 用户经系统文件夹选择器选择项目根，即为该项目下的角色授权；
> 之后**左树点一个角色 → 中栏立即进入聊天，没有任何确认弹窗**。
>
> - 不显示 writeSet、不显示边界文件清单、不显示 acceptance 来源——**用户对这些无感**
>   （边界是项目管理管的事，不是聊天的人管的事）；
> - 聊天是多轮的：消息自由发、按对话累积；
> - **门禁照常在后台拦每一次写入**，被拒时在聊天流里**内联显示一条拒绝消息**
>   （含按根分组的允许路径，可展开）——这是有用的反馈，不是手续；
> - 会话经编排的 `openRoleSession` 建立（**只建一次**），之后每条消息直接发送。

演进记录：初稿「每次派发前弹确认框（含 writeSet）」→ 客户否决 writeSet（聊天里没有预先任务）→
改为「每会话一次确认（无 writeSet）」→ 客户再次简化为「导入项目 = 授权，点角色即开」。最终以本节为准。

### 5.4 IPC 通道（定稿）

| 通道 | 方向 | 作用 |
| --- | --- | --- |
| `app:pick-project` | 渲染 → 主 | 调系统文件夹选择器，返回项目路径 |
| `app:list-project` | 渲染 → 主 | 返回角色清单、角色卡正文、边界条目、文档与变更记录索引 |
| `session:open` | 渲染 → 主 | **点角色即开**：一次调用直接建立与该角色的会话（无确认步骤） |
| `session:send` | 渲染 → 主 | 发送消息（**可反复调用**：多轮聊天） |
| `session:stop` | 渲染 → 主 | 关闭会话（切换角色/关窗时调用） |
| `session:event` | 主 → 渲染 | 推送会话事件（流） |

具体通道名与参数见 `api-spec.md`。**不存在「先请求摘要、再确认、才启动」的顺序**——已随授权模型一并删除。

### 5.5 su 的写权不呈现于角色列表（2026-10-11 客户裁定：**取代**上一版「只读」徽标/提示）

> **上一版实现**曾在角色列表与 su 会话里呈现「**只读**」徽标 + 「本版只读」内联提示（判据 `isReadOnlyRole` → `RoleView.readOnly`）。**该呈现已被本决定取代。**

客户看截图后裁定（原话「这个 su 有角色也不不是只读的，**一直可以聊天**，你看图，**还是只读的**」）：**回到本稿 §5.3 早已定过的模型**——**导入项目 = 授权；门禁静默执行，拒绝在聊天流里内联显示**；**不需要提前打预防针**。**「只读」徽标是后加的、偏离了这条**（客户另说过「文件边界压根用户无感」——边界归项目管理，不该在角色列表上摊给用户）。故移除：

- 角色列表不再渲染 `只读` 徽标（`RoleView.readOnly` / `isReadOnlyRole` 及其派生一并删除）；
- 打开 su 会话不再内联「本版只读」提示。

**保留**（**均非**边界机制）：

- `主入口`（= 默认入口）、`内置`（= 无角色目录）两枚徽标；
- **写入语义**提示（**现为单一句、常驻中栏横栏**：写入会真正落到导入项目，但受角色边界约束，越界写在写之前被拒）——那是**运行时**语义（这条消息是否真的落盘），非边界/写权机制，也不暴露 writeSet / 边界路径 / acceptance。**客户 2026-10-11 再裁定：去掉运行时选择器、桌面一律跑 pi**，故它不再「随运行时切换」、只剩 pi 一层意思，且从输入区**上移到横栏**（§7 末条）；
- **拒绝内联显示**（§5.3 的 `denied` 事件，浅红可展开块）——**那才是客户要的「静默执行 + 拒绝内联」**，保持不变。

> 实现与验证证据见 `角色卡/桌面应用/changelog.md` 顶部「移除 su 的『只读』徽标与只读内联提示」。

## 7. 已知偏离与风险

- **与设计文档 §8 冲突**：原文写明「本期不做 Dashboard、云端同步、代码图谱」。本应用属明确 scope 变更，如实记录。
- `package.json`（electron 依赖、scripts、入口字段）属**装配**角色的 Section 1；跨角色需求交项目管理协调。
- **角色枚举是新增能力**：现有引擎只按 id 解析单个角色，没有"从一个项目根列出全部角色"。按 §2 的约束，这必须由门禁引擎提供，不能在界面里另写一遍解析。
- 渲染进程越权（直接拿到 Node 能力）是主要安全风险，靠 preload 白名单约束。
- 界面成了一条真实写路径，其授权模型**必须与 CLI 一致**，不能更松。
- **写入语义（客户 2026-10-11 定稿：去掉运行时选择器、桌面一律跑 pi）**：桌面**不是整体只读**——一律走
  **pi 路径**（经编排 `createPiAdapterFactory` → 真实 Pi 适配器，`writeRoot = projectRoot`）**会真正写入被导入项目**，
  但**受门禁约束**（角色边界 Section 1 + acceptance，与 CLI 同一套 `resolveWrite`），越界写在**写之前**被拒。
  这与 §5.3「导入项目 = 授权该角色按其完整边界工作」一致。界面**不再**一概而论「V1 桌面：只判不写」，
  也**不再**暴露运行时选择器：写入语义压缩为**一行**、与状态提示一同**常驻中栏横栏**；底部输入区**只剩输入框 + 发送**。
  （demo 适配器保留于 `app/desktop/chat-adapter.ts`，但只作**测试注入缝**上的替身——e2e 注入它顶掉真实 pi 工厂以离线跑完整流程；界面**无任何后门开关**。）
- **授权模型对 CLI 的已知偏离（客户定稿）**：CLI 用 pin 确认边界；本应用定稿为「导入项目 = 授权」。
  这是客户明确要求的交互简化，`acceptance.source` 已如实标注
  「desktop-app:导入项目即授权该角色按其完整边界工作（原型，无客户 pin，已知偏离）」；
  门禁判定本身（`resolveWrite`、fail-closed、按根分组拒绝信息）与 CLI 完全一致，未放宽任何一条路径判定。
- Electron 打包体积与签名分发方式未定。

## 8. 验收标准

1. 能通过系统文件夹选择器导入一个项目；
2. 左树列出该项目下的角色；
3. 点角色，右栏正确显示角色卡、边界条目、变更记录索引与文档索引；
4. 点角色，中栏**立即进入聊天，全程无确认框**；多轮消息直发、按对话累积；
5. 会话事件（`tool_call` / `denied` / `accepted` / `settled`）实时刷出；
6. 越界写入在写之前被拒，拒绝信息含按根分组的允许路径；
7. 解析与判定**没有第二份实现**：全部来自门禁引擎；
8. 渲染进程无法直接访问文件系统。

## 10. 视觉方向（2026-10-11 定稿：浅色、中性、极简）

### 10.0 现行方向（定稿，取代「图纸」）

**客户发来参照截图，原话「整体风格和这种就行了」——参照即 Claude 桌面应用本身的界面**（浅色、干净、极简）。据此**作废**此前「图纸（drafting）」方向（方格底纹、斜线阴影带、尺寸标注、实线/虚线行那套）。现行视觉：

- **底/分隔**：主内容区近白 `#FFFFFF`；**侧栏**略灰 `#F4F4F2`，与主区**靠色差区分**（不靠边框）；分隔用**极淡的线**（`#E8E8E6`）或干脆不用线（靠留白分组）。**不是奶油、不是深色。**
- **文字**：近黑 `#1F1F1F` 为主、次级灰 `#6B6B6B`；字号偏小、行距舒展。
- **强调色基本没有**：按钮 / 选中态 / 药丸一律**中性灰**（选中 = 浅灰底 + 深字；主按钮 = 中性深色实心）。唯一允许的是**语义色**——拒绝 `#B42318`（浅红底内联块）、成功 `#067647`——**面积小、只在必要时**。
- **圆角只给交互元素**（按钮 / 输入 / 药丸 / 列表选中项，6–8px）；**内容区域不做圆角卡片、不加投影**。
- **字体一套无衬线为主**（系统栈）；**等宽只留给技术事实**（路径 / SHA-256 / 工具名）；**去衬线正文**。
- **中栏横栏**：一行标题 + 状态 + 操作（`聊天中` 药丸、`Pi 设置`、`结束会话`），下面**一行小字**放状态提示与写入语义（各压缩成一行）。**底部输入区只有一个输入框 + 发送**（无选择器、无提示行——客户看截图裁定「底部搞复杂了，应该就是一个输入框」）。
- **保留**（与新方向一致）：技术事实等宽；**拒绝有明确但不喧哗的呈现**；**一处用力**（现在是拒绝的语义红）。
- **作废**：方格底纹、斜线阴影带、尺寸标注、实线/虚线行、等宽+衬线+无衬线三套字的用法。

**硬约束（本方向下仍成立）**：纯 CSS、零外部依赖（含不引外部字体）、无 emoji、无装饰性花纹/渐变；**只动视觉层**（`app/renderer/{styles.css,index.html,renderer.js}` 的样式与呈现），`renderer.js` 里**判定的读取一个未动**、渲染侧**无第二份判定**；响应式到窄窗、键盘 focus 可见、尊重 `prefers-reduced-motion`。

> 实现与验证证据见 `角色卡/桌面应用/changelog.md` 顶部「视觉方向定稿：浅色、中性、极简」。

## 11. 窗口装饰：由原生改为自绘（2026-10-11 客户裁定）

**来源**：客户要求——原话「**顶部需要去除 electron 原本的，自己搞一个**」。顶部原有**两样原生 chrome**：最上面那条 **OS 标题栏**（应用图标 + `ANS` + 最小化/最大化/关闭），以及它下面那条**默认菜单栏**（`文件 / 编辑 / View / …`）。**两样都去掉**，改为一条自绘的窄栏。

### 11.1 去原生 chrome（主进程 `app/main.ts`）

- **无边框**：`BrowserWindow` 加 **`frame: false`**。**缩放宽没弄丢**——`resizable` **不动**（默认 `true`），Windows 上无边框窗口默认仍带缩放边框（`thickFrame` 默认 `true`）；最小化/最大化/关闭改由自绘按钮经 IPC 驱动。
- **去默认菜单栏**：`app.whenReady()` 里 **`Menu.setApplicationMenu(null)`**（那条「文件/编辑/View…」就是 Electron 默认 application menu，置 null 即整条移除）。
- **快捷键**：编辑类快捷键（Ctrl+C/V/X/A、撤销）由 **Chromium 原生**处理、不依赖菜单，**未失效**；被移除的只是默认菜单的加速键（Ctrl+R 重载、Ctrl+Shift+I 开发者工具、Ctrl+Q 退出等）。本应用是极简聊天工具，这些**并非必要**，故 **不补回任何加速键**，更**不把菜单栏加回来**。

### 11.2 自绘标题栏（渲染侧 `app/renderer/**`）

- **构成**：顶部一条窄栏 `#titlebar`——**左＝应用标识**（`ANS 治理会话工作台`）；**右＝三个窗口按钮**（`#win-min` / `#win-max` / `#win-close`）。原左栏头里重复的品牌标识**上移到标题栏**，左栏头改成分区标签「项目」（与右栏「角色资料」并列），**不重复堆砌**。
- **拖动区 / no-drag**：整条 `.titlebar` 设 `-webkit-app-region: drag`；按钮及容器设 `-webkit-app-region: no-drag`（否则点不动）。
- **双击最大化＝系统原生**：拖动区在 Windows 上按 **HTCAPTION** 对待，**双击即按惯例最大化/还原**——系统原生完成，故渲染侧**刻意不挂 `dblclick`**（叠加会与原生切换抵消成「双击没反应」）。
- **按钮 → IPC**：`window:minimize` / `window:toggle-maximize` / `window:close`（渲染 → 主）→ `win.minimize()` / `win.maximize()|unmaximize()` / `win.close()`；`window:is-maximized`（读当前态）+ `window:maximized-changed`（主 → 渲染，`maximize`/`unmaximize` 时外推）→ 渲染侧 `setMaximizedUI` 在「最大化 / 还原」两图标间切换（`.win-btn.is-maximized`）。
- **风格**：融入 §10 浅色中性极简——无装饰、无 emoji、小圆角只给可交互元素；关闭按钮**不是** macOS 式刺眼红块，hover 只给一点克制的语义提示（浅红底 + 深红字）；按钮为原生 `<button>`，**键盘可聚焦**、`:focus-visible` 可见。

> 通道名与参数见 `api-spec.md`；实现与验证证据见 `角色卡/桌面应用/changelog.md` 顶部「去掉原生标题栏与默认菜单栏，自绘标题栏」。

## 12. bootstrap 收口的确认面（T38；客户裁定：su 提议 → 客户确认 → 完成）

**来源**：客户 2026-10-11 裁定——「完成 bootstrap 应该是 **su 主动觉得差不多了来完成**；后面 su 可以动态增加和修改」+「当然需要客户确认了」。故完成方式 = **su 提议「可以收口了」→ 界面把这件事摆给客户 → 客户确认 → 才 finalize**（设计 §13）。本层（桌面）承担「**确认面**」这半。

### 12.1 确认通道（**复用既有 (a)，不造第二套**）

finalize 收口时经 **同一个 `OperatorChannelFn` 通道**（§4 冻结契约家 `src/provider/pi/session.ts`；与 shell 闸的 (a) 操作者确认**同一机制、不同实例**）把「su 提议收口」摆给客户确认。落点：`app/desktop/operator-channel.ts::createDesktopOperatorChannel`（**已存在**，本次只**接上**——此前**未注入 finalize 路径** ⇒ 收口时「未接入客户确认通道」→ **不完成**，这正是旧测试两条红的根因）。主进程 `app/main.ts` 用**渲染侧 presenter** 构造该通道，经 `createDesktopInterface({ operatorChannel })` → `SessionManagerDeps.operatorChannel` → **仅创世 finalize 会话**透传给编排 `openRoleSession`（普通聊天逐字不传）。

- **fail-closed**：未接通道 / 不可用 / 超时（默认 120s）/ 客户拒绝 → **不完成**（**不写** `.ans`/manifest/治理边界文档，**零副作用**）。

### 12.2 确认面（**改造旧的「完成 bootstrap」按钮，不删**）

- **触发**：`#bootstrap-action`（**仅创世 su 会话**显示）的按钮**「让 su 提议收口」**——点它请 su 发起收口提议（T37 的 `finalize()` 语义 = **提议，非立即完成**）。
- **提议在聊天流可见**：提议经 `session:finalize-proposal`（主 → 渲染）推达，渲染成**聊天流里的一张确认卡**（`renderer.js::appendFinalizeProposal`）：标题「**su 提议：可以收口了（完成 bootstrap）**」+ 将写出什么（reason）+ `[确认完成]` / `[暂不]`。**确认面只在 su 已提议时才出现**（不是一直挂着的按钮）。
- **回传**：点 `[确认完成]` → `session:finalize-confirm` `{toolCallId, allow:true}`；点 `[暂不]` → `allow:false`（→ 不完成，su 可继续工作或稍后再提议）。卡片就地定格（已确认 / 已暂不）。
- **确认后如实呈现**：成功示写出什么（wrote/pins/roles），措辞读作「**项目已转正**（创世态→正式态），**su 仍可继续增改角色**」；未完成示完整原因（**不假装成功**）。
- 视觉：浅色、近单色——确认卡只用一点克制的深色边框标示「待你确认」（`styles.css::.msg-finalize-proposal`）。

### 12.3 与「聊天无确认弹窗」不对立；通道不删

客户先前定的「无弹窗」**针对普通聊天消息**；**这次是一次性、把项目从「创世态」推进到「正式态」的动作**（客户明确要确认），两者不对立。`session:finalize` / `session:bootstrap-state` 两个通道**保留**（`finalizeBootstrap()` 仍是「请 su 提议收口」的入口）；**不弹系统对话框**（确认渲染为应用内卡片）。

> 通道名与参数见 `api-spec.md`；实现与验证证据见 `changelog.md` 顶部「T38」。

## 10x.（历史）「图纸（drafting）」方向（**已作废**，仅留痕）

> **⚠ 以下「图纸」方向已被 §10.0「浅色、中性、极简」取代。**

**客户要求把界面美化重做**；当时选定视觉方向为**图纸（drafting）**。核心判断：本产品最独特的**不是聊天**，是「**边界**」与「**越界被拦下**」——故视觉语言取自制图/图纸。

### 10.1 被取代的上一版

上一版是「**柔和深色三栏 + 一个蓝色主色**」（`--bg:#101318` 一族 + `--accent:#5b8def`；圆角 6/8/12、柔和面板、uniform 卡片）。该版属 **AI 生成的典型痕迹**（① 近黑底 + 单一亮色 / ② SaaS 卡片套装），客户看得出——**本方向整体取代之**：

- **改浅色**：冷调**纸面** `#ECEFF1`（不是奶油），工具是拿来**读**的；
- **去卡片化**：`border-radius:0`、无 `box-shadow`，三栏**由线划分**，不再有浮起的圆角卡片；
- **制图蓝** `#2E6B8A` 作结构 / 边界 / 允许；**红铅笔** `#A33A22` **仅**表拒绝。

### 10.2 色与字（零外部依赖）

| 名 | 值 | 用途 |
| --- | --- | --- |
| 纸 | `#ECEFF1` | 冷调纸面 |
| 格 | `#D9E0E4`（主格 `#CDD7DC`） | 方格底纹（`repeating-linear-gradient`，画的是线） |
| 墨 | `#1E2529` / `#5C6870` | 主/次文字（石墨，非纯黑） |
| 线 | `#2E6B8A` | 制图蓝：结构 / 边界 / **允许** |
| 拒 | `#A33A22` | 红铅笔：**拒绝**（只此一处用力） |

字体**只用系统字体栈**：等宽 `ui-monospace, "Cascadia Mono", "SF Mono", Consolas, monospace`（路径/hash/工具名/行号）；衬线 `"Iowan Old Style", Palatino, "Songti SC", "SimSun", Georgia, serif`（角色卡/留痕/长文）；系统无衬线**只**给 affordance（按钮/树标签）。

### 10.3 唯一用力处与各区域的画法

- **唯一用力处**：拒绝走一条**斜线阴影带**——`details.sys-denied` 用 `repeating-linear-gradient(45deg, rgba(163,58,34,.14) 0 1px, transparent 1px 9px)` 画**斜向排线**（是「线」，不是装饰性渐变洗色）；其余一切安静克制。
- **整页当一张图纸**：`body` 方格底纹贯穿三栏；三栏由**线**划分。
- **左树**：角色条目=标注过的字段；su 置顶，用**带边框的区域**标为「主入口」，其余归「其他角色」组。
- **中栏**：对话是一份**连续记录**（用户=右侧蓝调块 / 助手=衬线 + 左缘细线）；系统事件（`tool_call`/`accepted`）做成**图纸注记**（蓝线 + 对勾、等宽文字）；拒绝放进斜线带。
- **右栏**：边界条目**真的画出来**——每条一块：`root` 用**尺寸标注** `|— project —|`、`kind` 用**线型样片**（实线目录 / 虚线条件 / 细线文件）、允许条目**实线行**、条件目录**虚线行**。
- **输入区**：有横线的**填写栏**（textarea 只留上下横线，聚焦转制图蓝）。

### 10.4 硬约束（本方向下仍成立）

- **纯 CSS、零外部依赖（含不引外部字体）、无 emoji**；`repeating-linear-gradient` **只**画方格与拒绝斜线（画线），**不用装饰性渐变洗色**。
- **只动视觉层**：`app/renderer/{styles.css,index.html,renderer.js}` 的样式与呈现；`renderer.js` 里**判定的读取**（`primaryRoleId`/`hasRoles`/`readOnly`/`st.available`/`st.settled`/`res.config.*`/`res.wrote|pins|roles|reason`）**一个未动**，渲染侧仍**无第二份判定**。
- **响应式到窄窗、键盘 focus 可见、尊重 `prefers-reduced-motion`**。

> 实现与验证证据见 `角色卡/桌面应用/changelog.md` 顶部「2026-10-11 — 视觉重做：上一版『深色三栏 + 蓝色主色』被『图纸（drafting）』方向取代」。
