# 全项目工程法案（草稿）

本文件是全项目唯一的工程约束记录。**它是草稿**：只写本阶段**确凿**的事实与已经客户确认的要求；未确认项单独标注为「方案/待确认」，不混入已生效规则。

**本文件不扩张任何角色的文件权限。** 一个角色能改哪些文件，只看它自己 `boundary.md` 的 Section 1。法案只描述共同约束，不构成写入授权。

**缺失不等于阻塞**：本项目由 ANS Governance 从零 bootstrap，法案尚未定稿；技能规则明确"缺法案不阻止启动"。已授权的工作照常进行。

## 一、现状（确凿事实）

这些来自**已验收的角色定义与边界**，以及 `ans-governed-construction` 技能的全局规则。

1. **语言**：TypeScript。各角色边界列出的源码均为 `.ts`（如 `src/interface/cli/run.ts`、`src/service/gate/resolve-write.ts`、`src/provider/pi/session.ts`）。
2. **五层调用方向**：
   ```text
   Interface -> Pipeline -> Service -> Provider -> 外部基础设施
   Model: 由上面四个运行层共享
   ```
   - 只允许**相邻层**调用；不得向上、跳层或平级互调。
   - Interface 只调 Pipeline；不直接触达 Service / Provider。
   - Service / Provider 层内部三段式 `abstract/` / `public/` / `impl/`；上层只依赖 `abstract/` 与 `public/` 入口，不直接依赖 `impl/`。
3. **Model 共享**：共享类型、值对象与不变量由四个运行层共同引用，不属于调用链中的一环。
4. **固定角色隔离**：一个上下文从绑定到结束只承担一个角色，不能中途切换。跨角色工作必须用**独立上下文**。本次客户明确授权专属角色与并行开发，项目管理按技能 `group-leadership.md` 的 Without task_ops 路径核对每角色授权、文档、边界、依赖与写集冲突后启动 fresh worker。普通组员不自行调度同伴。没有客户 pin 的 `.ans/project.json` 时，不伪造 task_ops 配置/审批，也不手写 scheduling 机器日志。
5. **单一主属主**：共享抽象（Model 类型、公共入口、跨模块契约）只能有一个主属主角色，其他角色只读引用。本项目：
   - `src/model/boundary.ts`、`src/model/role.ts`、`src/model/decision.ts` 的主属主是**门禁引擎**。改动它们会让所有引用方的既有证据失效，须先经项目管理协调。
   - `src/common/shared/`（跨角色共享组件）的唯一写入者是**项目管理**。**现有共享组件**（登记于 `docs/architecture/shared-components.md`）：`config-loader.ts`（`.ans/project.json` 有效配置加载 + pin-backed acceptance 校验）、`path-primitives.ts`（跨角色路径原语，安全相关）、`runtime-shared.ts`（`RuntimeKind` / `PI_CREDENTIAL_ENV_VARS` / `resolveSkillRoot`）、`argv-primitives.ts`（argv 规范化 `normalizeArgv`——**编排**写审计与**桌面窗口**展示操作者所见须**同源**，否则审计的 argv ≠ 操作者看到的 argv）、`env-file.ts`（`.env` 读写模块——**逐行**只改相关键、**原子写**（temp+`rename`）、**凭据不回显**；`.env` 仍归**装配**，本模块是它的**指定写入者**（设计 §11，经 Governance 记档 **G-2**））、`atomic-write.ts`（跨角色共享**原子写**原语——同目录 temp + `fsync` + `rename` **覆盖目标**，并对 rename 的 **Windows 瞬时 `EPERM`**（实时防护/索引器短暂持有目标句柄）做**有界重试**（仅瞬时码 `EPERM`/`EBUSY`/`EACCES`、≤200 次（`RENAME_MAX_ATTEMPTS`，由实测尾部≈63 定）、次数间只 `setImmediate` 让出事件循环、非瞬时立即抛）；抽自 `env-file.ts` 与 **Pi适配器** `fs-write.ts` 两处**同源**写法，消除该处 §6 镜像）。**消费方更新规则**：消费方（**装配**、**桌面窗口**、**编排**、**Pi适配器**、**门禁引擎**）**只读导入**该等模块，**不得复制第二份实现**；组件增删由 pm 在 `docs/architecture/shared-components.md` 登记。**加载器逻辑须单一实现**——已由 `src/common/装配/config-loader.ts` **整体搬迁**至 `src/common/shared/config-loader.ts`（T11，**搬迁非 fork**，逐字等价）；装配侧的本地副本须由 **T12** 改为从共享模块导入并**删除**。在 T12 完成前存在一段**过渡性「两处并存窗口」**（两份代码**逐字相同、行为不分叉**）；此窗口是搬迁的中间态，**不**构成对「不得复制第二份实现」的长期许可。**argv-primitives 消费方动作**：**编排**（`src/common/编排/shell-gate.ts`，**写审计侧**）与**桌面窗口**（`app/desktop/operator-channel.ts`，**呈现操作者侧**）各自删去本地 `normalizeArgv`、改从 `src/common/shared/argv-primitives.ts` 导入（**T21 / T22**）；二者完成前同样处于**过渡性「两处并存窗口」**（两份**逐字相同、行为不分叉**）。
6. **`common/` 是支撑目录，不是第六层**：
   - 每个角色拥有私有 `common/<role-id>/`，可在已批准任务内增删内部文件，不必逐文件改边界；不得导入其他角色的私有 `common/`。
   - 跨角色共享走项目管理的 `common/shared/`。
   - `common/` 不得反向调用运行层；共享代码不得依赖某个角色的私有 `common/`。
7. **未列即只读**：不在某角色 `boundary.md` Section 1 中列出、也不落在已授权目录内的文件，默认只读。要修改须先由 ANS Governance 更新 Section 1 并经客户确认。
8. **构建与配置归属**：`src/index.ts`、`bin/ans.js`、`package.json`、`tsconfig.json`、`README.md` 归**装配**角色；其他角色不修改构建配置。

### 命名现状（如实记录，不是新规则）

技能 `references/architecture.md` 的示例树用复数层名（`models/`、`services/`、`providers/`、`pipelines/`）；本项目已验收边界用单数：`src/model/`、`src/service/`、`src/provider/`、`src/pipeline/`、`src/interface/`。职责不变，仅词形不同，以本项目实际路径为准。

## 二、已确认要求（来自技能全局规则）

1. **编辑只限允许的文件**：文件必须在本任务写入范围内，否则先申请范围变更。
2. **遵守层规则**：代码只能调用本层与已约定公共接口允许的能力。
3. **补丁不等于完成**：先跑所需的结构检查与行为测试。
4. **测试只证明它实际跑过的**：记录代码版本、环境、输入与所用规则。
5. **改动依赖后重测调用方**：受影响代码的旧结果不再当前有效。
6. **不得把失败伪装成成功**：不得为让测试通过而删测试、放松断言、放宽权限或隐藏错误。
7. **业务代码需在客户确认文档并授意实施后再改**：设计文档先写拟采用方案。
8. **文档区分"未实施 / 未测试 / 未部署"**三个状态，不把计划写成结果；未确认内容标为候选。
9. **验收先判风险档位**：运营调度必须在交给独立验收的变更包中标注风险档位 **T0–T3**，档位定义以技能 `references/testing.md` 的「Risk-Based Verification and Change Packages」为唯一口径，不得为省检查而压低档位。**独立验收必须先核对档位与改动是否相符并记录，再决定证据与检查**；档位与改动不符时，退回运营，或按更高档位补证。检查强度：**T0 只查文档；T1 只跑受影响单测；T2 补受影响集成检查；全量回归只在 T3（发布、共享抽象、治理或权限变更）或证据不足时执行**；其余档位只做受影响检查，并复用未受影响且仍有效的证据。验收报告首行必须写明：**风险档位、判定依据、选定检查、复用证据、全量回归理由**（未执行全量回归时写明 N/A 理由）。**本规则不扩张任何角色的文件写权。**
10. **打印/日志-01：代码/文档工作在必要处添加打印/日志**（客户 **2026-10-23 确认，立即生效**）：
    - **范围**：本项目全部角色的代码、测试、脚本，以及生成/校验/迁移/复算类文档工作；自本条生效起适用于当前正在进行的角色根文档展示实现及后续全部变更；不追溯要求重写未受影响的历史代码。
    - **要求**：在必要处添加打印/日志，便于运行观察与排障。不要求每行、每个函数或热循环逐项刷屏；不得打印密钥、令牌、真实 `.env` 内容或个人敏感信息；不得用日志伪造成功、掩盖失败或代替测试证据；日志不得改变控制流或业务结果。
    - **正确办法**：
      - **代码**：优先使用项目既有诊断设施（`src/common/shared/diagnostics.ts` 的 `createDiagnosticLogger`，以及既有 `log.record` / `log.error` 写法）或既有 CLI/用户可见输出，不另起日志框架、不新增依赖；在入口/出口、状态迁移、外部 I/O、失败/重试/跳过、批处理开始/结束与跳过原因、证据写入、配置来源选择等必要处记录；热循环按聚合/摘要记录，不逐项刷屏；用户可见输出与诊断日志分开，诊断日志沿用既有字段白名单与净化，不写入命令原文、prompt/源内容等正文。
      - **文档/脚本**：生成、校验、迁移、复算脚本在关键步骤打印命令、输入、输出路径、退出码/计数与证据位置；变更/验收记录引用真实输出，不把摘要当原始证据。
    - **检查方式**：代码审查/差异检查核对必要日志是否存在，且无秘密、无噪声、无伪造；运行受影响脚本/测试，确认输出可复现；行为相关处可在测试中断言日志；不以噪声日志冒充可观察性。
11. **独立验收-01：所有变更默认独立验收**（客户 **2026-10-24 确认，立即生效**；取代此前“独立验收仅随发布版本启动、非发布不派”的口径）：
    - **范围**：**T0–T3 的代码/文档/测试变更**——**包括非发布变更、修复与演示**——在 change-package 与证据齐备后，由应用按验收门**自动派发 Proof/独立验收**（含验收标准/报告与验收卡）；**发布版本只是其中一种变更，不是启动独立验收的条件**。
    - **`release` 标记**：`release` 仅为**发布元数据**，**不再作为独立验收门**；非发布 flow/变更**不得停在 `awaiting-release-acceptance`**，满足流程完成与证据条件即进入独立验收。
    - **独立性不变**：Proof/独立验收独立于实施方，**不自动 accept/reject、不代批、不伪造证据**；**客户保留最终决定权**。
    - **检查强度**：仍按**第 9 条风险档位**执行——T0 只查文档、T1 只跑受影响单测、T2 补受影响集成检查、全量回归只在 T3 或证据不足时执行；本条不改变第 9 条任何内容。
    - **本规则不扩张任何角色的文件写权。**
12. **gate 复核-01：关键节点 gate 复核独立于最终验收**（客户 **2026-10-26 授权实施**；设计 `docs/design/2026-10-26_design_proof-gate-reviews.md` §5–§8、§12）：
    - **独立性**：gate 复核由 质检/Proof独立判定；运营只做证据完整性检查、请求 gate 复核与返工协调，不得自查代替 Proof、不得代标 gate 通过、不得写 gate 报告。**gate 复核 ≠ 验收通过 ≠ 客户批准**：gate 结论不写 `customer.decision`、不进入验收分诊；最终验收仍按第 9、11 条与既有验收卡链路执行。
    - **防吹毛求疵**：gate `fail` 必须有 `blocker`/`major` 依据；只有 `minor`/`nit` 的 `fail` 按结构不符**退回 Proof、不触发返工**；gate `pass` 可带 `minor`/`nit` 备注，不因非阻断建议反复开 gate。
    - **范围**：不新增治理角色、不新增 `FlowStepKind`、不新增 cardKind；`request_gate_review` 只注入运营会话，`request_acceptance` 保留为最终验收唯一主动通道；无 gate 的旧 flow 行为不变。
    - **本规则不扩张任何角色的文件写权。**
13. **决策卡-01：材料性选择必须发 decision 卡，推荐项唯一，与验收分离**（客户 **2026-10-26 新规则**；规则登记见 `docs/design/2026-10-26_design_decision-card.md`）：
    - **主体与通道**：产品（Lead/liaison）发现**材料性选择**（会影响目标、范围、方案取舍或客户可感知结果的选项）时**不得自定**，须交运营（Steward/Convener）以 `request_choice(cardKind="decision")` 向客户发**决策卡**。decision 卡是独立卡种，不属于提案接受、任命或验收。
    - **推荐项唯一**：每张 decision 卡**恰好一个推荐项**；推荐项是建议，不是客户决定，也不替客户选择。
    - **默认代批**：「替我决策」开启时，判断 agent（judge）**默认选择唯一推荐项**，不得自行发明选项或改动推荐；代批结果行必须标明 `judge 代批 · 代决策（自动代理）`，**不得写成客户本人**。开关关闭、判断不可用或判断结果不符合唯一推荐项时，交客户手动选择（fail-closed）。
    - **与验收分离**：decision 卡**不是客户批准、不等于验收通过、不是 gate**；选择结果仅记录材料性选择，**不作为验收/提案/任命决定记账**（应用按 `decisionKind="material-choice"` 单独审计留痕，门禁/收尾/分诊不读它），**不触发 gate 复核、不触发或替代验收**；最终验收与客户批准仍按第 9、11、12 条及既有验收卡链路执行。
    - **结构 fail-closed**：缺少唯一推荐项、参数非法或卡种不属于允许范围时，**不得向客户发卡**；发起方与应用应如实回执并修正后重试，不得伪造推荐项或代选。
    - **范围说明**：本条不新增治理角色、不新增 `FlowStepKind`；decision 卡以 `cardKind="decision"` 实现（在飞实现已登记），由模型/编排/桌面/门禁卡属主实施并各自验收；本规则不替代实施授权与验证。第 12 条的「不新增 cardKind」仅约束 gate 复核范围，**不适用于本条**。
    - **本规则不扩张任何角色的文件写权。**
14. **图片证据-01：角色可查看项目内图片证据（`view_image`），同轮工具结果附图优先、下一轮附件回退**（客户 **2026-10-27** 明确要求「同轮看图修复」并已选择安排修复；设计见 `角色卡/编排/docs/design/2026-10-27_design_view-image-same-turn.md`；规则登记见 `docs/change/2026-10-27_change_view-image-same-turn.md`）：
    - **能力**：角色可通过 `view_image` 读取**项目内**图片（截图、设计稿、图表等）作为查看证据；工具只读，不写文件、不执行命令、不读取项目外路径。
    - **同轮优先**：支持同轮交付的引擎把图片作为**本轮工具结果的图片内容**送回同一模型轮次，模型在本工具调用后的下一次模型调用中即可直接查看并判断；同轮模式**不产生**队列项、系统行或伪装成客户消息的用户消息。工具结果文本须写明图片已随本工具结果附上（同一轮可见），并要求模型在上下文未包含图片时明确说明未看到，不得假装已看到。
    - **逐引擎 policy**：同轮/回退由运行时核心的**逐引擎策略**（单一来源）决定，不在工具层写引擎分支；初始落地四个运行时全部先按 `next-turn`，每个引擎完成适配器映射与**真实端到端探针证据**后才翻为 `tool-result`。Pi 先行（SDK 类型与 agent loop 已核实，图像管线待探针）；Claude（MCP/Anthropic 规范支持）与 Codex（本机 0.162.1 schema 已含 `inputImage`）在真实探针通过前保持 `next-turn`；demo/未知运行时保持 `next-turn`；探针失败即保持或回退 `next-turn`。
    - **回退附件**：未启用同轮或探针失败的引擎，图片排队为**下一轮用户提示的图片附件**送达**同一角色**；本轮工具结果只确认「已读取并排队（下一轮以附件提供）」，模型**不得假装本轮已看到**。同一角色同一轮多次调用合并为**一条**系统投递（`background:true` + `kind:"system"`，不冒充客户消息、不抢活动角色），轮末送达；跨轮不合并。
    - **fail-closed**：路径不在项目内（绝对路径、`..` 逃逸、符号链接、非普通文件）、真实类型不受支持（扩展名/声明类型不作数）、超过大小或每轮预算上限、读取/排队/投递失败、能力回执与 policy 不一致时，工具**如实返回失败且不提供图片**；不得返回占位/伪造内容，不得部分交付或部分排队；失败/中止/未映射不得出现「已看到」的肯定表述。
    - **审计**：工具只记录结构化事实（项目相对路径、MIME、字节数、交付方式、原因码等）；**图片字节、base64、`data:` URL 不得进入**日志、诊断、事件或 ANS 回放；原生会话历史可能因附图变大，如实登记。
    - **注册条件**：图片查看能力未注入时**不注册**该工具（不提供假装可用的壳）；能力注入由装配/运行时属主按各自边界接线。
    - **范围**：不新增角色、不新增 `FlowStepKind`、不新增 cardKind；`view_image` 是运行时公共工具，不改变任何角色的文件写权；实现、接线与验证由对应属主负责并各自验收，本规则不替代实施授权与验证；本条**不声称同轮看图已实现或已验证**（截至修订时实现仍为两轮附件）。
    - **本规则不扩张任何角色的文件写权。**
15. **需求变更-01：提案新授权必须走 `request_requirement_change` + 独立审批（decision 卡）+ 产品执行**（客户要求；审批主体经客户 2026-10-26 多次纠正，以最近一次为准；规则登记见 `docs/change/2026-10-26_change_requirement-change-request.md`）：
    - **通道**：策划 / Draft 在提案阶段发现需要**新授权或新范围**（超出已确认意图/提案授权）时，**不得把新授权写进提案卡或提案正文**；必须调用 `request_requirement_change` 提交需求变更申请（带 `flowId`、`intentId`、变更内容与理由）。**申请 ≠ 批准**。需求变更申请由**运营或策划角色**发起（两者都可以，其他角色不可）。
    - **发起方（运营或提案，其他角色不可）**：需求变更申请由**运营或策划角色**发起（两者都可以发起，不限定仅其中一方），审批卡由应用在申请成功后自动经发起方会话的客户卡通道呈现（发起方不得再调用 `request_choice` 重复发卡）；**其他角色不得发起或持有**；**发起方不得自批**。
    - **独立审批（decision 卡，非产品）**：审批由**开启「替我决策」时的独立判断 agent** 默认选择唯一推荐项（代批结果必须标明 `judge 代批 · 代决策（自动代理）`，不得写成客户本人），或由**未开启「替我决策」时的客户**在 decision 卡上手动完成；判断不可用或结果不符合唯一推荐项时转客户手选（fail-closed）。**产品不审批、不代选**。
    - **产品只执行**：仅当独立审批通过后，产品才按**批准范围**更新 `docs/intents/<flowId>.md` 意图（goal/scope/acceptance 与客户原话），并通知 Draft 修订提案；不得扩大批准范围。申请提交、审批卡已发、产品执行意图变更都不等于客户批准或已获其他授权，不得据此解锁其他门禁。
    - **修订时机**：仅当独立审批通过且产品完成意图变更后，策划 / Draft 才可依据已确认意图修订提案；修订仍走既有提案卡（`cardKind=proposal`）与 gate 1，不得跳过提案卡。
    - **提案卡禁令**：提案卡/提案正文不得承载未获批准的新授权；申请与审批结果不得被表述为客户本人批准。
    - **不得绕过 gate 0**：不得通过删除、改写或拆分需求来规避 gate 0；申请、独立审批记录与意图变更记录缺一不可。
    - **范围**：不新增治理角色、不新增 `FlowStepKind`、不新增 cardKind——decision 卡是既有卡种；`request_requirement_change` 只作为申请通道，不改变任何角色的文件写权、不代替客户决定与独立验收；实现、接线与验证由对应属主负责并各自验收，本规则不替代实施授权与验证。
    - **本规则不扩张任何角色的文件写权。**
16. **确认问题卡片化-01：需要客户确认/选择的问题必须弹卡，不得在聊天里口头问**（客户新规则，2026-10-27 转达；规则登记见 `docs/change/2026-10-27_change_customer-confirmation-cards.md`）：
    - **通道映射**：确认/取消用 `request_confirmation`；单选题/多选题/decision 用 `request_choice`（decision 卡沿用第 13 条）。任何需要客户确认或选择的问题**必须**以对应卡片呈现；**不得**用普通聊天消息、系统行、工具文本或其他非卡通道要求客户回答；**不得**把沉默、默认值、超时、未勾选或「没有反对」当作客户确认或选择。
    - **「替我审批」与确认卡（按现状）**：shell 命令确认与 `request_confirmation` 的写盘/写卡确认（如 `write` / `appointment-write` / `schedule-write`）受「替我审批」开关控制——开关关闭或无判断上下文时由**客户本人**在卡上作答；开关开启且判断可用时由判断 agent 代批（`allow` ⇒ 放行；`deny` ⇒ 拒绝并带理由；manual / 不可用 / 超时 / 解析失败 / 结果行投达失败 ⇒ 按现状**拒绝**，fail-closed，不默认放行、不回落为客户手批）。
    - **「替我决策」与选择/decision 卡（按现状）**：单选题、多选题与 decision 卡受「替我决策」开关控制——开关开启且卡片带**已定格的推荐项**时，判断 agent **仅按卡片推荐项**代选（decision 卡恰为一个唯一推荐项）；不得自造选项、改写选项或推荐项、选非推荐项；开关关闭、无推荐项、判断不可用或结果不符合推荐项时回落**客户本人**在卡上选择（fail-closed）。**两个开关互相独立**：不得合并、不得互相顶替，也不得用一个开关的状态推断另一个；若要合并须另立规则。
    - **材料缺口先发卡**：产品（主理）或运营（统筹）发现未决的**材料性缺口**（影响目标、范围、方案取舍或客户可感知结果，如验收范围或方案取舍）时，**必须**在进入依赖该决定的步骤**之前**发 decision 卡（第 13 条），不得自行决定、不得按默认值推进；**没有卡或卡未决时不得推进依赖步骤**。
    - **`report_artifact_ready` 不是客户卡**：该工具是角色向**应用**汇报工件就绪（如质检的验收标准落盘），由应用校验并决定是否收口；它**不向客户提问，不构成客户确认、选择或批准**；不得用它替代确认卡/decision 卡，也不得因汇报成功而绕过依赖步骤的未决卡。
    - **范围**：不新增角色、不新增 `FlowStepKind`、不新增 cardKind；不改动产品/工具/桌面/运行时/编排代码与 i18n；本条只固化客户沟通通道与两个开关的**现状**，不改变应用行为；本条不替代实施授权与验证。
    - **本规则不扩张任何角色的文件写权。**
17. **验收证据-01：验收标准最多截图、不得要求录屏**（客户 **2026-10-27** 新规则，适用 ANS 系统本身而非 demo；规则登记见 `docs/change/2026-10-27_change_acceptance-screenshot-only.md`）：
    - **适用范围**：策划（提案/Draft）的提案与验收标准、质检（验收/Proof）的 gate 复核与验收标准，以及**任何依赖证据的步骤**，均**不得**把录屏列为必需项、可选项或 decision 卡选项；不得以「需要录屏」阻塞、退回或要求补充。
    - **证据上限**：需要视觉证据时，**最多**使用**真实运行截图**（UI/游戏截图须关闭 DEBUG 覆盖层，并随附 sha256、候选清单、命令等；日志/输出/哈希可作辅助）。截图是证据形式的**上限**；既有要求截图的场景照旧，本条不新增录屏要求，也不因缺少录屏而补充或升级证据要求。
    - **缺录屏不构成失败**：任何步骤**不得**因缺少录屏判 `fail`、`insufficient evidence` 或等价结论，也不得以「未提供录屏」为由退回或要求返工；证据是否充分按既有验收标准与风险档位判断（第 9 条）。
    - **不得作为材料缺口/decision 卡**：**不得**把「截图 vs 录屏」作为材料性缺口示例，也不得为此发 decision 卡（第 13、16 条）。如客户未来另行明确要求录屏，属**独立需求变更**（第 15 条 `request_requirement_change` + 独立审批），不写入默认验收标准，也不改变本条。
    - **范围**：不新增角色、`FlowStepKind`、cardKind 或权限；不改动产品/工具/桌面/运行时/编排/i18n/角色卡；本条只登记验收证据口径，不改变应用行为，不替代实施授权与验证。
    - **本规则不扩张任何角色的文件写权。**
