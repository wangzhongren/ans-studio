# 受治理交互与聊天体验：设计稿（草稿）

> **状态：草稿，未实施、未验证。** 客户确认本稿并授意实施后才动代码；实施按角色派工。
> 本文覆盖**四条客户需求**，分两组：**A 组（治理交互）**与 **B 组（聊天体验）**。

## 一、客户原话与拆解

### L-1 每角色任务队列（归属：编排 + 桌面应用；投递机已具备排队，本轮补「可见性 + 客户入队 + 回执如实」）

- **语义**：每个角色**至多一个在跑的任务**；其余**按到达顺序排队**。派发（su）、回交投递、**客户手动消息**共用**同一条队列**（单一通道，不造第二套）。
- **回执如实**：`dispatch_task` 受理回执要写明**是否入队与队列位置**（如「已受理：目标忙，已入队（第 2 位）」）；**受理 ≠ 完成**（既有措辞保留）。
- **可见性（桌面）**：① 左树角色徽标在「工作中」之外可显示待办数（如 `工作中 · 2 待办`）；② 该角色会话流里给一条**队列行**（「【队列】N 条待办：<一句摘要>…」），队列变化时更新，**不得**把排队中的任务内容当已执行呈现。
- **客户手动消息**：目标角色忙时**入队**（而不是 SDK 层 "already processing" 报错/丢弃）；入队时界面**如实**提示（如「已入队，待其完成当前任务后处理」）。
- **失败与边界**：投递失败 → 如实 + 放回队首（既有）；**不做**跨角色的优先级/抢占（本轮不做，登记待议）。

### K-1/K-2 输入框改版与图片发送（归属：桌面应用 + Pi适配器；K-2 需先核实模型侧能力）

- **K-1（桌面）**：输入框改**圆角胶囊**、发送键**内嵌**在框内（右侧箭头）；保持既有快捷键（Enter 发送 / Shift+Enter 换行）与「等待你确认」等状态提示位；样式落 `styles.css`，结构落 `index.html` + `renderer.js`。
- **K-2（需先核实）**：
  1. **Pi适配器核实**（只读，先做）：`pi-coding-agent`/`pi-ai` 的会话 API 是否接受**图片内容块**（如 `{type:"image", source:{type:"base64", …}}`）？给 SDK 产物证据；若只接受纯文本，说明缺什么、能否透传 content blocks。
  2. **桌面**：选图（文件选择器）/粘贴/拖入 → 渲染进程**不碰文件**，经 preload 白名单 IPC 把**数据**交主进程 → 主进程组装图片块交会话；**尺寸/类型上限**（如 ≤5MB、png/jpeg/webp/gif）与**失败如实提示**；渲染侧缩略图预览 + 可移除。
  3. **诚实边界**：**网关模型是否多模态未知**——若模型不接受图片，必须在发送前/失败时**如实提示**（不得假装已识别图片）；图片随会话落盘（D-1）的体积影响**如实登记**，必要时设上限或不计入转录。
  4. **治理无涉**：图片是**用户输入**，不经写门禁、不改变任何边界语义（在文档中写明，避免误读为"可绕过写闸"）。

### I-1 开放 shell（客户裁定 2026-10-12：启用 V1 未接线的三层链）

**链路（既有实现，本次接线并 arm）**：`run_shell` 工具 →（c）**确定性硬地板**（既有 `classify-shell`，明显危险/写类直接拒）→（b）**su 模型审读**（既有 `pm-reviewer` 即治理角色审读；su 判「危险」→ 升级）→（a）**操作者确认**（桌面既有「看命令原文、放行/拒绝」框；关窗/不答 = 不放行，fail-closed）→ 执行（cwd 钉项目根；spawn 时**剥离凭据环境变量**）。
**已知与接受的边界（如实登记）**：V1 **无 OS 沙箱**——被放行的命令其文件写入**绕过写门禁**（靠 (c) 硬地板 + su 审读守卫）；命令逐条留痕（审计）。
**范围**：`run_shell` 只在会话构造路径注入 `ShellGate` 时注册（既有语义）——本次由**编排**装配该闸（(c)+(b) 用既件）、**桌面** arm（`DESKTOP_SHELL_GATE_ARMED` 置真 + 既有确认框接线）。su 自身会话是否 arm 由实现方按同一规则处理（默认同规则）。

### H-1 su 派发任务（归属：Pi适配器 + 编排 + 桌面应用；V1「派发执行不在范围」的**最小闭合**）

**工具**：`dispatch_task{ roleId: string, task: string, reason?: string }` —— 注入才注册（同交互工具先例），**只给治理角色 su**。
**语义硬约束**：**派发 ≠ 授权**——写权仍只来自目标角色自己的 Section 1 与 `request_confirmation` 的 `confirmed:true`；派发只是把「任务与上下文」送过去（沿用 SKILL 的交接语义：转移任务与证据，不转移身份或写权）。
**前端路由（桌面，复用 E-1 那套）**：把派发转成目标角色会话的一条输入（模板：「[派发] 来自 su 的任务：…（原因：…）——完成后请交回报告」）；目标角色**未开会话 → 自动开**；**忙 → 排队**；**失败/超时 → 如实提示 + 保留待重投**；**一条派发只投一次**（去重键复用 `handbackKey` 形态）。
**闭环**：角色完成 → 回交（E-1 自动投递回 su）→ su 验收 → 需要返工则**再 dispatch**（要求与证据随任务文本带走）。
**校验与失败语义**：`roleId` 非本项目角色（或指向 su 自身）→ 工具**如实返回错误**（不静默、不猜测）；目标角色无可用会话且开不起来 → 如实告知 su 并保留。
**CLI**：一次性前端不做同等路由（登记）。
**测试锚点**：工具注册/参数校验/文案；路由（自动开、排队、失败保留）；去重；闭环（su 派发 → 角色回交 → su 收到报告）。

### G-1 客户确认不设超时（归属：Pi适配器 + 编排 + 桌面应用）

**客户裁定（2026-10-12）**：交互工具的等待**不超时**——一直等客户同意/拒绝。

- **Pi适配器**：① 去掉 `ANS_PI_CUSTOMER_INPUT_TIMEOUT_MS` 的缺省等待上限（保留该配置为**显式**可用：仅当客户显式配置才计时）；② **每轮硬超时（prompt timeout）在客户输入挂起期间不得掐断该轮**——等待期间暂停/续期该轮时限，作答后恢复正常计时（否则 120 秒默认值仍会把"等你点头"的轮次杀掉）；③ 等待期间会话 = **忙**（不并发 send）。
- **编排**：CLI 通道语义同步——终端问答**不设超时**；EOF（无人值守）仍 → `unavailable` → 不完成、零副作用（fail-closed 不变）。
- **桌面**：卡片**不再按时间过期**（去掉"超时定格"路径；`expired` 仅保留给**应用关闭/重启导致请求消失**这类真实失效场景，文案如实）；等待期间该角色状态 = 「等待你确认」（B-3），未查看时在当前会话给指针（已实现）。
- **诚实边界（必登记）**：未决请求**只在进程内存**——应用关闭/崩溃即消失，恢复后**不会**有半截的"已同意"；模型那一轮也随之结束（D-1 恢复的是会话历史，不是未决工具调用）。此类失效文案必须如实（"请求已失效，未获同意"），不得假装成功。
- **测试锚点**：等待不超时（模拟长时间后作答仍生效）；客户输入挂起期间 prompt 时限**不**掐断该轮；应用关闭后的失效文案；CLI EOF 的 unavailable 不变。

### E-1 回交后的 su 验收（归属：编排 + 桌面应用）

**现状**：回交只做「事件 + 界面呈现」——卡片镜像进 su 的会话流**给客户看**，su 本身**不被触发**（不验收、不汇总）。

**设计**：把回交**投递进 su 的会话**作为一条输入（一条结构化消息，含 `来自 <角色> / 任务 / 结论 / 摘要 / 证据`），并**明示请 su 验收**（确认通过 / 要求返工 / 上报客户）。su 的回复自然落在其会话流里（已 Markdown 渲染），必要时可用既有交互工具向客户取证后再裁决。

**触发方式（客户裁定 2026-10-12：全自动，不做开关）**：
- 回交到达即**自动投递**给 su 验收（无开关）。
- su 的会话**未开**时：**自动开启 su 会话**再投递（su 是治理主入口，验收是其职责）；开启失败/投递失败/超时**如实提示**，不静默丢。

**忙时与失败语义**：su 会话可能正忙（B-2 下多会话并存）⇒ 投递须**排队**并按序处理；投递失败/超时要**如实提示**（绝不静默丢）。一条回交只投递一次（去重），避免重放刷屏。

**选装**：**O-E1**——让 su 以**结构化方式**记录验收结论（如经既有交互工具/新工具写明 `accepted|rework|escalate` 与理由），便于后续汇总与审计；不加则验收结论只体现为 su 的自然语言回复。

**测试锚点**：回交生成一条 su 会话输入（含报告字段、去重）；自动/开关的行为；su 忙时排队与失败提示；手工触发路径（若采纳 b/c）。

### D-1 重启恢复（归属：Pi适配器 + 编排 + 桌面应用；可行性已核实）

**可行性（Pi适配器只读核实，证据为 SDK 产物）**：`SessionManager.create(cwd, sessionDir?)` / `open(path)` / `continueRecent(cwd)` / `findById` / `findMostRecentSession`；落盘 JSONL（首行 header，其余每行一 entry），含**完整消息史**（含工具调用与结果）、压缩记录、branch_summary、model/thinking 变更；恢复＝`createAgentSession({ sessionManager: SessionManager.open(path) })`，构造时按投影恢复 `state.messages` 并从转录恢复工具装载。

- **存储位置（需客户拍板）**：
  - **(a) 项目内自持（推荐）**：把 session 目录指到**项目内**（如 `<project>/.ans/sessions/`）——符合本仓「**环境封闭**」纪律（适配器刻意不读写 `~/.pi`），会话随项目走、可随项目清理。
  - (b) Pi 原生默认（`~/.pi/agent/sessions/<编码 cwd>/`）：跨项目集中，但**违反既有纪律**，需同时改适配器头部对「环境封闭」的登记。
- **恢复流程**：前端启动 → 对每个角色解析其最近会话（自持目录内的最近文件 / 或 `findById`）→ `open(path)` → 交给 `createAgentSession`；**界面记录**由我们只读回放该会话的持久 entry 重建（渲染为「历史」段，与实时事件同构）。
- **一致性坑（必须守）**：恢复时的 `SettingsManager`/`resourceLoader`/工具集必须与首启一致（我们现为固定 in-memory settings，满足）；**能力集变化**（如注入的 customerInput/reportHandback 增减）会让转录里声明过、但本次未注册的工具保持 pending —— 如实登记，并在界面上给出提示而非静默。
- **上限**：每角色保留最近 N 个会话（建议 5），旧的归档/清理策略随 (a) 的目录一起定。
- **验证**：单测（SessionManager 接线、entry 往返、恢复后 messages 非空）+ 桌面测试（同一 sessionDir 下"新实例恢复"）+ **真机端到端属客户跑**（关掉应用重开，记录与上下文都还在）。

### C-1 交报告工具（归属：Pi适配器 + 编排 + 桌面应用；客户裁定「新增交报告工具」）

- **工具**：`submit_report{ status: "completed" | "blocked", summary: string, evidence?: string[] }`——`summary` 是**模型自己写的、改了什么**；`evidence` 是产物路径 / 变更 / 测试结论。**注入才注册**（新能力 `reportHandback`，同交互工具先例）；**只给项目角色**（治理角色 su 不自我回交，故不给它）。
- **文案**：`description` + `promptGuidelines` 写死「本轮任务完成（或确认无法完成）时**必须**调用本工具交回报告：一句话结论 + 改了哪些文件/产出了什么 + 关键证据」。
- **编排**：项目角色会话注入该能力；**模型交的报告即回交事件的内容**（`TaskHandback` 的 `summary`/`evidence`/`status` 取报告值）；**未调用则回退既有推导**（不硬失败）。既有推导同时**修一个噪音缺陷**：`evidence` 应只取**被接受的写类事件**（文件路径），不再混入 `read_file` 之类的读事件。
- **桌面**：回交卡按 `角色 / 任务 / 结论 / 摘要 / 证据` 呈现（证据逐条列出）；沿用既有镜像（回交卡进 su 会话流）。
- **测试锚点**：交报告后手事件内容=报告值；不交则回退推导；`evidence` 不含读事件；卡片渲染断言。

## 三、A 组设计：客户确认制交互

### A-1 工具族（归属：Pi适配器）

**一族两工具**（优于单工具 + kind 枚举：描述更聚焦、模型更易照做）：

```jsonc
// request_confirmation —— 请求客户确认（可带预览）
{ "title": "…", "preview": "…markdown…", "detail": "…" }
// request_choice —— 请求客户选择（单选/多选，可带预览）
{ "title": "…", "question": "…",
  "options": [{ "id": "…", "label": "…", "description": "…" }],
  "multiple": false, "preview": "…markdown…" }
```

**返回给模型**（新冻结类型，因勾选结果装不进现有 `OperatorOutcome`）：

```ts
{ outcome: "answered", value: { confirmed?: boolean; selected?: string[] } }
| { outcome: "declined" }     // 客户拒绝
| { outcome: "unavailable" }  // 通道不可用 / 超时 / 出错
```

- **注册**：`options.customerInput` 注入即注册（取代 `finalizeBootstrap` 那个槽；先例 `tools.ts:545`、`:599-605`），判据从「创世态」改为「**有客户通道**」。
- **纪律**：工具 handler **只调用注入的 fn**，不写盘、不做治理判定；**不进** `GOVERNED_WRITE_TOOLS`（无 path、无写，加了等于没加——同 `run_shell` 的理由）；`shellKillSwitch` 不动。
- **失败文案**（绝不说成已同意）：`未获客户同意（原因：…）→ 不要写盘；如实告知客户，不得假设同意`（措辞先例 `tools.ts:552-576`）。

### A-2 模型行为文案（归属：Pi适配器 + 门禁引擎）

- 工具 `description` + `promptGuidelines`（仅工具激活时进系统提示，SDK `types.d.ts:455-456`）写死流程：**调用任何写盘工具前，必须先经本工具取得 `confirmed:true`；未获同意/超时/通道不可用 → 不写盘、如实告知**。
- **su 的角色卡同步此流程**（`src/service/role/resolve-role.ts` 的内置 su 卡文本，属门禁引擎）。

### A-3 「同意才落盘」落在哪一层（归属：编排，复用 F4）

不造票据机制（**票据已废**、可重算者只是装饰）。做法：

1. 客户在预览卡上**确认**后，工具返回 `confirmed:true`；
2. 编排把「**已预览且校验在创世种子边界内的具体路径**」发行进**本次会话的 writeSet**；
3. 写入照旧经 gate；**F4 拒掉一切未确认路径**（`resolve-write.ts:135`）。

**已知残留 —— 内容漂移**：预览的是 A 内容、写出的却是 B 内容，本方案**关不住**。
- 选装 **O-A1（默认推荐）**：确认时在工具层存 `(path, content)`，写盘时比对内容哈希，不一致即拒。代价：一处比对 + 两处存储；收益：把"预览即所写"做实。

### A-4 删「收口」（A3，归属：编排 + 桌面 + Pi适配器）

**删「提议 + 确认」，保留「自动收尾」**：

- 删：`finalize_bootstrap` 工具的提议-确认半（其「挂起等确认」职责由 A-1 工具族取代）；CLI 的收口确认面（`src/interface/cli/govern.ts:113` 的 arm）；桌面的收口卡与「完成 bootstrap」入口。
- 留：**客户同意后，代码自动收尾** —— 写 `.ans`(pin) + `角色卡/governance-boundary.yaml` + `docs/bootstrap-manifest.md`（`finalize.ts` 的写入本体保留，`repinIfBootstrapped` 扩为含首次）。
- **为什么保留自动收尾**：① pin 与「项目正式态」的既有语义（`config-loader` 终态规则、桌面 `hasRoles` 过渡）不破；② **创世授权自终止**仍成立（治理边界文档写出 ⇒ `gov.path` 非空 ⇒ 先于创世分支）。
- **若不保留**（即连 `.ans` 也不写）：项目**永远停在创世态**，`ans govern <目录>` 每次重新拿创世授权、永不终止 —— **不推荐**。

**删除顺序（下游先、本层后）**：编排 `govern-session.ts`/`finalize.ts`/`govern.ts` → 桌面（卡、IPC、preload、interface/session 面）→ 最后删 Pi适配器侧 `session.ts:109-135` 的 finalize 三型（否则编译断）。

### A-5 桌面与 CLI 的呈现（归属：桌面应用）

- **通用交互卡** `appendOperatorRequest`（复用现有卡壳）：`kind: confirm | select | multi | preview`；预览用 `details` 折叠 + `max-height:40vh; overflow:auto`；选择用 radio/checkbox + 提交；提交后定格。
- **通道泛化**：`session:operator-request`（主→渲）/ `session:operator-response`（渲→主），沿用 `toolCallId` + pending Map 模式；主进程按请求快照校验回包（选项 id 必须是被给的子集）。
- **fail-closed**：窗关 → deny；超时 → unavailable；拒绝/缺字段 → deny。「不落盘」由工具 + 门禁上游保证，桌面只保证**绝不悄悄放行**。
- **CLI 映射**：单选 `1`；多选 `1,3`；空/未识别 = 拒；EOF → unavailable → 不完成、零副作用（**注意**：readline 挂 stdin 会拖住进程——既有教训）。

### A-6 并发与超时（归属：Pi适配器）

- Pi 默认**同批并行**执行工具（`pi-agent-core agent.js:145`）⇒ 同批 `write_file` 可能抢跑于确认 ⇒ 交互工具须设 `executionMode:"sequential"`（SDK 有此能力，**未实测**，实施时先验证）。
- **确认时限必须小于每轮硬超时**（默认 120s，`real-adapter.ts:543`）——否则长等待会被整轮掐断。
- `execute` 的 `AbortSignal` 现被 `toPiTool` 丢弃（`:253`），须透传，防悬挂。

## 四、B 组设计：聊天体验

### B-1 Markdown 渲染（归属：桌面应用）

> **客户修订（2026-10-12）**：「markdown 渲染**应该用第三方的**，现在看起来像是你自己实现的」。
> 据此**取代**原先「自写最小子集渲染器、不引库」的路线：改用**第三方库**，且因渲染进程无打包器（经典脚本），库须**随仓库自带单文件（vendored）**。
> 约束不变：**模型输出绝不可直通 HTML**（选 `html:false` 一类默认转义原文 HTML 的库，或库 + 消毒）；链接仍须 `rel="noopener noreferrer"` 且经 preload 外开；渲染器仍是**可单测的纯函数面**（测试改为断言库配置下的输出与 XSS 反向用例）。**选型与版本 pin 由桌面角色在实现记录里写明**（含许可与升级路径）。

- **自写最小子集渲染器，不引库**（渲染进程无构建步骤、无前端依赖）。← 已被上条修订取代
- **红线：先行转义、再解析，只产白名单标签**；模型输出**绝不可直通 HTML**（XSS）。
- 子集：标题 / 有序·无序列表 / 围栏代码块 / 行内代码 / 粗斜 / 链接（`rel="noopener noreferrer"`，外开经 preload）；**表格与图片不做**。
- 落点：`appendAssistant`（`:134-143`）改受控渲染；`appendUser` 同法保持一致；`sys-*` 状态行**保持转义**（无收益）。
- **渲染器抽为纯函数**，node 测试直接断言：`**x** → <strong>`、`<script>`/`<img onerror>` **保持转义文本**。

### B-2 切换保留历史（归属：桌面应用，引擎侧已确认可不动）

- **路线 a（推荐）：并存会话**。每角色各持一个会话句柄（`openRoleSession` 无「同时仅一会话」假设、句柄可长期持有、`dispose` 幂等），**切走不 stop、切回直接续** —— 记录与**模型上下文天然保留**。
  - **必须配套（一）事件信封**：现在的事件流**不带角色标识**（`renderer.js:378-391`），多会话并存会**串消息** ⇒ 事件须加 `roleId` 信封，渲染侧按角色分发。
  - **必须配套（二）后台消费**：事件流是**拉驱动**的（`run-role.ts:251-268`）——切走后若停止拉取，重 pin / 回交会停摆、适配器队列积压。故需**后台持续消费**并写入该角色的转录缓冲，界面只渲染"当前选中"的那份。
  - **上限与恢复**：同时保活会话数设上限（建议 3，LRU）；被淘汰者 `dispose` 但**保留界面快照**——再切回时恢复 DOM 并**明示「模型上下文已重启」**（不假装历史仍可续问）。快照恢复要注意**事件监听器**（按钮等）——用事件委托或重绑，否则卡片按钮失灵。
  - **落点**：`app/desktop/session.ts`（单 handle → Map + LRU + 事件信封）、`app/desktop/interface.ts`（定向 stop）、`renderer.js`（每角色 DOM 缓存 + 恢复）；编排 `openRoleSession` **预期无需改**（待其确认「多句柄并发无共享态」）。
- **路线 b（不推荐）：转录重放**。UI 事件是**摘要**而非模型协议史，重放不忠实、且重喂费 token —— 只在内存极紧时才考虑。
- **路线 c（长期最优，本轮不承诺）**：Pi 层的**会话恢复**（若 `pi-coding-agent` 支持持久化会话）——可以把"活句柄"降级为"可恢复的持久会话"，内存与上下文兼得。是否可行需 **Pi适配器**核实后再立提案。
- 界面：左树小圆点标「有活动会话」；缓存命中即时恢复、不转圈。
- 测试锚点：`test/桌面应用/session.test.ts` 断言「A→B→A 不 dispose A（open 计数=2）」「LRU 逐出」；e2e 断言「切回历史仍在」；`renderer.test.ts` 钉「`selectRole` 不得无条件 `clearChat`」。

### B-3 角色状态显示（归属：桌面应用）

左树每个角色一个**状态徽标**（色点 + 短标签），**只由既有事实推导，不发明进度/预计时间**：

| 状态 | 判据（既有信号） |
| --- | --- |
| `未开启` | 无该角色的会话句柄（且无历史） |
| `空闲` | 会话已开、无进行中的轮次 |
| `工作中` | 轮次进行中（prompt 已发、未 settle） |
| `等待你确认` | 该角色有**未决的交互请求**（A 组落地后可有；此前恒不出现） |
| `已停止` | 会话被停（stop/dispose） |
| `错误` | 该角色最近一次轮次/会话以错误结束 |

- 悬停显示**最近一条事件的摘要 + 时间**（复用事件流，不新增数据源）。
- LRU 淘汰后仍保留状态与历史标注（配 B-2 的「模型上下文已重启」提示）。
- 测试锚点：`renderer.test.ts` 断言「状态徽标的文案随给定状态变」（纯函数映射，与渲染分离）。
