# 项目管理 变更记录（治理动作）

## 2026-10-11 — 记录 `.env` Pi 键的指定写入者安排（G-2）

**性质**：跨角色治理动作，**记录在案**（**非**边界授权）。本记录由 **ANS Governance（内置治理角色 su）** 以治理身份写入；变更记录归档在项目管理（全项目变更记录归此）。依据：设计稿 `角色卡/项目管理/docs/design/2026-10-11_design_v1-full-implementation.md` §11.2 与派发清单 **G-2** 行。

**背景**：客户新增需求「桌面 Pi 配置界面 → 保存到 `.env`」（设计 §11）。桌面面板要让用户在界面里填 Pi 配置（`ANTHROPIC_AUTH_TOKEN` 掩码 + `ANS_PI_BASE_URL/MODEL/PROVIDER/CONTEXT_WINDOW` 等非机密项）并保存为**仓库根 `.env`**——与 CLI `--env-file=.env` **同一个文件**。本记录说明「谁写这个文件、以什么形式」。

**安排（要点）**

- **`.env` 归属不变**：`角色卡/装配/boundary.yaml` 里 `kind: file` / `path: .env` / `purpose: 本地环境配置，含 Pi 凭据；不入库` 那一条**一个字不动**，**装配仍是 `.env` 的属主**。
- **日常写入者 = 共享模块 `src/common/shared/env-file.ts`（pm 属主）**：由**桌面应用在运行时调用**它来保存用户在界面里填的 Pi 配置。该模块是 `.env` 解析/合并/原子写的**单一实现**（T26，pm 边界内），与既有 `docs/scheduling/`「目录归 pm、内容由指定写入者 `task_ops` 写」**同形**。
- **不新增任何 Section 1 条目**：本条**不是**边界授权，**未**改动任何角色的 `boundary.yaml`。写入逻辑落在 pm 的 `src/common/shared/`（pm 边界内），`.env` 归属不变，故无需 Section 1 授权；仅需 Governance 将「指定写入者安排」**记录在案**（即本条）。
- **客户已确认**：本安排经客户**明确确认**（即治理流程所要求的「经客户确认」一步），非 Governance 自裁定。

**为何用此形式，而非把 `.env` 加进桌面应用的边界（关键理由）**

若把 `.env` 加进**桌面应用**的 Section 1（`角色卡/桌面应用/boundary.yaml`），等于授予**桌面应用角色在开发期改写仓库 `.env` 的权限**——即桌面身份可在**任何任务**里直接写 `.env`。这**比实际需要宽**：真正需要的只是**运行时、由用户操作触发**的保存（用户在面板点「保存」时，经共享模块写 `.env`），而非「桌面角色随时可写」。把 `path: .env` 放进桌面边界会把「运行时的一次用户触发的写」升格为「角色的常设开发期写权」，**权限面被放大且不精确**。采用「归属不变 + 指定写入者」既满足需求，又不扩大任何角色的常设权限——与既有 `docs/scheduling/`（**目录归 pm、内容由指定写入者 `task_ops` 写**）**同一模式**。

**无越界改动**

- Governance 本次**只建档记录**：**未**修改任何 `boundary.yaml`（装配与桌面均**一字未动**），**未**修改任何产品代码。
- 边界与合规：仅在本文件（pm 的 `docs/change/`，全项目变更记录归档处）写入。**未**读 `.env`（注意：被要求不读它，并不代表它不存在或为空）、**未**发任何真实网络请求、**未**打印任何凭据值。

**关联**：设计 §11.2（正当形式与 G-2）；派发清单 G-2 行；下游任务 **T26**（pm 建 shared `env-file`）/ **T27**（Pi适配器 红线改写）/ **T28**（桌面 面板 + 载入/保存）/ **T29**（测试）。**装配无改动**。
