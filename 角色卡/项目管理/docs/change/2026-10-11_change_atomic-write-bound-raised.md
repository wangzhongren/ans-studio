# 项目管理 变更记录

## 2026-10-11 — 原子写原语：把 rename 瞬时 `EPERM` 的**有界重试上界由 20 上调为 200**（附「失败安全」的可回归证据）

**来源（本角色自报的 flake）**：同步设计稿时如实回报——本轮新加的用例 `test/项目管理/shared/atomic-write.test.ts` 的 **③ 并发自争用**「多路 `atomicWrite` 反复覆盖同一目标，全部成功」**在全量并发下约 15 次挂 1**。该用例的**目的**正是「证明那个有界重试有效」，结果它在高压下自己翻红，必须**当场查清**：是**产品代码真的失败**（甲）还是**用例自身竞态**（乙）。

### 一、复现（先复现，再定性）

| 条件 | 命中率 |
| --- | --- |
| `node --test "test/**/*.test.ts"`（全量，Node 默认并行多文件），连跑 | **2/40**（RUN 8、9 各挂一次），失败点恒为用例 ③ |
| **多路并发同跑压测**：同一测试文件 **24 路并发 × 8 批 = 192 实例**（沿用本仓既定的「并行实例同跑」压力法） | **13/192**、另一次 **20/288**（最高一次 **13/192≈7%**） |
| 单跑该文件（单进程，无外部负载），连跑 60 | **0/60** |
| 进程内自加负载（24 个 8 lane × 250 轮场景同跑，共 48 万次 rename） | **0/240 场景** |

**结论**：命中率随**系统级并发**（多进程 / 全量多文件）显著上升，**单进程内 8 路自争用不足以触发**——与「仅在全量并发下出现」的现场吻合。

### 二、定性 ＝ **(甲) 产品代码的真实失败**（非用例竞态），有证据

对整个重试核心临时加计数/日志（**仅诊断，已全部删除、未提交**）后：

1. **上界确被打满**：失败时日志为 **`[RETRY-EXHAUST-DIAG] attempts=20 code=EPERM`**。抛出的错误码是 **`EPERM`**，而 `EPERM ∈ RENAME_TRANSIENT_CODES`——按 `retryOnTransient` 的逻辑，`EPERM` 只在 **`attempt == maxAttempts(=20)`** 时才被抛出，**即第 1~19 次全为瞬时失败、第 20 次仍失败 → 上界耗尽**。故**产品代码在该压力下确实会失败**，不是测试问题。
2. **排除 (乙)**：抛出的是 `rename` 的 `EPERM`（栈指向 `retryOnTransient` 的 `rename`），**不是**用例断言失败；用例侧**全部 await**（`Promise.all(lanes)` 已 await，round 循环串行），**无未 await 路径、无等时间赌时序的断言**。故非用户例竞态。

**（这条比「测试挂不挂」重要得多）失败是安全的**——把用例的失败点改成「先取快照 `snap1`（在途）→ 等所有 lane 落定 → 再取 `snap2` → 读目标」，13/13 次失败**全部**满足：

```
snap2(落定)=[".env"]   ← 落定后**无任何 temp 残留**（temp 已被 atomicWrite 的 catch 清理）
targetIntact=true      ← 目标是一个**完整**的写入（未半写、未损坏、非空）
```

即：**上界耗尽时只损失「这一次写」，绝不损坏文件**（`atomicWrite` 失败即 `rm` temp 并抛错；`rename` 原子，未成功即不改目标）。（`snap1` 偶见 temp，属**在途**的其它 lane，落定后即消失——非泄漏。）

### 三、根因与**尝试次数分布**（决定上界该取多少）

用与产品算法逐字同构的可计数副本 + 多进程同跑量化（24 路 / 32 路）：

- **绝大多数 rename 1~2 次即成**（≈53% 第 1 次、≈26% 第 2 次）；
- **但尾部长**：单个 rename 最坏需 **≈63 次**（24 路观测 max 62、32 路观测 max 63），且**不随并发再升（24→32）而爆涨**——是**特征尾部**，不是发散。
- 上界取 20 ⇒ 尾部（>20）**必然翻红**，与现场一致。

### 四、修根因 ＝ **按实测上调上界**（非 sleep / 非 retry-on-test / 非降并发）

- **改** `src/common/shared/atomic-write.ts`：`RENAME_MAX_ATTEMPTS` **20 → 200**（= 观测尾部 ≈63 的 **~3×**）；其文档注释改为**引用本轮实测**（1/20 全量命中、`attempts=20` 被打满、尾部 ≈63），并更新 `renameReplacingExisting` 中已失效的「≤6 次内清除、无一次硬失败」旧断言。
- **为何「加大不心虚」**：`setImmediate` 每轮即一个事件循环轮次，**成本可忽略**（与原 20 同量级）；**仍是有限上界**——真·持续失败照样在 ≤200 次内**显式抛出**，不吞、不伪装成功。
- **明确未用的手段**：**未**用「加大 sleep」、**未**在用例里加 retry、**未**降低用例并发度去盖红——这些都会把「产品在高并发下会失败」这一事实**藏起来**。这里改的是**能由实测辩护的参数**，并把失败路径**另立单测**（见下）。

### 五、新增确定性用例：失败路径的**安全性**（可回归）

`test/项目管理/shared/atomic-write.test.ts` 新增 **③ 失败路径安全**：令「rename 覆盖目标」**必然失败**——目标是**已存在的非空目录**（Windows：`EPERM` 瞬时码 → 重试至上界再抛；POSIX：`EISDIR`/`ENOTEMPTY` 非瞬时 → 立即抛）。断言（两平台同契约、**不靠概率**）：**显式抛出**、**temp 已清**、**目标（目录及其内文件）未被触碰/损坏**。这正是「即便上界耗尽也绝不损坏文件」的**可重复证据**（把诊断期的一次性观察固化成单测）。

用例 ③ 原「全部成功」断言**保留**（这是该原语在现实到重度争用下**设计上应交付**的行为），但改用 `Promise.allSettled`：一旦将来翻红，报错会**直接给出错误码**，便于区分「上界耗尽（瞬时码）」与「真·损坏」。
