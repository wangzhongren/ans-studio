## 1. 失败 1：Windows 无界 grep 守卫漏判（产品缺陷）

### 1.1 根因

`splitSimpleCommands` 在非引号分支把 `\` 一律当 POSIX 转义符消费（`\X` ⇒ `X`），Windows 绝对路径 `D:\a\ans-studio\…\.release\source` 被拼成 `D:aans-studio….releasesource`，`isWidePath` 解析结果不再等于项目根/cwd ⇒ 无界递归搜索被判 `allow`。双引号分支同样把 `\` 一律当转义符，`"D:\…"` 同样被破坏。

### 1.2 修复（最小、可解释）

- 非引号分支：新增 `windowsPathSeparator(current, next)`。token 处于 Windows 路径形态时保留 `\` 作分隔符：
  - 盘符绝对路径 `^[A-Za-z]:[\\/]`：token 为 `D:`（本字符即首个分隔符）或已是 `D:\…`/`D:/…`；
  - UNC `^\\\\`：token 已有前导反斜杠，或正看到首个 `\` 且下一个也是 `\`。
  - 例外：`\` 后是空白/`|`/`&`/`;`/`(`/`)`/引号时，**POSIX 转义优先**——空白不切词（`D:\a\my\ dir` 保持一个 token），元字符不切命令。
- 双引号分支：改为 POSIX 语义——`\` 只对 `$`、反引号、`"`、`\`、换行生效；其余字符前保留字面反斜杠（`"D:\a\b"` 不再变成 `D:ab`）。行续接（`\`+换行）与既有转义不变。
- `isWidePath`：Windows 绝对路径（盘符/UNC）用 `path.win32` 解析与比较（大小写不敏感、`\` 与 `/` 等价），根比较统一去尾分隔符；不同形态（Windows 绝对路径 vs 宿主 POSIX 路径）不互相包含。**该判定不依赖宿主平台**，macOS 上可直接回归 Windows 路径。POSIX 分支逻辑不变。
- 未放宽无界搜索判定：宽范围仍指「等于/祖先于 cwd/项目根/home、文件系统根、UNC 共享根」；具体子目录/文件照常放行。

### 1.3 回归（不依赖宿主平台）

`test/编排/shell-command-guard.test.ts` 新增 1 例（deny 5 形态 + allow 2 对照）：
- deny：未加引号 `D:\…\.release\source`（CI 红用例原形）、双引号包裹同一路径、含空格的 Windows 根经 `\ ` 转义（不切词）、UNC 项目根、UNC 共享根 `\\server\share`；
- allow：`D:\…\source\src`、`D:\…\source\src\index.ts`（防一刀切）。
- 均以 `cwd/projectRoot` 直接传 Windows 路径调用 `guardShellCommand`，macOS 本机可复现 Windows 判定。

## 2. 失败 2：flow-service 原子写失败用例在 Windows 不成立（测试平台真值）

### 2.1 根因

用例用 `chmodSync(flowsDir, 0o500)` 让目录不可写来制造原子写失败；Windows 上目录 mode 不阻止写入（chmod 对目录只影响只读属性）⇒ `completeAcceptanceStep` 实际成功，`result.ok` 为 `true`，断言 `true !== false`。

### 2.2 修复（断言本体不放宽）

`test/编排/flow-service.test.ts` 该用例按平台分支制造**真实会失败**的条件：
- POSIX（保持原样）：目录 `0o500`，同目录建临时文件失败 ⇒ `write-failed`；
- win32：目标 `docs/flows/flow-a.yaml` `chmod 0o444` 设为只读。`atomicWrite` 先在同目录建临时文件再 rename 覆盖目标；`MoveFileExW` 覆盖只读目标返回 `ERROR_ACCESS_DENIED`（Node `EACCES`/`EPERM`，两者均在 atomic-write 的瞬时重试集合内；只读属性持续存在 ⇒ 重试上界 200 次耗尽后抛错）⇒ `write-failed`，目标未被触碰。`finally` 恢复 `0o644`。
- 断言保持：`ok=false`、`code=write-failed`、原文件字节不变；**新增**恢复权限后再调用一次 ⇒ `ok=true` 且 `verification` 为 `done`（失败路径无半写/坏状态）。
- 注释写明平台真值与依据。

## 4. 残余风险

- **Windows 结论仅能由 CI 原生 runner 实测**：本机为 macOS。守卫回归用例已做成平台无关（Windows 路径判定走 `path.win32`），但「真实 Windows shell 命令文本」的端到端仍以 CI Windows job 复跑为准。
- flow-service 的 win32 分支依赖「rename 覆盖只读目标返回 ERROR_ACCESS_DENIED（EACCES/EPERM）」这一 Windows 语义；本机无法执行该分支。若 Windows 语义与预期不符，该用例会在 CI 上失败（不会静默放宽）；`renameReplacingExisting` 对持续失败会重试至 200 次上界后抛错，测试耗时略增但仍有界。
- UNC 判定覆盖「UNC 项目根 / UNC 共享根」；任意 UNC 子目录（非项目根、非共享根）与 POSIX 一样按窄范围放行——这是既有「具体目录不拦」策略，不是本次放宽。
- 本次未重跑发布 CI；两处修复的最终关闭以 CI 复跑三平台全绿为准。
