# 变更记录：验收任务加入「架构方案/架构影响分析核对」硬要求（2026-10-19）

## 1. 客户批评

客户指出：交付「感觉也没有啥架构」，提案角色应考虑到扩展性、给出一个架构方案。落到验收侧：
验收不能只看功能与演示，还要按提案/变更声明的架构方案（或架构影响分析）核对实现；
缺失架构章节或实现偏离声明时不得建议 accept。

客户原话：**「这个感觉也没有啥架构的啊，提案角色应该也要考虑到扩展性，给出一个架构方案啊。」**

本角色写入面仅覆盖 `app/desktop/**`、`test/桌面应用/**`、`角色卡/桌面窗口/**`。提案角色自身的
提案模板/任务文案（是否强制含架构章节）不在本角色边界内，本变更只落**验收核对要求**；
提案侧要求如需要，由提案角色/项目管理另行落地（见 §5 残余风险 2）。

## 5. 残余风险

1. **任务文本约束非强制**：模型可能忽略硬要求直接建议 accept；兜底仍是客户/判断 agent 在
   验收卡上把关（与上一批「真实启动/演示」硬要求同一风险面）。
2. **前提取决于提案/变更本身含架构章节**：本角色不改提案模板与提案任务文案（属提案/项目管理
   写入面）。若提案/变更缺「架构方案或架构影响分析」，验收方按第⑤条只能建议退回或补充证据；
   要真正从源头解决「提案没有架构」，需提案角色在提案模板/任务文本中强制该章节，由项目管理协调。
3. **架构一致性依赖人工/AI 判断**：模块边界、依赖方向、扩展点、数据 schema/API 版本迁移是否
   「与声明一致」无法机械判定；未加机械门槛属有意选择（沿用 `flowCompletionIssue` 只做可机械
   核对判定的纪律）。
4. **报告路径不变**：第⑤条核对结论并入既有 `docs/verification/<flowId>-v1.md` 与验收卡，
   不新增文件路径约定；未改演示证据/质量基线要求。
5. **无跨角色改动**：未碰 `src/**`、`app/renderer/**` 及他角色文件；若其他角色对验收任务文本
   另有副本或断言，需属主角色自行同步（本角色 grep 未发现第二份）。
