# 变更记录：验收任务加入「真实启动与演示 + 工程质量基线」硬要求（2026-10-19）

## 1. 客户决定

客户指出：验收前最起码要把应用真实启动起来给客户看；当前流程只把人工冒烟当可选项，
导致没运行过应用就验收。桌面侧需要把「真实启动与演示 + 工程质量基线」写进验收任务与验收门槛。

客户原话：**「可以，按你说的改」**（批准本改动）。

## 2. 改动

`app/desktop/governance-advance.ts::buildAcceptanceTaskMessage`（现文件 205–227 行）：

1. 既有文案逐字保留：

   ```text
   流程 <flowId> 步骤已全部完成（流程单：docs/flows/<flowId>.md；回交/核对报告路径：…）。
   请汇总证据并出验收卡（不要自行验收或代替客户决定）。
   ```

2. 其后追加**四条硬要求**（发给 Proof / verifier 的验收任务文本）：

   ```text
   验收前必须满足以下硬要求：
   ① 按工程质量基线逐项核对并给出结论与证据：正确性、健壮性、安全、可维护性、
      可观测性、性能、前端可访问性、测试矩阵；
   ② 必须真实启动应用并向客户演示：给出启动命令与访问地址，附截图或录屏
      （你已有审批档 shell，可执行启动命令，命令逐条提交审批）；
   ③ 未真实启动/演示、或质量基线某项无证据，不得建议 accept（只能建议退回或补充证据）；
   ④ 演示证据与逐项核对结论写入 docs/verification/<flowId>-v1.md，并在验收卡中引用。
   ```

3. **`flowCompletionIssue`（收尾推进触发门）逐字未改**：不新增硬编码步骤名，也不把
   「必须有演示证据」加为派发前置（见 §5 决策与 §6 残余风险）。`buildAcceptanceTaskMessage`
   仍只产出任务文本，不是验收判定；验收卡仍由决策开关/判断 agent/客户手批。

## 5. 触发门为何不改（决策记录）

任务要求「如认为需要在触发门增加『必须有演示证据』，先只写进报告与变更记录，不要擅自改门槛」。
本角色**不**改 `flowCompletionIssue`，理由：

1. 触发门只能看到流程单与治理账本；`docs/verification/<flowId>-v1.md` 是否存在只能证明「写了报告」，
   无法机械证明「应用被真实启动/演示过」（截图/录屏内容、启动命令与访问地址都需人/AI 核对）。
2. 以报告存在性作前置会误伤：Proof 被派发前尚无该报告（鸡生蛋），而「先派发、后写报告」正是本
   变更的任务文本约束面。
3. 现有纪律是「触发门只做可机械核对的完成判定」；本需求落地在任务文本 + 验收卡判断（客户/判断
   agent），保持既有语义与最小改动。

若后续治理需要硬约束，建议另立设计：由账本新增机械事实（如 Proof 回报 `demo.started` /
`demo.presented` 事件），再做触发门判定——不要按步骤名或报告文件名硬编码。

## 6. 残余风险

1. **任务文本约束非强制**：模型可能忽略硬要求直接建议 accept；目前唯一兜底是客户/判断 agent
   在验收卡上把关。未加机械门槛属有意选择（见 §5）。
2. **Proof 的 shell 依赖审批**：真实启动命令走审批档，客户拒绝或通道不可用时演示无法完成；
   任务文本要求此时不得建议 accept，但系统不会自动阻止一张不合规的验收卡。
3. **演示证据质量**：截图/录屏可能过时或与本次改动不对应；文本无法校验，仍需客户在验收卡上判断。
4. **路径约定**：`docs/verification/<flowId>-v1.md` 为本次任务给定的固定写法（v1）；若后续同一
   flow 需要多轮验收报告，需另行约定版本化规则（未在本变更处理）。
5. **无跨角色改动**：未碰 `src/**`、`app/renderer/**` 及他角色文件；若编排侧对验收任务文本另有
   副本或断言，需属主角色自行同步（本角色 grep 未发现第二份）。
