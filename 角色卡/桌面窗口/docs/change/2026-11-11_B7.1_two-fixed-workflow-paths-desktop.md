## 2. 施工口径（实现摘要）

### 2.1 `app/desktop/session.ts::routeDispatch`：fixed 会话 fail-closed

- 位置：trio 来源防御之后（`:8846` 附近），先算 `chatMode`，再按模式分流；legacy 分支保留原
  `dispatchFlowId !== ""` 块逐字（含 B3 首启动例外与 `routeFixedPathDispatch`/`routeStarDispatch` 选择）。
- fixed stage-request 校验一次性汇总全部缺失/非法字段（一次回执给出可重试修正方向）：
  `flowId`（trim 非空）、`workflowPath ∈ {"A","B"}`（`isWorkflowPath`）、`stage ∈ WorkflowStage`
  （`isWorkflowStage`，A1–A13 含 A12a/A12b、B1–B4）、`workflowAction === "advance"`（**缺省不补**）、
  `roleId ===` 本项目运营（`handbackOwnerRoleId ?? "convener"`）。失败回执与系统行均带
  `stage-request-invalid：` 稳定码；路径上不触碰任务账本/项目配置/run 目录、不 enqueue。
- 完整 stage-request：`isFixedPathEnabledForFlow` 已开 ⇒ `resolveFixedPathMode` 复核；未开 ⇒
  `ensureFixedPathStarted`（原子写 `workflowSchema:"two-fixed-paths/v1"`，显式 legacy 不覆盖，失败
  `project-config-write-failed` fail-closed）。复核结果非 fixed（例如该 flow 有在飞 legacy run）⇒
  `stage-request-invalid：(未能解析为 fixed workflow)` fail-closed——**不落星形**。
- 非 stage-request：`workflowId` trim 非空 + `stage !== undefined` ⇒ `routeFixedPathDispatch`；否则
  `stage-request-required：…`（系统行注明「已拒绝 legacy 星形派发」）。
- 影响面：**fixed 聊天不再按被派 flow 的 per-flow 模式分流普通派发**（v1.3 §4.1 的 per-flow 判定仍用于
  有 flowId 的 fixed 任务与 `workflowModeForFlow` 注入；普通星形派发只存在于 legacy 聊天会话）。
  这是 B7.1 任务的明确要求（RR2 fail-open 关闭），旧 legacy 项目的行为不变。
  边界情形（如实披露）：显式 `two-fixed-paths/v1` 的混合项目里仍有在飞 legacy run 时，项目聊天按
  `sessionWorkflowModeForChat` 为 fixed ⇒ 该 flow 的普通星形派发在 fixed 聊天中同样 fail-closed；
  若后续需要在混合项目继续 legacy 派发，应另行确认以任务/会话模式（`sessionWorkflowModeForTask`）
  替代项目聊天模式的判定口径。
