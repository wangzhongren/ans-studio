# CI run 38931760696 新红判别与修复（桌面窗口）

**现场**：v1.3.0 第四跑 run `38931760696`（Windows runner）——`test/桌面应用/session-rebuild-race.test.ts:346`「重开失败保留原错误，不恢复假活动目标、不发送消息」：`:357` `assert.equal(result.ok, false)` 实得 **`ok: true`**（该在 stale 重建失败时如实失败的 send 成功了）。同一 runner 前三跑（38924209553/38927621909/38929587975）该用例均绿。

## 一、机制判定（三分：**时序脆弱**，非确定性平台真值、非产品并发竞态）

**机制链（排除法＋受控实验，两类证据都指向同一点）**：

1. `send` 返回 `ok:true` 的**唯一**路径：`:357` 的失败点之前，`send` 走 `rebuildIfBoundaryStale(targetRoleId, true)`；该函数返回 `undefined`（未判陈旧）时消息落在存活句柄上直发成功。逐段核：entry 在、`busy=false`（无在跑）、`profileRevision` 未变（该链路无 `profileChanged` 调用）——**一切只取决于 `boundaryDiff(entry)` 是否返回非 null**。
2. `boundaryDiff` 只对冻结路径做 `filePrint` 比对：`角色卡/A/boundary.yaml`（+ `.ans/project.json`，恒 `<missing>` 稳定）。**内容已真变**（`writeFileSync` 已完成）、**尺寸恰等长**——夹具失败点即：初始 `"v: 1\n"` 与重写 `"v: 2\n"` **都是 5 字节**。
3. `filePrint`（Q-1 派工的判据，`hit.mtimeMs === st.mtimeMs && hit.size === st.size`，被 `hot-path.test.ts:244` 源钉）——等长 ⇒ 命中与否**全看 mtimeMs**。若该次 runner 把「makeProject 写初始值」与「用例重写」两次写入的 mtime **合并进同一平台时间戳粒度**，stat 返回与冻结值完全相同的 `(mtimeMs, size)` ⇒ **缓存按「未变」命中、漏检陈旧** ⇒ `ok:true`。
4. **受控实验（/tmp 探针，脚本：open → 等长重写 → `fs.promises.stat` 补丁强制报告冻结 mtime）**，三相位输出：
   - A 旧夹具＋强制 mtime 相等：`{"ok":true,"sent":["失败不得发送"],"openCount":1,"rebuildFailedRow":false}` ——**精确复现 CI 失败签名**；
   - B 旧夹具＋真实（不同）mtime：`{"ok":false, error:"…重开失败原文——本条消息未发送，请重试。","sent":[],"openCount":2}` ——绿路径；
   - A2 **修复后夹具**＋强制 mtime 相等：`{"ok":false,…,"sent":[],"openCount":2}` ——**对粒度合并免疫**。
5. **三分结论**：
   - **非「确定性平台真值」**：同 runner 3/4 跑绿——输入（等长）确定但**触发条件（两写 mtime 是否被粒度合并）依平台/负载而变**。
   - **非「产品并发竞态」**：无并发窗口；单线程顺序执行下这是缓存判据的**确定行为**——前提「内容变 ⇒ mtime 变」在**时间戳粒度合并**时失效；Q-1 判据 `(mtimeMs,size)` 是派工指定口径（`hot-path.test.ts:244` 钉住），宽泛「内容哈希」意图由缓存加速实现。
   - **是「时序脆弱」**：触发面＝「**等长重写 + 两次写入落在同一时间戳粒度内**」；本用例是**最紧序**（open 完成后立刻重写、再立刻 send，写-写间隔 ~1ms），恰落在粒度合并窗内；文件内其它等长重写点（:170/:222/:260/:287/:389）同一风险面。
6. **为何不用「有界等待」硬化**：缓存命中后是**持久态**（文件此后不再变 ⇒ `(mtimeMs,size)` 恒等 ⇒ 永远命中旧 print），等待/重试不会令其收敛——f1-timeout 式有界等待**不适用**；对症最小面＝让「陈旧触发」**尺寸可判**（缓存必失效，与 mtime 粒度无关）。
