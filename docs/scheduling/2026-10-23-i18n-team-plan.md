## 一、任务与基线

### 1.1 目标

按客户在闸门 0/1 已确认的意图与策划方案 v1，实施 i18n 变更：

1. **单一消息目录 + 单一翻译实现**：`src/common/shared/i18n/`（项目管理唯一写入）承载 `zh-CN` 参考目录、`en-US` 目录、key 类型、插值/复数/回退与格式化；渲染层只经 `app/renderer/src/i18n/` facade 再导出，不复制第二份目录或 resolver。
2. **运行时切换与持久化**：默认 `zh-CN`；`en-US`；设置面板语言区切换立即生效；`<userData>/ans/preferences.json` 为权威、`localStorage["ans.locale"]` 仅首屏镜像；重启保持、项目切换不变；偏好损坏/非法回退中文并记稳定诊断码。
3. **分层覆盖**：渲染层 chrome 与聊天/面板文案归 `ui.*`（桌面UI）；主进程生成、最终显示给用户的文本归 `main.*`（桌面窗口）；共享设置元数据归 `shared.runtimeSettings.*`（项目管理 key 化、桌面窗口解析）；CLI 本轮不纳入。
4. **不国际化机器标识**：`roleId`、`cardKind`、`GovernanceFunction`、flow step id、协议字段、事件/日志/诊断码、测试断言标识、路径/环境变量/工具名保持原样。
5. **分批迁移、zh-CN 逐字不变**：B0 基础设施 → B1 渲染层外壳 → B2 渲染层聊天/面板 → B3 主进程用户可见文本 → B4 共享设置元数据；每批旧中文断言保持，新增 en-US 断言；AST 硬编码守卫允许清单逐批收紧。
6. **布局与真实 UI**：英文变长在 960×620、侧栏 208、标题栏 36px、设置保存条 64px、200% zoom 下无关键溢出；截断有 `title`/`aria`；真实 Electron 冒烟 + 截图证据。
7. **独立验收**：T2 做受影响角色检查 + 跨层集成 + 真实 UI；本变更单独 `docs/acceptance/` 标准与报告，不与目录授权变更合并判定。

### 1.2 风险档位：T2

依据技能 `references/testing.md`「Risk-Based Verification and Change Packages」：本变更同时触及渲染层、主进程、共享元数据与新增 IPC 契约，属于跨角色/接口契约/shared 变更，不是 T1 局部实现；它**不**改变治理/权限/角色边界，因此不是 T3。

**T2 默认验证**：受影响角色的单元/层测试 + 跨角色集成检查（主进程↔渲染层 IPC、shared 目录↔两个消费方）+ 受影响的渲染构建/typecheck；不默认全量回归。**若 `src/common/shared` 改动导致其消费者受影响，按 T2 重测所有实际消费者**（装配、桌面窗口、编排、Pi适配器、门禁引擎中实际导入 shared 的部分）。

**升档条件（触发即停止并回报统筹，重开闸门 2）**：
- 实施中发现需要改动 `src/common/shared/` 的属主、角色边界或治理权限/角色定义；
- 需要新增/修改 `cardKind`、`FlowStepKind`、`GovernancePower`、`GovernanceDecisionKind`；
- 需要修改会话/任务 scope、`src/model/**`、`src/service/**`、`src/provider/**`、`src/pipeline/**` 的产品语义（i18n 本轮不触碰）；
- 偏好文件或 IPC 改造超出方案 §5.2/§5.3 契约（如把系统行改成 key+params、追溯历史）；
- 客户把 CLI 纳入本轮（增加装配/编排写集与 `--lang` 契约，需重开闸门 2，必要时升档）。

## 三、五维判断与决策表

### 3.1 五维判断

| 维度 | 判断 | 依据 |
| --- | --- | --- |
| 1. 责任独立性 | **无新增持续独立责任** | i18n 是横跨既有分层的横向能力：消息目录/翻译实现属 shared（项目管理既有职责）、渲染层消费属桌面UI、主进程偏好/IPC/文本属桌面窗口、跨层集成/回归属测试。没有产生需要不同知识与契约的独立角色。新增的「共享消息目录」是共享抽象，但已有合适唯一 owner（项目管理），按决策表「新增共享抽象但无合适 owner → 指定唯一 primary owner」，此处 owner 已存在 |
| 2. 范围归属 | **现有 Section 1 精确覆盖；无默认缺口** | 方案 §9.1/§9.2 的路径逐个映射到现有 Section 1（见 §四）。`src/common/shared/i18n/` 是项目管理已授权目录内的新文件；`app/renderer/src/i18n/` 在桌面UI 的 `app/renderer/` 目录内；`app/desktop/preferences.ts`/`i18n.ts` 在桌面窗口的 `app/desktop/` 目录内；`test/桌面UI/` 是目录授权；`test/项目管理/shared/` 是目录授权。按 `references/module-boundary.md`「已接受目录内新增文件不需要重写边界」，均不构成边界变更 |
| 3. 契约影响 | **有，跨角色共享契约变更** | 新增共享 i18n 公共 API（`translate`/`createTranslator`/`Locale`/`MessageKey`/`MessageParams`）；新增 IPC 契约 `preferences:get`/`preferences:set-locale`/`preferences:locale-changed` 与 preload 方法；新增偏好文件格式 `{version:1, locale}`；共享设置元数据由 `label/help/choiceLabels` 改为 key 字段（渲染层视图契约不变）。单一主属：shared 目录/元数据 → 项目管理；IPC/preload/主进程文本 → 桌面窗口；facade/渲染消费 → 桌面UI；集成证据 → 测试 |
| 4. 证据独立性 | **已满足** | 各实施角色跑自己的单元/层测试；测试角色跑跨角色集成与消费者重测；桌面UI 产出真实 Electron 布局冒烟；内置独立验收按实施前标准判定。实施者不自验，调度不改验收结论 |
| 5. 协调成本 | **维持现有团队最低** | 5 个现有 worker（项目管理、桌面UI、桌面窗口、测试；装配条件启用；UIUX 条件咨询）+ 内置独立验收 + 统筹。新增 i18n 专职角色会增加建卡、边界、交接与证据成本，而本轮没有产生新的持续独立责任；不新增角色 |

### 3.2 决策表结果

**不变，派给现有角色。**

- 无新增、无拆分、无合并、无角色卡改动。
- `src/common/shared/i18n/`、`app/renderer/src/i18n/`、`app/desktop/preferences.ts`、`app/desktop/i18n.ts` 均为既有目录授权内的新文件，不需要重写边界。
- **条件项（不是默认）**：
  - 若 B0 验证发现 Vite 开发/构建无法解析 `app/renderer` 之外的 shared 模块，需要装配在 `vite.config.ts` 增加 `server.fs.allow`（装配 Section 1 已覆盖）；这是**装配参与条件**，不改变边界；若客户不接受该条件，B0 停止并回报，不自行改构建配置。
  - 若实施确实需要新建 `test/桌面应用/<新文件名>.test.ts`：该目录对桌面窗口是**逐文件授权**，触发**改边界**，须由 ANS 人事按本计划与闸门 2 的额外确认补精确单文件条目；本计划默认**不新建**该目录文件，把新断言并入既有精确文件。
  - 若布局必须调整固定高度/最小窗口/侧栏宽度（改变设计基线），需 UIUX 设计评估与客户确认；默认按方案用布局伸缩/换行/title 解决，不改设计基线。
- 产品运行期是否使用 i18n 与本仓库执行无关；本计划只改本仓库产品代码/测试。

### 3.3 考虑过的选项

| 选项 | 结论 | 理由 |
| --- | --- | --- |
| A. 现有 4 个核心 worker（项目管理、桌面UI、桌面窗口、测试）+ 装配条件 + 内置验收 + 统筹 | **采用** | 写集与现有 Section 1 一一对应；共享目录/渲染层/主进程/集成分离；协调成本最低 |
| B. 新增「i18n 专职角色」 | 否决 | 一次性横向能力，不构成持续独立责任；项目管理已是 shared 合适 owner；新增角色触发人事写卡与额外闸门 |
| C. 把消息目录放渲染层、主进程只发 key | 否决 | 需改大量 IPC/持久化/历史格式，超出 T2；旧历史无法回填（方案 §10.2 C/§10.3 B） |
| D. 分层目录（shared 运行时 + renderer/main/cli 各自 messages） | 否决（按 Q4 A） | 目录多份、key 全集/类型统一难、跨层重复文案需额外检查；客户已确认单一目录 |
| E. 引入 i18n 库 | 否决（按方案 §10.1 A） | 仅 2 个 locale，无需异步加载/框架绑定；新增依赖违反本轮非目标与工程基线 |
| F. 用一个角色包办全部实现 | 否决 | 跨越项目管理/桌面UI/桌面窗口/测试的 Section 1；违反单一属主与写权限 |
| G. 只做渲染层、不做主进程 | 否决（按 Q2 A） | 会出现系统行/错误/对话框仍是中文的混合语言；客户已确认覆盖主进程用户可见文本 |
| H. 每批各自独立验收 | 不采用 | 方案 §11 的 P1–P12 覆盖整个变更；分批只做阶段放行，最终一次 T2 验收；避免同一变更多次判定口径漂移 |

### 4.2 共享属主核对（不猜）

- `src/common/shared/`：**项目管理唯一写入者**（`角色卡/项目管理/boundary.md` + `docs/project-rules.md` §一.5 + `docs/architecture/shared-components.md`）。新增 `i18n/` 必须在 `shared-components.md` 登记；其他角色只读导入，不复制第二份实现。
- `src/common/shared/runtime-shared.ts` 顶部 import `node:os`/`node:path`：**渲染层不得导入它**（渲染源码守卫禁止 `node:`）；`RUNTIME_LABELS.demo` 的本地化只能走 i18n 目录 key，不能把渲染层改为导入 runtime-shared。`src/common/shared/i18n/**` 必须是**不依赖 Node/DOM 的纯模块**，否则 Vite 打包与渲染守卫都会失败。
- `src/model/runtime.ts`：运行时核心唯一主属；本变更**不改**。
- `src/model/boundary.ts`、`role.ts`、`decision.ts`：门禁引擎唯一主属；本变更**不改**。
- `app/desktop/`、`app/main.ts`、`app/preload.cjs`：桌面窗口；`app/renderer/`：桌面UI；`vite.config.ts`/`package.json`：装配。写集互不重叠。
- `test/桌面UI/` 是桌面UI 的目录授权；`test/桌面应用/` 是桌面窗口的**逐文件**授权；`test/项目管理/shared/` 是项目管理目录授权；`test/测试/` 是测试目录授权。四者互不重叠。

## 六、证据要求

### 6.1 通用证据（每个实施角色）

1. **写前基线**：目标文件的 `git hash-object` 与 `sha256sum`、`git rev-parse HEAD`、`git status --short`；若与本计划记录不一致，停止并回报统筹。
2. **候选身份**：每个改动文件的 `git hash-object` 与 `sha256sum`（工作区；CRLF/LF 差异分别记录，不互相误判）；新增文件同。
3. **改动范围**：`git diff --name-only` 与 `git status --short` 必须落在该角色写集内；`git diff --cached --name-only` 为空（不暂存）；无授权外已跟踪变化。

- 统筹在 I9 完成后组装变更包：`docs/scheduling/i18n-change-v1.md`，含候选哈希（产品代码/测试文件；`git hash-object` + `sha256sum`）、改动路径（相对本变更阶段入口基线）、任务节点 I1–I11、证据链接、风险档位 T2、复用证据与失效说明。

### 7.3 证据复用与档位纪律

## 九、前置问题、风险与阻塞

1. **闸门 2 未确认**：本计划只是团队计划；客户确认角色指派前不派发、不改代码；实施授权另行取得。
