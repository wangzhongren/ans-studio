# 幕僚选用外置工作流与客户确认启用

v1.1 · 2026-11-17 · 已处置独立复核发现，待复核受影响部分。以[客户确认](../communication/2026-11-17_intent-workflow-chief-start.md)为范围，补充[外置工作流方案](2026-11-17_design_path-a-dapr-workflow.md)。冻结产品候选 `4c6efec34182563e3fa8b1ef6ef6372fe282d220`，既有测试取证 `87b3c0f154814ba2598ee3ce262778126b043c8c`。

## 使用方式与切换

客户在普通幕僚对话中交付需求。幕僚查看当前项目可用的工作流，依据实际需求和项目条件选择一份定义并说明理由。应用自动提供一张待确认启用卡。客户本人核对需求、理由、定义名称、来源、ID、版本和摘要后，选择「确认启用」或「不启用」。确认后的回执可区分尚未启动、已创建实例和阻塞；实例创建后仍由定版工作流及既有角色和授权推进。启用决定只授权创建该实例，不替代后续意图、方案、任命、独立验收或本人发布审批。

任务中心保留预设浏览、复制、导入、校验、待确认启用和运行实例状态。移除定义选择后直接启用的表单、`enabled` 开关和 renderer 待重试草稿。`app/main.ts`、`app/preload.cjs` 及桌面入口的旧 `durable-workflow:start` 不再允许任何新实例直启；若为同一候选的兼容调用保留入口，一律返回 `workflow-start-confirmation-required`，无重试或替代令牌，零排程和占用。

有持久幕僚入口的桌面项目，新需求一律走幕僚提议和客户确认。传统 `dispatch_task` 中可开启工作流的首个 A1/B1 请求须在创建任务、写旧账本和获得作用权前拒绝，覆盖未提议、待确认、已拒绝/撤销及批准后与新启动竞争等状态。兼容续接必须由受信账本和当前真实任务定位到已经存在的原实例；仅由模型填 `workflowId`、工具类型或来源声明不能通过。原已启动的 Dapr v1/v2、只读实例和旧 JSONL 流程继续按现有入口查询、回交和收尾。无持久幕僚入口的旧环境仍按原规则运行。外部 API、工作流编辑器、角色制度和 Dapr 控制面重构另议。

## 真实工具与批准入口

冻结版本的 `DurableWorkflowPanel.tsx` 直调 `durable-workflow:start`，主进程只检查受信窗口和 `enabled` 等启动参数。`app/desktop/session/lifecycle/open.ts` 已有绑定真实角色和回合的工具注入范式，`project_state` 通过 `session/tasks.ts` 生成受信只读投影。`app/main.ts` 的普通 `session:send` 与 `lifecycle/send.ts` 的投递、ACK 是客户消息绑定点。现有后台投递也可因缺省落入 `kind:"message"`，消息种类不足以证明真人来源。现有 `request_choice` 可复用桌面卡呈现和客户回传，普通卡种与「替我决策」通道不具备启用授权。`app/desktop/customer-input.ts` 的应用自有本人确认卡已有来源排除机制。用同一执行器和启动校验，增加下列窄入口。

**客户来源。** 仅从实际受信主窗口 `webContents.mainFrame` 的普通 send 识别客户输入。宿主排除执行指令后签出内部来源标记，固定原稳定输入 ID、实际文本及摘要和项目/幕僚会话。排队时保持该绑定，运行时 ACK 后绑定真实 turnId。幕僚工具仅能在原会话 handle 上按当前 ACK 回合查此来源，保存提议前再检查回合有效。真实同文新发送拥有不同 ID，受信重送沿用原 ID。后台默认 `message`、回交、系统投递、内部续跑和角色自报均不能取得该标记。客户端传入的任意来源字段无授权效力。

| 接口 | 输入与权限 |
| --- | --- |
| `project_state` 的工作流目录 | 从现有 `listDefinitions`/选择规则生成有界只读输出，至少含名称、来源 `preset`/`project`、ID、版本、摘要、用途前置提示或拒绝原因。按实际定义可用性展示，项目覆盖随包预设的旧规则继续生效；A、B 与合法导入图走同一目录、校验及选择路径。为该段保留输出额度，超过额度时提示截断或按定义 ID 查，不因旧任务摘要过长而隐去全部定义。读取不创建业务记录、预留或启动控制面。 |
| `request_workflow_start({ definitionId, source, expectedDigest, reason })` | 建议 RoleTool ID `requestWorkflowStart`。仅受信项目内普通幕僚治理会话获得，调用时核验实际角色、会话 handle、当前 ACK 回合和宿主签出的原客户输入。定义选择参数只用于定位并核对当前定义，项目、原需求和决定事实沿用宿主来源。校验和保存提议后返回 `pending`、`activationId` 与定版摘要，发起回合可正常结束。独立决定上下文、后台续跑、其他角色、CLI 和 renderer 无此入口。 |
| 应用自有 `workflow-start` 选择卡 | 复用现有 Choice 渲染、受信窗口回传及项目卡排队。由宿主生成固定单选 `approve-workflow-start`/`reject-workflow-start` 和快照内容。请求 ID 与对应提议代次绑定；通用 `request_choice` 不可自造该卡。应用继续以本人保留卡核验，judge、委托、指令、无卡令牌的旧回调及错项目/错窗口回传均不能授权；「替我决策」开启也走本人卡。 |
| 内部 `startApprovedWorkflow(activationId)` | 仅应用消费 SQLite 已保存的批准、完整图和唯一启动键。仍使用同一启动服务的工作区、当前项目、治理角色、已有流程/运行、图用途和权限检查，以及原占用、版本固定和 Git owner；批准启动采用保存的图，不经 `expectedDigest` 重读定义文件。原幕僚发起回合结束前保留「已确认，待启动」。其他有效运行或项目切换时显示原因，待原项目恢复且条件满足后续办。返回原实例 ID 或真实阻塞，不经 renderer 再启动。 |

## 快照、决定与恢复

- **提议先落盘。** 持久记录规范化项目、原稳定输入 ID、文本及来源、真实回合、幕僚理由、定义来源/ID/版本/摘要及固定定义、提议代次、请求 ID、状态。宿主从项目、客户输入凭据和提议代次派生稳定 `activationId`、卡 ID 和启动键，固定原需求摘要与启动元数据（含选定 runtime），重开不重新推导指纹。每个客户需求至多有一个有效待决提议，同键同内容查原提议，同键异内容拒绝。改选需要撤销旧代次，或旧代次已拒绝、失效，才生成新卡。仅提议阶段零实例、零任务、零 Git 及零业务写权。
- **决定先落盘。** 本人答复时用与目录、提议相同的有效定义规则，重核当前项目、需求、请求身份、定义来源/ID/版本/摘要和覆盖关系。待决期间需求变更或定义改字节、删除、换源使旧代次失效，换源即使字节相同也须重提。客户拒绝或明确撤销保留终态，批准与撤销竞争时以先提交的合法决定为准。关窗、切换项目或重启只暂停呈现，重开同项目时继续呈有效原卡，本轮无按时长到期规则。批准事务同时持久提交本人决定、已确认的完整图/来源/版本/摘要，以及唯一键启动待办。重复同向查原决定，反向、已失效代次或假来源拒绝。批准后到实际启动前编辑、删除或换源，仍用批准事务保存的图。只有原启动安全门及占用冲突可阻塞启动。
- **启动一次。** 应用领取同一待办并沿用原工作区及 Git owner、版本固定、业务 SQLite、实例 ID 和 Dapr 排程补投。未实际取得 owner 之前没有工作区写权，也不接管已有实例。批准后退出、实例已经创建但回复丢失或控制面暂不可用，重新打开同项目查原提议与实例并续办，未经批准的记录不会启动。恢复扫描包含尚无实例的待决提议和已批准待办。区分「已批准待启动」「实例已创建，控制面未就绪」「已排程」「拒绝／失效／阻塞」，拒绝、失效和暂时不可用均不得被解释为批准。

## 建议影响面

- **角色工具和门禁。** 复用冻结的注册桥，最小涉及 `src/model/role.ts`、`src/common/门禁引擎/role-tool-registry.ts`、幕僚模块的工具声明及上下文、`src/pipeline/orchestration/run-role.ts` 和 `src/provider/runtime` 实际工具 schema/装配，按角色工具契约同步登记及相关测试。持久项目的普通幕僚上下文明确先查目录、选用、提议及等待本人，已有实例沿用原续办指引。业务宿主再次核验普通幕僚与真实来源，注册表允许项本身不等于应用授权。
- **编排和桌面入口。** `src/service/durable-workflow` 与其 SQLite Provider 承担持久提议/决定/启动许可和回执；现有启动守卫、Dapr 执行图与能力注册复用。`app/desktop/durable-workflow.ts`、`interface.ts`、会话注入/卡、`customer-input.ts`、主进程/preload 去掉直启路径并接入真实启动待办。Renderer 限工作流面板、桥和客户卡需要的状态。既有定义 schema、业务角色卡和 Git 发布许可维持当前边界。
- **证据责任建议。** 由编排与桌面/运行时入口按既有所有者承担业务与接线，桌面 UI 收窄面板，固定测试角色跑受影响链，独立验收核对确认版证据。此处是预计影响范围，由统筹另定实际分工和写集。

W1 先固定提议/批准/完整图与共用启动的服务契约，W2 以同一契约接真实 send/ACK、旧入口前置拒绝和应用卡，W3 保留只读状态/定义管理并剔除直启。W2/W3 共同核对应用卡使用现有项目卡队列；有其他卡时启用卡等待，不抢先或覆盖。切换项目中止呈现回调时保持原提议，W1 只消费确切的当前本人回答，Renderer 只呈现其回执。

| 用例 | 可核对证据 |
| --- | --- |
| 启用链 | 通过真实普通幕僚 RoleTool 及受信桌面卡，从客户对话到 A、B、导入第三图各一次。三类的选用记录、卡、固定摘要、本人决定和实例同一关联标识，批准前零任务/实例，批准后业务入口工作并出现第一个合法节点。至少一例从实际 Windows 候选包的普通 UI 客户输入、卡作答和查询取证，其他例可用同候选真实业务控制器与受控角色脚本。 |
| 阻断绕过 | 实际主框普通 send 入队与直发各验证一次，原输入、ACK 和提议匹配。后台缺省 `message`、内部续跑、错 Frame、假来源/ID、其他角色、独立决定上下文、通用 Choice 模仿、委托/判断和裸 IPC `enabled` 均无越权批准。分别在未提议、待决、拒绝和批准后发旧首次 A1/B1，均不创建旧新实例或任务，已有实例真实续接和旧环境正常流程可用。 |
| 重放和恢复 | 实测同键重放与异内容、明确拒绝/撤销及与批准竞争、关窗或切换项目后隔日（超过 24 小时）回原项目呈同卡、待决时同版本改字节或相同字节换源、失效旧卡和反向决定。对已批准未启动和已建实例未回复各注入一次中断；批准后启动前分别改写、删除或换源，仍按 SQLite 保存的原图、版本与原占用门只启动一次。`activationId`、决定、图摘要和 SQLite/运行时回执可查。原幕僚回合未结束、有其他卡或跨 appData/旧引擎占用时不得抢占。 |
| 交付与回归 | 同候选有受信窗口行为、实际包哈希、受影响类型/结构/卡与任务回归，新入口至少连接真实 Dapr/SQLite。复用上一候选 A/B/第三图正常链及恢复的已覆盖证据，对本轮改到的旧实例查询/回交、未决卡、v1 恢复和文件校验定向复测。保留原测试基线和取证限制，未用新包实跑的场景按实际标识；无真实线上模型、完整 OS 重启或其他平台的推断。 |
