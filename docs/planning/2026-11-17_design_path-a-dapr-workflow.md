## 使用方式与范围

客户在既有项目入口打开或初始化工作区，在持久工作流面板选择随包提供的 A、B，或导入自己的定义。用户可将预设复制到项目的 `docs/workflows/` 编辑，以相同方式放入额外的 YAML。选择后，应用显示名称、版本、摘要和准入问题。客户显式开启并启动所选定义；若配置或权限不满足，界面显示错误位置和原因。运行视图显示实例、当前步骤、尝试、待决定事项、已保存的证据与恢复状态。外部文件决定步骤、边和返工走向，写入与审批继续经原应用入口核验。

预设来自发行包资源，由同一面板列出、校验、启动。用户可以选择将预设复制至项目，或从受信选档入口导入本地 YAML。导入验证通过后写入 `docs/workflows/<id>.yaml` 并选中该 ID、版本和摘要，遇已有文件、重复 ID 或已固定版本摘要冲突时拒绝覆盖。合法项目文件优先于同 ID 的随包预设；已选的项目文件失效时显示错误，不回落预设。默认选择随包预设不会写项目文件。无 Git 时也可按已登记的项目 ID 查询实例和卡，A9 绑定仓库后仍以相同实例 ID 查找。

交付两份可编辑的预设及同一执行器，并用第三份包含受治理写入和本人发布的不同流程证明可扩展性。本轮使用现有桌面 Dapr、Scheduler、SQLite 与控制面，定位为 Windows x64 分支原型。旧实例收尾和 v1 兼容纳入本轮。默认切换、历史迁移、跨设备同步、外部 API、脚本或代码插件、角色制度变更、产品合并与发布另议。

## 定义、执行与已有实例

**定义文件。** 新契约声明 schema、ID、版本、名称、起点和有限步骤。每个步骤选择一个已注册的能力和许可的角色选择器，声明其结果分支或下一步；循环必须有持久上限与可达出口。定义 ID 只做项目内定位。同项目相同 ID/版本只对应一个摘要。任意合法 ID 和步骤名可导入；同一份 A 或 B 改名不能改变验证或权限。应用从随包预设或当前项目的 YAML 读取明确选中的文件。导入前按 YAML 1.2 严格解析，校验项目边界、未知字段、重复键、资源大小、角色/活动、完备的分支、可达性和返工上限；导入同名冲突给出错误，预设更新不覆盖项目编辑。启动时再次核验，事务保存规范化图、来源、ID、版本、摘要及执行器和活动契约版本。外部文件改错、删除或升级后，在途实例从同一快照继续。

**注册能力。** 每个能力登记允许的发起/接收角色选择器、作用范围（如只读、治理文档、项目写入、Git 或发布）、需要的可信前置、各合法结果能产生的事实，以及宿主消费者。首次准入沿可达路径核验前置，遇到多条边时只把每条进入边均已具备的事实视为保证，退修边退役对应旧证据。危险能力还须在实际执行端以当前实例、尝试、授权来源、证据及工作区重新验证。代码、任意表达式、外部命令、裸 Git 与审批豁免都不属于可配置能力。应用按真实变更资格判断适用的既有治理路线；配置引用 B 的变更能力也不能把新项目或新功能伪装成已有实现的小改。“已发布”终点必须有对应的真实合并证明；只读流程可有自身完成终点。

**能力与宿主消费。** 表中的名称描述业务能力。实现可沿用已登记的具体 action 名称，在一份能力契约中声明前置、结果事实、合法角色及作用端。配置用这些能力组合步骤。

| 能力 | 受信前置与产出 | 宿主消费者 |
| --- | --- | --- |
| 准备、受治理文档任务、只读分析 | 已绑定客户需求、真实幕僚请求和运营派发权；按当前任务、作用范围和尝试取得准备回执、已核验文档及报告。只读分析可记录既有 HEAD/工作区快照。 | `dispatch_task`、受治理角色会话、`submit_report`、`close_created_task`；写区经原门校验。 |
| 意图、方案、任命确认 | 已核验文档/基线与当前快照；通过原卡入口取得已提交的合法决定。修订退役该文档版本的下游依据。 | 现有客户卡 gateway 持久请求与决定，Service 核验依据后提交事实。 |
| 角色激活、团队基线、既有仓分支准备 | A 激活需要已确认方案及 roster，团队基线需要全员激活和有效计划。既有仓分支准备需要受信 HEAD/状态和实际仓库独占。分别产生 `role.activated` 集合或基线、任务分支及 OID。 | `activate_role_documents`、`complete_team_plan` 与受控 Git Provider。既有仓准备允许只读分流后调用；A 的初始化专属团队基线。 |
| 范围与实施 | 已有实现变更需要当前只读影响报告和真实 B3 请求派生范围；新建/新功能需要真实任命、基线及已创建的标准任务。输出写集、排他任务、已验证提交和收口。 | 真实幕僚/运营的阶段与实施派发，文件工具与 Git 写门，角色报告/收口。 |
| 独立标准、报告、归档 | 幕僚直派给有效独立验收角色。标准绑定基线与写区；报告与归档绑定同一标准、当前 accepted 候选及实际证据。 | 幕僚验收派发及真实收口、验收角色 `submit_report`、应用归档端口。 |
| 发布、交付及停稳 | 发布检查合格的实施、运营汇总、治理路线和本节点要求的归档，以及客户本人最新批准；输出真实合并、说明与送达回执。停稳需要有权运营报告、无活跃任务及作用完成证据。 | 现有 `merge-main` 卡、受控 Git/恢复端口、说明查看回执及停止入口。 |

用途由应用从已绑定的客户输入、可信角色的真实路由决定以及 Git/业务证据核定。未明确用途或证据不符时禁止发出写入授权。测试第三图以实际已有实现场景进入变更用途，YAML 和提交参数无权声明这一事实。新项目/新功能即使选用了名称相近的能力，也须满足原三卡、任命和独立验收链。应用发布能力有统一的最低门，第三图的发布节点选择要求当前独立验收归档的策略，且采用同一客户卡和 Git 消费者。解析时检查每条到达该节点的路径都产生匹配归档，执行时按已固定策略重新核对。归档结果绑定本次候选；配置可以增加需要的证据，既有强制门继续由应用核定。

**复用与权威账本。** A/B 旧阶段标签用于现有工具回执和兼容投影。每个工具请求从宿主绑定项目、实例、已关联的 flow、当前作用域/尝试、真实角色会话与父任务，读取现有领域校验及证据；模型给出的 ID、路径和哈希仅作为待核输入。旧 JSONL 可保留工具产出的任务、决定、角色与证据事实，或供旧实例读取。新实例的 Dapr 当前节点和有效待办是唯一受理依据，新实例的 SQLite 依据经校验的领域事实和 outbox 推进。将旧卡/激活/基线/归档函数中的阶段写入分开，旧阶段投影、扫描、补派和自动呈卡不能反向开放新节点。

**兼容。** 既有固定 A/B 的 JSONL 和在途 Dapr v1 仍由原入口、原执行器与原契约读取，复用同一控制面，不重写历史。若新执行语义需新注册名，沿用现有兼容预检，并在同一 Worker 注册旧名、旧活动及新契约；缺少所需兼容项时在消费前暂停和提示。两份新预设由同一个新注册能力入口执行。旧只读定义、旧 B 范围审计、发布恢复和独立交付说明及查看回执纳入受影响回归。

## 工作区身份、占用与 Git 基线

1. **选择与保留。** 持久工作流使用受信目录选择和项目注册入口。空目录沿用桌面已有的项目注册/治理初始化，尚未授权的写入保持等待；此时不初始化 Git。已存在 Git 的工作区用规范化真实根目录和 `git common-dir` 核对仓库身份。无 Git 时基于规范化真实目录和本地持久项目登记取得稳定身份，拒绝父仓库内子目录、身份不明和非受支持的链接/重定向。启动键、角色消息、事实及卡均绑定该稳定项目 ID 和实例 ID，renderer 不能自报替换。
2. **同项目独占。** 可能写治理文档、代码或 Git 的图，在任何业务派发前原子占用工作区共享的项目级持久登记，选用受控 `.ans/state/` 下的 SQLite，权限、真实目录及重定向在 Provider 确认。保留稳定项目 ID、申请键与请求指纹、实例计划、owner、原数据目录和申请状态。不同 appData 均访问同一物理登记；已有 Git 时按目录、`git common-dir` 顺序取得两处占用，沿用兼容的旧 `path-b` 仓库槽。新启动双向检查活动 JSONL、旧运行及 v1 B 的仓库独占及当前任务。既有引擎的启动和重派也须遵守同一登记，识别按原权责恢复的既有在途实例。只读实例可独立运行，由实际作用端保证不写。进程退出、关闭开关或效果不明不释放，终止且经核对无未决写作用后才释放。
3. **占用中断与 A9 绑定。** 启动占位与业务库分开落盘时，申请保留原始身份与配置摘要。原数据目录的同键同内容重试按已登记快照补建同一实例或取回回执，另一 appData 不接管，异内容拒绝；无法证明申请内容或当前状态时阻塞。A9 运营调用原 `complete_team_plan`，核准计划、名单和冻结文档后，应用按既有规则准备 `.gitignore`、基线及任务分支。空仓库只允许该基线能力初始化。先持久记基线意图和操作前证据，持目录独占创建 Git 并绑定实际 `git common-dir`。同一仓库的路由在录入期间须从实际仓根检查目录占用，另一 worktree 也检查这项登记和共同仓库。绑定未提交前不可调后续 Git/角色作用；原项目 ID、实例、队列及操作键保持一致。
4. **A9 恢复。** 重开先核对实际仓库根、是否原意图创建、初始分支、`.gitignore` 和基线提交或任务分支的父关系及 OID，只补做能证明尚未开始的合法步骤。已发生且效果可唯一验证时补记同一基线与绑定。遇不相符仓库、意外修改、另一占用或效果不明则阻塞，零借用、清理或重复提交；错误在面板可查。复用既有仓库时也保留当前基线检查，路径 B 从空目录仍拒绝启动。

## 预设业务合约

| 预设步骤 | 受信输入、输出和判断 |
| --- | --- |
| A1/A2 → A3 | 幕僚向运营发阶段请求。A1 在运营真实创建产品准备任务时达到该阶段完成条件。A2 独立撰写 `docs/product/<flowId>-intent-vN.md`，运营凭应用验证的证据 accepted 收口。幕僚按原授权准备 `docs/intents/<intentId>.md`，应用在呈卡及确认推进前核对入口、flow、版本、intentId 和批准字节摘要。应用生成真实 `documentRefs` 与卡标记，入口缺失或不符时保持阻塞，补齐后按同请求重试。修订回 A2 的新版本。 |
| A4/A5 → A6 | A4 在运营真实创建策划准备任务时达到该阶段完成条件。A5 有独立方案任务，按 proposal、modules、roster、architecture 实际证据 accepted 收口。A6 幕僚原卡入口取当前已确认意图与四件方案材料，应用计算五件 `documentRefs` 并绑定来源和对象，客户决定绑定该快照。接受进入 A7，有限修订回 A5，拒绝阻塞。 |
| A7/A8 → A9/A10 | A7 在运营真实创建人事准备任务时达到该阶段完成条件。A8 另有激活任务，以 A6 决定、名单和真实角色文档为凭据，按角色幂等，齐备才推进。A9 团队计划/基线获应用回执后，A10 经原卡入口由应用按当前 roster 生成合法的多选项并核验决议选集。决定保留 `source:"stage-a10"`、workflow 与 roster 引用，供实施真实授权。A10 自身不派实现。 |
| A12a → A11 → A12b | 幕僚直接派独立验收标准任务，真实创建且绑定当前基线与有效验收角色后，才受理 A11 的实现派发；标准不必先收口，但必须能作为本轮 A12b 的依据。运营据 A10、模块和基线派 A11；应用核对当前写集和提交。实现 accepted 后，真实验收角色核对当前候选并交 A12b 报告，应用验证标准、报告、归档哈希和对应候选。验收不通过只可合法返工或停止；缺运行证据时仅可按原受信处置选择显式轻量验收，归档须留具体限制及决策，交付披露「运行期未验证」。归档失败不能进入发布。 |
| A13 | A12b 有当前归档及运营最终报告才生成发布预览。客户本人经现有应用卡批准；应用经受控 Git 端口本地合并。已有 Git 效果且可核验只补记一次，冲突、漂移、未知效果安全停。交付说明与首次显示回执独立记录，实际 OID、diff 和验收限制可查。 |
| B1 → B4 | 新预设通过同一能力契约实现 B1 只读分析、B2 范围决定随真实 B3 请求提交、B3 运营派工和收口、B4 客户本人发布。保留已核实的角色和证据、单次范围审计、任务/回交恢复以及符合前轮约定的独立交付说明。 |

**卡及返工。** A3/A6/A10 三张卡独立保存快照、尝试、对象摘要、决定来源及受信回执。客户本人操作及既有显式「替我决策」按原角色、当前开关与 delegation revision 复检，撤销委托不认可旧代次。A13 与 B4 仅接受客户本人。未决卡重开恢复同一请求，决定落盘后掉线按原键续投；旧快照及冲突决定拒绝，漂移需生成新卡。A2/A5/A11 返工遵守图的上限、旧证据退役和新尝试门，不能靠 YAML 给原角色追加写权。停止或改道沿用真实停稳报告、关闭在途请求和无活动副作用门，停稳不明保持阻塞。改道须结束原实例，获明确启动后由新定义另起实例，旧审批、许可和队列不能跨用。

**验收标准待办。** A12a 或同能力节点由幕僚先真实创建标准任务，SQLite 持久保留独立待办及实际任务 ID、创建者、验收角色、批准依据、基线、尝试和写区；开始 A11 后仍可在该固定作用域内收报告并由幕僚真正收口。A11 当前节点不会使原标准回交变成迟到，无须在 YAML 增加并行语法。实例重开可恢复独立待办。变更依据或换代时再次校验匹配和有效性，待办不能跨实例或给旧候选放行。A12b 等匹配且已收口的标准及当前已接受候选，必须用实际报告和归档证明推进。

**第三图接线。** 隔离测试仓使用当前既有模块、可核验 Git HEAD/状态，以及合法配置的独立验收角色与模块写区。先用真正只读分析能力得到报告并分流，期间不调用会创建提交或切分支的 B 基线端口。写支以已记录 HEAD/状态重新核验后才调用同一既有仓准备能力、绑定和审计真实范围，再复用验收标准、受限实施、独立报告及应用归档。本人发布预览包含当前实际提交、范围、归档证据和运营汇总。另一支只读收口，受控作用端始终拒绝写项目或改 refs。只读完成条件要求无已发出或未知的写作用，尝试从写支绕向只读完成应拒绝。A 仍只在 A9 初始化；B 预设保留原基线准备顺序。

## 五层调用及交接

| 层 | 入口和消费者 |
| --- | --- |
| Interface | 既有 Electron IPC 提供导入、列表、验证、显式启动及按实例查询；受信项目窗口提供卡操作、构成任务来源并显示错误。角色工具仍走已有宿主门。 |
| Pipeline | 统一 Dapr 定义执行和兼容 Worker 装配。步骤根据固定图与已消费事实推进。桌面 observer 订阅投影及持久作用意图，回接真实角色派发、报告、卡、Git 和展示回执。Observer 重连可重取待办，回调不拥有阶段。 |
| Service | 校验定义、能力及可信前置，处理项目/仓库独占，验证角色、任务、文件、卡和验收，写业务事实与待投递项，提供已授权的作用认领、结算及查询投影。 |
| Provider | 现有文件、SQLite、Dapr 客户端和进程、角色会话、Git 及归档副作用端口。按持久幂等键恢复可验证的实际效果。 |
| Model | 定义、能力、步骤结果、事实与证据引用、对象代次、尝试和错误的数据契约；供各层使用。 |

沿 `Interface → Pipeline → Service → Provider` 调用。定义解析与外部文件访问通过所属下层公开入口。审批、任务、报告和作用结果按项目、实例、定义快照、步骤及尝试入账，事实与 outbox 同事务提交后才对外确认。`raiseEvent` 成功只是 Dapr 已受理；对应消费结果及下一作用意图持久记录后才闭合待办。派发/送达/执行、报告/收口、核验/归档以及合并/交付各有回执。宿主实际作用端串行认领；未知 Git、归档或模型效果先核对，迟到旧尝试不重放或改变当前结论。数据事实用现有应用 SQLite，Dapr 历史用现有状态 SQLite，两者由原桌面控制面管理。
