## 复核结论

**建议修订后提交。**

理由：方案方向与闸门 0（意图记录 ②「预知门控全部删掉」）及客户补充规格一致；对现状代码的定位（`inspectInitializationProtection` 的 B1–B14、调用点、Claude/Pi 结构性 unknown、`official-pure-preparation-unproven`、失败准入 recheck、run-stop/controller-stop 的 native 要求、journal 校验器与 `checkGitPolicy`）经只读复算基本准确；「动作时授权 + 可选证据」的总体原则成立；与 PR #72 INV-2（写/发布门不读 `applicationMediation`）未发现直接冲突；未出现与客户意图明显相反的方向问题，因此不属于「暂不建议提交」。

但 F1–F5 是影响客户确认基础与验收可判性的重要发现：
- F1：新 gate 的输入契约与 H8/H9/authorization 输出不一致，AC-1 的 policy/lease 审计字段没有实现落点；
- F2：`finalizeRunChange` 的宿主继续 actor（deferred/disposed/无 active tool）会被新伪代码拒绝，直接影响「Claude/Pi 运行成员可 run-stop」的客户可见结果；
- F3：journal `authorization` 若按现状加入现有重放/结算身份比较，会破坏 pending-recovery/重试/旧 journal 兼容；
- F4：prepared/failed 条目与 inspection 失败的 active 条目不再被逐条检查，替代门存在 fail-open 缺口；
- F5：Codex native 可选缺少 `ensureAdapter`/`bindRole` 的 fallback，AC-5 的示例又混淆 strict `toolSurface` 与 native plan。

F6–F9 为一般发现（drain reason 集合、`stopAndInspect` 活动循环、foreign MCP/未封闭工具的跨会话风险、N5/N7 不变量措辞），建议在提交闸门 1 前修订；F10–F12 为建议级。修订后建议由沟通就受影响部分（§3.3、§3.4.3、§4.1/Q7、§5 AC-1/AC-8/AC-16/AC-20、§6.1）启动一次窄复核，再提交闸门 1。

本结论仅是建议，不是客户确认、不是实施授权、不是验收基线，也不阻断沟通提交闸门 1。
