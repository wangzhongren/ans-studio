# 设计（草稿 v2）：两条固定工作流路径——新增与修改（2026-11-10）

- 日期：2026-11-10
- 状态：**客户确认进入开发**（2026-11-10「让各自的角色重新开始开发」；第六节四个默认项按默认采纳）。本设计作为本次重构依据。
- 背景：贪吃蛇冷启动全链真跑暴露——把 Git 当"治理数据库"（trunk/pin/冻结闭包/stable-write 许可/bootstrap）后，默认工作流被拆成十几道状态机接缝，真跑连环卡死。客户决定：**默认流程收敛为两条固定路径，且 Git 回归普通用法**。
- 核心原则：
  1. **Git 只装代码，执行普通用法**：实现角色在任务分支提交；"发布"= 合并到 main（高风险动作，需客户本人确认）。**取消** trunk ref、bootstrap、冻结闭包、候选 ref、stable-write 许可、run pin 等全部治理型 Git 机制。
  2. **治理状态走应用账本**：意图/方案/团队计划/角色卡/审批/审计都是项目目录下的普通文件（`-vN` 命名做版本化）+ 应用维护的 append-only 账本（`.ans/state/*.jsonl`）。"依据钉死"以应用记录文档哈希实现，不进 Git。
  3. **派发分裂**：**运营是生产线的唯一派发者**（产品/策划/人事/实现角色的任务全部由运营派发）；**独立验收由幕僚派发**（质量门与生产派发分离）；幕僚不派生产线角色。
  4. **幕僚做产线调度**：按固定路径驱动阶段推进（请求运营派发下一步）、呈客户确认卡、**调节验收强度**、汇总交付；不自行做专业判断，**依据专业角色的专业建议做决定**。
  5. 客户确认卡保留 **3 张**：意图确认、方案确认、任命确认（**不合并**）；高风险动作（发布/删除/外部副作用等，沿用既有清单）无论哪条路径都需客户本人确认。
  6. 审计与留痕不弱化：append-only 审计、judge 代批、文档格式说明（doc_format）保留；角色写区边界（文件级）保留。
  7. 默认路径**固定、确定**；例外情况（大项目/高风险/客户要求）可按需启用更重的机制，但不得成为默认路径的前置。

## 〇、角色权责

| 角色 | 职责 |
| --- | --- |
| **幕僚** | 客户唯一入口；产线调度（驱动阶段、呈 3 张客户卡、汇总交付）；**派发独立验收**、**调节验收强度**（轻量/完整）；依据专业角色建议做决定；不派发生产线角色、不自行做专业判断 |
| **产品** | 撰写意图（范围/目标/验收要点/非目标） |
| **策划** | 撰写方案+人员名单+模块+架构+契约（含验收标准） |
| **人事** | 按名单**机械**建角色卡/边界/激活（不自行增删角色） |
| **运营** | **生产线唯一派发者**（派产品/策划/人事/实现角色）；撰写团队计划；执行基线准备（见下）；集成汇总实现报告 |
| **实现角色** | 开发/自测/报告；任务分支提交 |
| **验收** | 由幕僚派发；实施前写标准、实施后独立判定（强度由幕僚调节） |

## 一、基线准备（简化后仅 3 件小事，由运营发起、应用执行）

1. **git init**：为项目初始化一个普通 Git 仓库（若尚未初始化）；
2. **哈希入账**：应用把当前治理文档（意图/方案/名单/模块/架构/契约/团队计划）的 SHA-256 记入应用账本（作为本轮"依据快照"）；
3. **团队计划落盘**：运营写团队计划文件（`docs/scheduling/<flowId>-team-vN.md`），应用校验结构（名单/模块/写区归属）后入账。

- 失败面收敛为：git init 失败（环境/权限）、文档不可读、团队计划结构不合法——每种都**fail-closed 且把真实原因交回运营/幕僚**，不再产生“不可提交的客户卡”。

## 三、路径 B：修改（既有实现的变更/修复）

| 步 | 角色 | 做什么 | 产物 | 客户卡 |
| --- | --- | --- | --- | --- |
| B1 | **运营 → 专业角色** | 运营派专业角色（模块属主优先；涉契约/结构用技术架构角色）做只读影响面分析并给专业建议 | 影响面/修改建议报告 | — |
| B2 | **幕僚** | 依据专业建议确定修改范围（不做技术判断） | 修改范围记录 | — |
| B3 | **运营 → 实现角色** | 运营派现有实现角色按范围修改（任务分支提交） | git 提交、测试/报告 | 高风险动作才出卡 |
| B4 | **运营 → 幕僚 → 客户** | 运营收报告交幕僚；幕僚汇总（发布=合并 main，需客户确认） | 交付说明 | — |

- 不涉及产品/策划/人事/团队计划/基线准备；不重建版本（除非客户要求走路径 A）。

## 四、门/机制的处置（相对现状）

| 现状机制 | 两条路径下的处置 |
| --- | --- |
| 意图/方案/任命卡 | **保留**（3 张，不合并） |
| trunk ref / bootstrap / 冻结闭包 / 候选 ref / run pin / stable-write 许可 | **全部取消**（默认路径不再存在这些概念） |
| Git 写候选/发布三段式 | 简化为：任务分支提交 + 合并 main（发布确认） |
| 16 MiB 清单预算 / 发布租约 / run 歧义 | 随上述机制取消而不存在 |
| 角色写区边界（文件级） | **保留**（写入越界拒绝） |
| append-only 审计 sidecar | **保留** |
| judge 代批 | 保留（作用于剩余客户卡与高风险动作） |
| doc_format 文档格式说明 | 保留（角色按权威格式写文档） |
| 高风险清单（发布/删除/支付/外部/权限/迁移） | 不变，两路径均需客户本人确认 |

## 五、对在研工作的影响

- **initial-workflow 发布补完修复**（分支 `feat/initial-workflow-publication-completion`，实施中 22 文件）：它修的是将被取消的 trunk 发布机器；**本设计生效后不再需要，暂停并留作历史**（不删除分支）。
- 其余已合并修复（judge 代批、文档格式、提案卡绑定等）继续有效；与 Git 治理机器相关的部分（bootstrap 闭包修复等）在新默认路径下不会被触达，保留代码但不再是路径前置。
- 现有项目（含贪吃蛇 target 的历史 trunk t1/t2 状态）按新路径可直接忽略 trunk 概念，用普通文件+账本继续。

## 六、剩余待定（默认见括注）

1. 基线准备失败可见性（默认：只回报幕僚/运营，不弹客户卡）。
2. 路径 B 触发判定（默认：幕僚判断；客户可明示覆盖）。
3. 幕僚暂停/改道（默认：具备请求能力，由运营执行）。
4. 合并 main 的确认形式（默认：客户本人确认卡；也可委托 judge 代批——高风险清单保持不变）。

## 七、非目标

- 不改五个内置角色与项目角色的边界模型；不新增角色；不新增客户可见的门。
- 不弱化审计与高风险确认；发布/tag 仍需客户明确授权。
- 本设计不含 UI 改动（卡片呈现沿用现有）。
