## 代码现状（已核实，v1.8.3 / main `32d8f0d`）

1. 「替我审批」开启后，判断 agent 是 shell 命令的**唯一审查者**（2026-10-19 客户裁定）；判拒**终结拒绝、不打扰客户**；`manual`（超时/解析失败/重试超限等）在桌面端**一律按拒绝处理**、不弹确认卡（`app/desktop/operator-channel.ts`）。
2. 判断 rubric 只审五类系统风险：破坏/装包/提权、卡死（长驻服务、交互式命令）、越界（写项目外、读凭据）、并发写坏数据、端口冲突；**业务必要性明确不归判断 agent**（`src/common/编排/shell-judge-prompt.ts`）。
3. 同一命令连续判拒上限默认 2，第三次转 `manual/retry-capped`；但桌面端把 `manual` 也按拒绝处理，**「转手动确认」阀门在桌面不可达**；命令稍有改写即视为新命令、计数不累计（`src/common/编排/shell-judge.ts`）。
4. 目前唯一出路是回执里的「关闭『替我审批』后重试」——关全局开关后每条命令都弹手动确认（`src/common/编排/shell-judge-verdict.ts`、i18n `main.operator.judgeWayOut`）。
5. 「替我决策」是治理卡（提案接受、任命、验收）上判断 agent 按推荐项**代批**的开关，与 shell 审批是两条通道（i18n `ui.judge.decisionOn/decisionOff`）。

## 意图理解（客户确认的方案，三层）

1. **判拒后的客户确认通道（核心）**：判断 agent 判拒后，角色可对**这一条精确命令**申请客户确认；应用向客户呈现确认（命令原文、cwd、判拒理由、角色一句必要性说明、judge 给的替代方案），选项为「允许一次 / 本会话允许该精确命令 / 拒绝」，无答复默认拒绝。客户批准记为**客户手批**（与 judge 放行在审计上可区分）。
   - 约束：**硬拒档**（凭据/破坏/外发，`c=deny`）与**确定性封堵档**（长内联、无界递归搜索）**不提供**该通道，保持终结拒绝；同一命令每会话最多申请一次；**不允许判断 agent 自翻判拒**（该确认的决策者只能是客户，不接入「替我决策」代批）。
2. **确定性白名单扩容（减少误伤）**：项目内例行命令（`npm test`、`npm run <script>`、`node --test`、`tsc`、`git status/diff/log`、只读查看等）走确定性放行、不惊动 judge；`npm ci`（按锁文件安装）与 `npm install <新包>` 分档处理，前者可确定性命中，后者保留判拒 + 申请确认。只对**静态可证明**为项目内例行操作的命令放宽，fail-closed 不变。
3. **回执措辞与开关粒度**：判拒回执的出路从「关闭『替我审批』后重试」升级为可执行的「转人工确认」入口；并提供「本会话暂停自动审批」等更细粒度选项，不再要求客户动全局开关。

## 非目标

- 不让判断 agent 推翻自己刚做出的判拒；不把 shell 判拒接入「替我决策」代批。
- 不放宽硬拒档与确定性封堵档；不做「一键允许所有」；不在无答复时默认放行（fail-closed 保持）。
- 不改变治理卡（提案/任命/验收）的「替我决策」语义；不改变 2026-10-19「开关开启时 judge 是唯一自动审查者」的其余范围——本意图只增补**判拒后的窄口径客户升级通道**。
- 不在闸门 1/2 确认前改任何应用代码或测试。
