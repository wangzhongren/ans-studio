## 沟通的意图理解

1. **目标**：从现在起，ans-studio 的开发按本地 `ans-governed-construction` 技能的治理流程管理，不再只依赖对话中的临时约定。
2. **范围**：
   - 客户入口只保留 ANS 沟通；需求先记录在 `docs/communication/`，依次经过闸门 0（意图确认）、闸门 1（策划方案确认）、闸门 2（角色指派确认）。
   - 采用技能内置的五个管理角色：沟通、策划、人事、统筹调度、独立验收。策划、调度、验收在独立子代理上下文运行；开发、测试、装配、项目管理等工作角色只由统筹调度派发。
   - 继续使用仓库已有的 worker 角色卡（运行时核心、桌面UI、桌面窗口、测试、项目管理等）。现有 `项目管理`、`独立验收` 两张管理类角色卡是否迁移或停用为技能内置角色，作为单独的迁移决策处理，不在本轮自动执行。
   - 验收按技能 `references/testing.md` 的 T0–T3 风险分档执行：默认核对原始证据并复用同一候选的有效结论，只补缺失、失效或高风险检查；全量回归仅在 T3 或证据不足时执行。这与客户此前「审核没必要每次都独立复核」的意见一致。
3. **优先级**：先建立管理流程、记录与闸门，再按该流程处理具体开发任务。
4. **非目标（本轮不做）**：
   - 不改产品代码、测试、构建配置或发布配置；
   - 不新建或修改 worker 角色卡与边界；
   - 不创建 `.ans/project.json`，不伪造 task_ops 凭据或调度记录；
   - 不自动迁移、停用或重命名现有 `项目管理` / `独立验收` 角色卡；
   - 不改变任何角色的既有写权。
5. **现状与已知约束**：
   - 仓库当前没有根 `docs/`，没有 `.ans/project.json`；已有 `角色卡/` 下多张 worker 角色卡和 `boundary.yaml`。
   - `角色卡/项目管理/boundary.yaml` 已包含根 `docs/scheduling/` 条目；`角色卡/独立验收/` 的验收文档在 `角色卡/独立验收/docs/`。采用技能内置统筹/验收后，职责与路径可能重叠，需由统筹在迁移计划中列明，经闸门 2 和人事处理。
   - 技能规定旧项目不会因更新技能而自动把已有项目卡换成内置角色；迁移必须先由统筹列出职责、卡与边界、未完成任务、配置绑定和缺失角色，形成迁移计划。
