# 意图记录：每个文档格式都要有说明，且每个角色都能读取到（2026-11-09）

- 日期：2026-11-09
- 记录角色：ANS 沟通（Communication）
- 客户原话：「每个文档格式要给说明，并且让每个角色都能读取到」

## 背景

贪吃蛇真实运行中，产品撰写意图文档第一版缺少应用校验必需的 frontmatter 字段 `schema: project-intent/v1`，导致意图确认卡被门禁拒绝、需要一次返工；同一轮运行中幕僚也报告 `dispatch_task`/`git_candidate` 的参数 schema 在会话里呈空。客户据此提出本要求：**每个文档格式必须有权威说明，并且所有角色都能读到**。

## 理解与范围

1. **覆盖对象**：应用读取/校验的**每一种文档格式**——至少包括全部版本化治理文档的 frontmatter schema（`project-intent/v1`、`project-proposal/v2`、`project-modules/v2`、`project-roster/v3`、`project-architecture/v1`、`project-topology/v2`、`project-assets/v1` 等）、团队计划（team plan）、workflow、角色卡、boundary.md / boundary.yaml、验收记录、变更/修复记录；以策划对解析器/校验器的**全量清点**为准，不得遗漏被应用真实解析的格式。
2. **说明内容**：每种格式给出权威规范——必填/可选字段、类型、允许值/枚举、版本规则、最小合法样例与常见错误示例；说明必须与**实际校验器**一致（单一事实来源，最好由测试钉住，不允许"文档说一套、代码校验另一套"）。
3. **可读取性**：「每个角色都能读取到」——所有内置治理角色与项目角色都必须能获得这些格式说明（途径由策划设计：内置只读工具 / 技能参考 / 项目内注入的格式文档等均可，但须对全部角色可达、随版本演进、不产生漂移副本）。
4. 格式本身**不放宽**：这是"把既有校验规则讲清楚并让所有角色读得到"，不是修改校验规则。

## 非目标

- 不改变任何文档的校验逻辑/字段约束（如需变更另开）。
- 不替代既有角色卡/工作流必读机制；不新增第二份互相漂移的说明。

## 流程与授权

- 闸门 0：客户消息即确认（要求明确）。
- 闸门 1/2：按既有预授权与全量委托（`docs/communication/2026-11-07_preauthorization_proceed-without-gates.md`）免逐次确认；本要求作为**独立变更**由策划出方案（含独立评审）与 B1、统筹出团队计划并派发实现与独立验收。
- 与同日的「judge 代批生效」变更（`docs/communication/2026-11-09_intent_judge-delegated-decision-effectiveness.md`）并行推进；两变更分别记账、避免同文件冲突。
- 验收须含：每个格式说明与校验器逐项一致（测试钉住）；至少一个真实运行场景证明普通角色（如产品）依说明一次写对格式，以及全部角色可读取到说明。
