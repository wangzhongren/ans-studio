# 意图确认：派发护栏只保留「谁能给谁派发」，不再按任务状态拒绝

- 日期：2026-11-02
- 提出人：客户
- 记录角色：ANS 沟通（Communication）
- 闸门 0 状态：**已确认（2026-11-02）**
- 变更类型：产品派发行为/治理规则修订；预计风险档位 **T3**（由策划定档）
- 范围澄清：沟通追问「哪一层」后，客户选择 **产品派发前置**（ans-studio 运行时），不是 ANS 技能自身的管理闸门。

## 客户原话

> 现在感觉这个规矩护栏，有点重了，规矩护栏应该放松一点。规矩护栏，应该只管控谁能给谁派发任务，而不能管任务状态是否满足。

## 意图理解

1. **派发是否受理，只看角色授权关系**：发送者身份、目标角色类型、目标是否真实存在等「谁能给谁派发」的条件满足即可派发；不再因为 run、名单、D3、意图/方案文档、交付任务、模块绑定、版本化文档等「任务状态」不满足而拒绝。
2. **保留必要的角色授权**（至少）：不能派给自己；幕僚不直接给项目 worker 派实现；运营只给项目 worker/质检派发；只有幕僚/运营可以派发；目标必须是真实存在的项目角色。
3. **状态类前置不再阻断派发**：是删除，还是保留为可见提示/诊断记录，由方案确定；默认倾向不阻断、保留记录。
4. **派发与任务流转解耦**：任务创建后继续按现有流程流转；本变更不改变写权/边界、验收判定和客户闸门。
5. **与已取消的 run-change-auto-approve 的关系**：若状态前置不再阻断派发，原来因 `run-role-missing` 等触发的 run-change 卡可能不再是阻塞点；是否保留卡片/代批逻辑由方案评估，不在本次意图中预设。
